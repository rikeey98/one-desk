# Spec: 컨텍스트 점유가 턴마다 100% 가까이 튀었다 떨어지던 것

- 출처: 사용자 보고(2026-09-28) — "대화를 할 때마다 (링이) 100 가까이 되었다가 다시 줄어들었다가 한다".
  원인이 분명하고 범위가 어댑터 한 함수라 intent·plan은 두지 않는다.
- 바꾸는 설계: `docs/sdlc/run-info/spec.md` §8의 "`iterations`가 없으면 최상위로 폴백한다"
- 작성자: 권용현 (초안: Claude)
- 상태: 구현 완료 (2026-09-28, 사용자 승인)

## 1. 원인

개발 장비의 DB(claude 턴 9개)는 전부 정상이었다 — 점유 3.8%→22.6%로 단조 증가, 창 1,000,000.
보고된 모양을 만드는 경로는 `claudeCode.ts`의 `resultUsage`에 둘 있었다.

1. **`usage.iterations`가 없으면 최상위 `usage`로 폴백했다.** 최상위는 턴 안의 모든 요청을 더한 값이다.
   같은 DB에서 그 합은 점유의 약 5~35배였다(예: 점유 218,335 / 합 7,607,037). 도구를 많이 쓴 턴은
   창을 넘어 `>99%`, 도구를 안 쓴 턴은 합 ≈ 점유라 정상 — **턴마다 튀었다 떨어진다.** `iterations`가
   빠지는 환경(CLI 버전·provider)에서 그대로 나온다.
2. **창 크기를 `modelUsage`의 첫 항목에서 읽었다.** 한 턴에 보조 모델(창 200k)이 같이 쓰이고 그것이
   앞에 오면 1M 창 대화를 200k로 나눠 비율이 5배가 된다.

## 2. 결정

- **FR-1.** `iterations`가 없거나 비었으면 `contextTokens`는 null이다. 토큰 합계·비용은 그대로 싣는다.
  화면(`conversationUsage`)은 점유를 모르는 턴을 건너뛰므로 앞 턴의 (점유, 창) 짝이 남는다 — 이미 있던 규칙.
- **FR-2.** `contextWindow`는 `modelUsage`에서 프롬프트(입력 + 캐시 읽기 + 캐시 쓰기)를 가장 많이 처리한
  모델의 것이다. 동률이면 앞의 것. init의 `model`과 맞추지 않은 이유: `parseLine`은 한 줄만 보고 앞 줄을
  기억하지 않는다(전체 설계 §7) — 맞추려면 `RunUsage`에 모델별 창 표를 실어 manager가 고르게 해야 해
  IPC 모양이 바뀐다. 대화를 싣고 도는 모델이 프롬프트를 가장 많이 처리한다.

## 3. 우려

1. `iterations`가 늘 빠지는 환경이면 링이 아예 서지 않는다(글자 `사용량`). 틀린 게이지보다 낫다고 봤다.
2. 이미 DB에 저장된 부푼 값은 고치지 않는다 — 원본이 없는 옛 run은 다시 계산할 재료가 없다.
3. 보고 환경의 원본 줄(`raw.jsonl`의 `result`)로 원인 1·2 중 어느 것이었는지는 확인하지 못했다.
