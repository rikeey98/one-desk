# Intent: 대화에 실행 정보 표시 — 모델·사용량·컨텍스트

- 작성자: 권용현
- 상태: 승인됨 (2026-09-21)
- 작성일: 2026-09-21

## 문제

**대화를 보고 있어도 그 턴이 무엇으로 돌았는지, 얼마나 썼는지 알 수 없다.**

지금 화면에 없는 것이 넷이다.

1. **어떤 모델로 돌았는가.** `run.model`은 DB에 있지만 화면에 안 나온다. 게다가 이 값은
   비어 있을 수 있다 — 빈 값은 "CLI 자신의 기본값"을 뜻하므로(workspace 기본값 작업에서
   정한 규칙), 사용자는 자기가 방금 opus로 돌렸는지 sonnet으로 돌렸는지 **앱만 봐서는
   영영 알 수 없다.** 실행 패널에서 모델 칸을 비워 두는 것이 기본 사용법이라 이 경우가
   대부분이다.
2. **어떤 effort로 돌았는가.** 앱에 effort라는 개념 자체가 없다. 컬럼도, UI도, CLI 인자도
   없다. 두 CLI 모두 지원하는데(아래 실측) 앱이 한 번도 건드리지 않아, 같은 모델이라도
   추론을 얼마나 시켰는지가 대화마다 오리무중이다.
3. **얼마나 썼는가.** 토큰도 비용도 화면에 없다. 두 CLI가 매 턴 정확한 수치를 보내주는데
   **어댑터가 그대로 버린다** — claude의 `result.usage`·`modelUsage`·`rate_limit_event`는
   파싱조차 안 하고, opencode는 코드 주석이 대놓고 "`step_finish`의 토큰·비용은 아직 쓰는
   곳이 없다"고 적어 두고 버린다(`core/runner/adapters/opencode.ts`).
4. **컨텍스트가 얼마나 찼는가.** 대화는 턴을 거듭할수록 세션이 무거워지는데, 한계에
   가까워지는 것을 알려주는 신호가 없다. 긴 대화가 어느 순간 이상해져도 원인을 짐작만 한다.

넷은 성격이 다르지만 한 가지를 공유한다 — **실행의 조건과 대가가 전부 화면 밖에 있다.**
one-desk의 목적이 "CLI에게 넘긴 일을 앱에 기록하는 것"인데, 정작 무엇으로 얼마나 돌렸는지는
기록되지 않는다.

## 실측 — 두 CLI가 실제로 주는 것

2026-09-21에 이 장비에서 직접 측정했다 (claude 2.1.278, opencode 1.18.30).

| 알고 싶은 것 | Claude Code | OpenCode |
|---|---|---|
| **모델** | **관측된다** — `system/init`의 `model`이 `claude-opus-5[1m]`처럼 변형까지 정확히 온다. `result.modelUsage`의 키와 `canonicalModel`도 같은 값 | **관측되지 않는다** — 스트림 어디에도 모델이 없다(`step_start`·`step_finish`·`tool_use`·`text` 넷뿐). 우리가 `-m`으로 넘긴 값만 알 수 있고, 안 넘기면 무엇이 돌았는지 모른다 |
| **effort** | **관측되지 않는다** — `--effort <low\|medium\|high\|xhigh\|max>` 플래그는 받아들이지만 스트림이 되돌려 주지 않는다(`--effort high`로 실행해 `init`·`result` 전 필드를 확인함). 즉 **앱이 보낸 값으로만 알 수 있다** | **관측되지 않는다** — `--variant`(provider별 reasoning effort, 예 `high`·`max`·`minimal`)가 같은 자리다. 역시 echo 없음 |
| **토큰** | **관측된다** — `result.usage`: `input_tokens`·`output_tokens`·`cache_read_input_tokens`·`cache_creation_input_tokens`·`output_tokens_details.thinking_tokens` | **관측된다** — `step_finish.part.tokens`: `{total, input, output, reasoning, cache:{read,write}}`. 스텝마다 오므로 합치거나 마지막을 쓴다 |
| **비용** | **관측된다** — `total_cost_usd`, 모델별 `modelUsage[...].costUSD` | **관측된다** — `step_finish.part.cost` (무료 모델은 0) |
| **컨텍스트 창** | **관측된다** — `modelUsage[...].contextWindow`(실측값 1,000,000)와 `maxOutputTokens`(64,000). 창 크기를 앱이 표로 들고 있을 필요가 없다 | **관측되지 않는다** — 창 크기를 알려주는 필드가 없다 |
| **요금제 소진율** | **관측된다** — `rate_limit_event.rate_limit_info`: `five_hour`·`seven_day`의 `utilization`(0~1)과 `resetsAt`. 실측 예: 5시간 창 3% 사용 | 없음 — 구독 한도라는 개념 자체가 다르다 |

읽어야 할 결론 셋:

- **"무엇으로 돌았나"는 claude에서만 공짜다.** OpenCode는 앱이 지정하지 않으면 알 수 없다.
- **effort는 어느 쪽도 되돌려 주지 않는다.** 그래서 "effort를 보여준다"는 **먼저 앱이
  effort를 고르고 넘긴다**를 포함한다 — 표시만 붙이는 작업이 아니다.
- **사용량·컨텍스트는 이미 매 턴 도착해 있고 우리가 버리고 있다.** 새로 알아낼 것이 없고
  파이프라인에 태워 저장하기만 하면 된다.

## 원하는 결과

대화를 보고 있으면 **그 턴이 무엇으로 돌았고 얼마나 썼는지가 한눈에 보인다.**

- 턴마다 **어떤 모델로 돌았는지**가 보인다. 모델 칸을 비워 CLI 기본값으로 돌렸더라도
  claude라면 실제로 쓰인 모델이 보인다.
- 턴마다 **얼마나 썼는지**가 보인다 — 토큰(과 비용).
- **컨텍스트가 얼마나 찼는지**가 보인다. 남은 여유가 줄어드는 것이 눈에 띈다.
- 이 모든 것이 **조용하다.** 대화록의 주인공은 여전히 주고받은 말이고, 실행 정보는 곁에서
  읽히되 말을 가리지 않는다. 사용자의 표현 그대로 "깔끔하게".

## 영향 범위

- **사용자**: agent를 실행하는 모든 사용자(현재 한 명, 작성자). 특히 긴 대화를 이어가거나
  비용이 신경 쓰이는 사용자.
- **시스템**:
  - `core/runner/adapters/*` — 지금 버리는 필드를 이벤트로 낸다. 두 어댑터가 서로 다른
    모양의 원본을 **같은 모양**으로 정규화해야 한다(어댑터의 존재 이유).
  - `shared/events.ts` — 사용량을 나를 이벤트(또는 기존 `result`의 확장).
  - `core/db/schema.ts` + 마이그레이션 — 턴마다 남길 값이므로 **`0006` 마이그레이션이
    필요할 가능성이 높다**. 로그 파일에만 남기면 목록·인박스에서 집계할 수 없다.
  - 렌더러 — 대화록의 턴. `Transcript` 근처. **실행 인자는 건드리지 않는다** — effort가
    범위 밖이므로 CLI에 새로 넘기는 플래그가 없다.
- **건드리지 않기를 바라는 것**: 권한·맥락 조립·큐. 이 작업은 실행의 **관측**이지 실행
  자체가 아니다.

## 제약

- `core/`는 `electron`을 import하지 않고, `renderer/`는 `core/`를 import하지 않으며, IPC
  핸들러는 얇다(`CLAUDE.md` 경계 셋).
- **어댑터 밖으로 CLI 방언이 새면 안 된다.** `RunManager`·UI는 agent 종류를 모른다(전체
  설계 §329). claude의 `cache_creation_input_tokens`와 opencode의 `tokens.cache.write`가
  UI까지 각자 올라오면 그 규칙이 깨진다.
- **없는 값을 0으로 채우지 않는다.** OpenCode는 컨텍스트 창을 모르고 claude 이전 버전은
  일부 필드가 없을 수 있다. 모르는 것은 모른다고 보여야 한다 — 0%로 그리면 거짓말이 된다.
- **한 줄이 깨져도 run을 죽이지 않는다**(전체 설계 §11). 사용량 파싱 실패가 실행을
  실패시키면 안 된다.
- 마이그레이션이 필요하면 **컬럼 추가만** 한다. `run` 테이블을 다시 만들면 `DROP TABLE`이
  `run_context_item`의 cascade를 태워 맥락 기록이 전부 지워진다(`CLAUDE.md`).
- `rate_limit_info`는 Claude 구독 상태다 — **개인 계정 정보**이므로 어디까지 화면에 남기고
  로그에 적을지 Design에서 명시적으로 정한다.

## 성공 기준

- claude로 모델 칸을 **비운 채** 한 턴을 돌리면, 그 턴에 실제로 쓰인 모델이 대화에 보인다.
- 한 턴이 끝나면 그 턴의 토큰이 보이고, 대화를 다시 열어도 보인다.
- 긴 대화에서 컨텍스트 사용률이 턴마다 올라가는 것이 보인다. OpenCode처럼 창 크기를 모르는
  경우에는 **비율 대신 토큰 수만** 보이고 거짓 비율이 그려지지 않는다.
- 앱을 껐다 켜도 지난 대화의 값이 그대로다(로그가 아니라 DB에 남는다).
- 실행 자체의 동작은 이전과 같다 — 기존 e2e가 전부 통과한다.
- 사용량 파싱이 실패해도 run은 정상으로 끝난다.

## 결정 (2026-09-21, 사용자)

세 가지를 정했다. 앞의 둘이 범위를 갈랐다.

- **effort는 이번 범위에서 뺀다.** 어느 CLI도 effort를 되돌려 주지 않으므로 "보여준다"는
  "앱이 고르고 넘긴다"를 전제하는데, 그것은 실행 패널·workspace 기본값·저장까지 건드리는
  별개의 기능이다. 관측으로 끝나는 나머지 셋과 성격이 다르다 — 이 작업은 **이미 도착해
  있는데 버리고 있는 값을 화면에 올리는 것**에 집중하고, effort 선택은 필요해지면 별도
  intent로 연다. 위 문제 절의 2번 항목은 그래서 이번 범위 밖이다.
- **"사용량"은 이 대화가 쓴 토큰·비용이다.** Claude 요금제의 5시간·7일 소진율
  (`rate_limit_info`)은 대화가 아니라 앱 전역 상태라 자리가 다르고, 이번에 다루지 않는다.
  개인 구독 정보를 저장·표시하는 판단도 함께 미룬다.
- **자리는 턴 머리의 얇은 한 줄이다.** 접힌 "자세히" 안이 아니라 끝난 턴에서도 늘 보이는
  자리다. 대화 헤더의 누계 줄은 이번에 넣지 않는다 — 턴마다의 조건이 먼저다.

```
┌─ 나 ──────────────────────────────────┐
│ 이 버그 고쳐줘                          │
└───────────────────────────────────────┘
┌─ agent ───────────────────────────────┐
│ opus-5[1m] · 12.4k↑ 1.2k↓ · 4%        │  ← 이 줄
│                                       │
│ 원인은 loadContext의 asset 필터입니다… │
│                                 [자세히]│
└───────────────────────────────────────┘
```

## 미해결 질문

Design에서 정한다. 범위를 바꾸는 것은 없다.

- [ ] 비용을 화면의 어디까지 올릴지. 위 한 줄에는 토큰과 컨텍스트만 두고 비용은 "자세히"
      안에 두는 것이 선택된 모양에 가깝다(고른 미리보기에 돈이 없다). 저장은 한다 —
      값이 공짜로 오고, 나중에 집계하려면 그때는 이미 늦다.
- [ ] 과거 run은 값이 없다. 빈칸으로 둘지, 줄 자체를 그리지 않을지.
- [ ] OpenCode는 모델도 컨텍스트 창도 관측되지 않는다. 한 줄이 어떤 모양으로 줄어드는지.
- [ ] 누적 사용량과 컨텍스트 점유는 **다른 수**다(합 vs 마지막 요청의 프롬프트 크기).
      한 줄에서 둘을 어떻게 구분해 읽히게 할지.
