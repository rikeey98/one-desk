# Intent: repo 아래의 이슈, 대화에 할당하는 이슈

- 작성자: 권용현
- 상태: 보류 (2026-10-02, 사용자)
- 작성일: 2026-10-02

> **보류한 이유.** 같은 날 더 작은 안 — 구조는 그대로 두고 대화에 이슈 칸 하나만 더하는 것 — 으로
> 갔다(`docs/sdlc/conversation-issue/`). 이 안은 마이그레이션·보관함·MCP·훑기·메모 대칭까지 바꾸는데,
> 이 장비의 workspace는 셋 다 repo가 하나뿐이라 "repo 아래 이슈"가 지금은 얻는 것이 거의 없다.
> **다시 꺼낼 신호:** workspace 하나에 repo가 여럿 붙고 repo마다 이슈가 쌓여 "이 이슈는 어느 repo
> 일이지?"가 헷갈리기 시작할 때. 아래 결정들(repo 필수, repo째 보관, 마이그레이션 규칙)은 그때의
> 출발점이다.

## 문제

**"이 이슈를 푸는 대화"가 앱 어디에도 없다.** 2026-10-02 사용자(요약): "하나의 대화에서 하나의
이슈를 해결하려고 그렇게 쓰고 있다." 쓰는 방식은 앱과 잘 맞지만(제목 폴백이 담은 이슈 이름을
고르고, 대화끼리는 병렬로 돈다), 그 약속을 앱이 모른다 — 이슈와 대화를 잇는 것은 "그 턴에
맥락으로 담았다"는 기록뿐이다.

그래서 생기는 틈(같은 날 대화에서 꼽은 것):

1. **이슈에서 그 이슈의 대화로 가는 길이 없다.** 이슈 상세에는 대화 표시가 없고, 도크 목록에서
   제목으로 찾아야 한다.
2. **"담은 적 있다"로 잇는 것은 추론이다.** 이 방식으로 이으려 했더니(앞선 안) 참고로 담은 대화도
   그 이슈의 대화가 됐다.
3. **작업 디렉토리 규칙이 둘이 된다.** 이슈에서 대화를 시작하려면 "이슈의 repo 태그"로 디렉토리를
   잡아야 하는데, v0.19.2가 "새 대화의 디렉토리 = 사이드바에서 고른 repo"로 이미 정했다. 이슈의
   태그는 0개일 수도, 여럿일 수도 있다.
4. **담기 칩은 앱에 하나다.** 대화마다가 아니라 `App`의 `chips` 하나라, "이 대화의 이슈"를 칩으로
   표현하면 대화를 옮길 때 칩이 따라간다.

뿌리는 구조다. **이슈는 workspace에 떠 있고 repo는 태그일 뿐인데(다대다), 대화는 늘 repo 하나에서
돈다.** 둘이 같은 축 위에 있지 않아서 이을 자리가 없다.

## 현황 (읽고 확인한 것)

- **이슈 ↔ repo는 다대다다.** `issue_repo` 연결 테이블(`core/db/schema.ts:76`). 태그가 없으면
  "공통 항목"이고, repo 필터는 "그 repo에 태그된 것 + 공통"이다(`issue.ts:122`, 설계 §9). 훑기의
  repo 축은 태그가 여럿이면 이슈를 여러 그룹에 보인다(`issueGroups.ts:77`). 이슈 패널의 추가 칸은
  repo를 골라 두었으면 그 repo로, 아니면 태그 없이 만든다(`IssuePanel.tsx:128`).
- **메모도 같은 모양이다**(`memo_repo`). CLAUDE.md의 대칭 규칙이 `repoIds`를 "계속 대칭으로 유지하는
  공통 필드"로 적어 두었다.
- **대화는 repo를 id로 모른다.** run에는 작업 디렉토리 경로(`cwd`)만 있다(`schema.ts:108`). repo 탭에서
  경로를 바꾸면 옛 대화와 repo의 연결이 끊긴다. 그리고 **core는 cwd가 등록된 repo인지 검사하지
  않는다** — 실행 패널이 repo만 고르게 해서 사실상 늘 repo일 뿐이다(`execution.ts`의
  `resolveFileMentions`가 "등록된 repo가 아니면"을 따로 다룬다).
- **대화의 저장 속성은 뿌리 행에만 있다** — `title`·`closed_at`(lifecycle). 이어지는 턴에도 칸은 있고
  null일 뿐이라, 저장소의 `assertRoot`가 유일한 방어선이다.
- **상태 편집은 상세에서만 한다**(`2026-08-14-issue-memo-body-design.md:137`). 상세 밖에서 쓰면
  열린 상세의 기대값이 낡아 사용자 자신의 클릭에 충돌 배너가 뜬다.
- **repo 삭제는 지금 진짜 삭제다.** 이슈·메모의 태그가 cascade로 사라지고(이슈는 공통으로 남는다),
  그 repo의 asset 행도 cascade로 지워진다(`schema.ts:192`). 대화는 `cwd` 글자로만 남는다.
- **"끝낸 것을 접어 두는" 모양이 이미 있다** — 도크 목록 아래의 "끝낸 대화" 토글(lifecycle),
  asset 패널의 `사라진 파일 N` 토글(asset-missing).
- **MCP `create_issue`는 `repoIds`를 선택으로 받고, `list_issues`의 `repoId`는 "태그된 것 + 공통"이다.**
- **이 장비의 실제 데이터**(2026-10-02, 읽기 전용으로 셈): workspace 3개에 repo가 하나씩, 이슈 1개
  (태그 없음 — 그 workspace의 repo는 하나), 대화 5개(전부 cwd가 등록 repo와 맞음), 이슈를 담은 대화 0개.
- 마이그레이션은 지금 `0009`까지다.

## 원하는 결과

사용자가 알아야 할 규칙은 셋뿐이다.

1. **이슈는 repo 아래에 있다.** 이슈를 보면 어느 repo의 일인지 하나로 정해져 있다.
2. **대화는 repo에서 돌고, 이슈는 할당해도 되고 안 해도 된다.** 할당하지 않은 대화가 "공통"이다.
   대화 하나에 이슈는 많아야 하나이고, 이슈 하나에는 대화가 여럿일 수 있다.
3. **repo를 지우면 보관함으로 간다.** 그 아래 이슈·대화가 같이 숨고, 되살리면 그대로 돌아온다.

그리고 그 위에서:

- **이슈에서 그 이슈의 대화로 한 번에 간다.** 대화가 없으면 거기서 시작한다 — 디렉토리는 이슈의
  repo이고, 이슈가 할당돼 있고, 제목은 이슈 이름이다. 대화가 하나면 그것을 연다. 여럿일 때만
  목록이 보인다.
- **대화에서 그 이슈로 한 번에 간다.** 대화 헤더에 할당된 이슈가 보이고, 누르면 이슈 상세가 열린다.
  상태는 거기서 바꾼다.
- **컨텍스트가 차면 같은 이슈로 새 대화를 이어 간다.** 이슈 본문에 진행 상황을 정리하고 → 대화를
  끝내고 → 이슈에서 대화를 다시 시작한다. 따로 기능 없이 된다 — 이슈에 대화가 여럿일 수 있어서다.

## 영향 범위

- **사용자**: 이 앱을 쓰는 모든 사람(현재 한 명, 작성자). 이슈를 많이 굴릴수록 크게 체감한다.
- **시스템**:
  - `core/db/schema.ts` + `drizzle/0010` — 이슈의 repo 하나, 대화(뿌리)의 repo와 할당된 이슈,
    repo의 보관 표시. 기존 이슈의 태그를 옮긴다.
  - `core/db/repositories/issue.ts` — 태그 다대다 → repo 하나, 필터에서 "공통"이 사라진다.
  - `core/db/repositories/repo.ts` — 삭제 → 보관·되살리기. 목록이 보관된 것을 어떻게 다룰지.
  - `core/db/repositories/run.ts`·`core/execution.ts` — 할당·검증(같은 repo인가), 뿌리에서만.
  - `core/assets/` — 보관된 repo는 훑지 않는다(지금 삭제가 asset을 지우는 것과 다르게).
  - `core/mcp/tools.ts` — `list_repos`(보관 제외), `create_issue`·`update_issue`·`list_issues`의 repo 인자.
  - IPC + preload + `shared/client.ts` — 할당·보관·되살리기 통로.
  - `renderer/components/IssueDetail.tsx`·`IssuePanel.tsx`·`TriageCard.tsx`·`RepoTags.tsx`,
    `renderer/issueGroups.ts` — repo 태그 칩 → repo 하나, 훑기의 repo 축.
  - `renderer/components/ConversationHeader.tsx`·`Dock.tsx`·`RunPanel.tsx`,
    `renderer/conversation.ts` — 할당된 이슈 표시, 제목 폴백, 이슈에서 대화 시작.
  - `renderer/components/RepoStrip.tsx`·`Sidebar.tsx` — 삭제 → 보관, 보관함 토글.
  - `InboxPanel`의 "관련 이슈 닫기" — 담긴 이슈 대신 할당된 이슈를 볼지.
  - e2e — 이슈를 repo 태그로 만드는 곳, 이슈 상세의 repo 칩을 잡는 곳, repo를 지우는 곳.
- **건드리지 않는 것**: 메모(태그 그대로), 사이드바의 이슈 표시(없음), 어댑터·권한·큐, 대화를 묶는
  규칙(`rootRunId` 승계), 맥락 담기 칩(참고 자료를 담는 용도로 그대로).

## 제약

- `core/`는 `electron`을 모르고, `renderer/`는 `core/`를 모르며, IPC 핸들러는 얇다.
- **`run` 테이블을 다시 만들지 않는다.** `ALTER TABLE ADD COLUMN`만 — `DROP TABLE run`이
  `run_context_item`의 cascade를 태운다. `issue`·`repo`도 같은 원칙으로 컬럼 추가만 한다.
- **대화의 저장 속성은 뿌리에서만 의미가 있다.** 할당된 이슈도 `title`·`closed_at`과 같은 방어를 받는다.
- **상태는 상세에서만 고친다**(본문 설계 §137). 대화 헤더에서는 이슈를 열기만 한다.
- **이슈·메모의 `repoIds` 대칭이 여기서 끝난다.** 훑기 축이 그랬듯 CLAUDE.md에 "어긋난 것을 고치려
  하지 말 것"으로 적는다.
- **보관은 아무것도 지우지 않는다.** 되살리면 이슈·대화·할당이 그대로여야 한다.
- **사용자가 따로 정리할 일을 만들지 않는다.** 마이그레이션은 사람에게 묻지 않고 자동으로 넣는다.
- 짧은 라벨을 새로 붙이면 기존 e2e의 부분 일치가 깨진다 — 새 라벨은 e2e를 먼저 돌려 본다.
  이슈 상세의 상태 select 이름이 이미 `상태`다.

## 성공 기준

- 이슈 상세에서 한 번 눌러 그 이슈의 대화를 열거나, 그 이슈가 할당된 새 대화를 시작한다. 새 대화의
  디렉토리는 이슈의 repo이고 제목은 이슈 이름이다.
- 같은 이슈로 대화를 하나 더 시작할 수 있고, 이슈 상세에서 둘 다 찾아 열 수 있다.
- 대화 헤더에 할당된 이슈가 보이고, 누르면 그 이슈 상세가 열린다.
- 다른 repo의 이슈는 할당할 수 없다 — 화면에도 후보로 나오지 않고, core도 거부한다.
- 새 이슈는 repo 없이 만들어지지 않는다(화면·MCP 모두).
- repo를 지우면 사이드바의 보관함으로 가고 그 이슈·대화가 목록에서 빠진다. 되살리면 전부 그대로
  돌아온다. repo 경로를 바꿔도 대화와 repo·이슈의 연결이 유지된다.
- 메모의 동작은 바뀌지 않는다.
- 기존 DB를 열면 마이그레이션 `0010`이 한 번 돌고, 이 장비의 이슈 1개가 그 workspace의 유일한
  repo로 들어가며, 기존 대화 5개가 각자의 repo를 갖는다.
- `pnpm test` · `pnpm typecheck` · `pnpm lint` · `pnpm test:e2e` 전부 통과.

## 결정 (2026-10-02, 사용자)

- **이슈는 repo 필수.** "공통 이슈"는 없다. **"공통"은 이슈가 할당되지 않은 대화를 부르는 말이다.**
- **repo를 지우면 보관함으로.** 사용자 제안은 "임시로 아카이브 같은 곳에 넣어 두기"였고, 이것을
  **repo째 보관**으로 넓혔다 — 이슈만 따로 보관하면 repo를 잃은 이슈가 생기고, 그것을 어디에 둘지
  규칙이 다시 필요해진다(추정 — 확인 필요).
- **이슈 하나에 대화는 여럿일 수 있다.** 제한은 대화 쪽(이슈 0~1개)에만 둔다. 인수인계·agent 바꾸기·
  다시 시도가 모두 새 대화이고, 막으면 할당을 풀고 다시 거는 단계와 오류가 하나씩 는다. 평소처럼
  대화가 하나뿐이면 화면도 하나만 보인다.
- **메모는 태그 그대로.** 메모는 대화에 할당되지 않고 여러 repo에 걸친 기록일 수 있다.
- **사이드바에 이슈를 표시하지 않는다.** 지금처럼 repo를 고르면 이슈 패널이 거른다.
- **규칙은 적을수록 좋다.** 사용자가 고르게 하지 말고 합리적인 기본값으로 정한다 — 아래 마이그레이션이
  그 예다.

### 마이그레이션 (사용자에게 묻지 않는다)

태그가 있으면 그중 사이드바 순서가 가장 앞선 repo, 없으면 그 workspace의 첫 repo로 넣는다. 틀렸으면
상세에서 옮긴다. repo가 하나도 없는 workspace의 이슈만 갈 곳이 없다 — 첫 repo를 등록할 때 그리로
들어가게 할지 spec에서 정한다.

## 이번 범위에서 뺀 것 (앞선 안에서 걸러짐)

- **대화 헤더에서 이슈 상태 바꾸기.** 본문 설계 §137과 부딪힌다 — 이슈 상세를 열어 둔 채 도크에서
  대화를 보는 것이 바로 이 흐름이라 충돌 배너가 가장 잘 터진다. 헤더는 이슈를 열기만 한다.
- **이슈 본문이 바뀌었다는 `수정됨` 표시.** `updatedAt`은 상태·축·agent의 MCP 편집에도 오르므로
  오탐이 많고, 본문만의 시각을 두려면 컬럼이 하나 더 든다. 당분간 "고쳤으면 다시 담는다".
- **대화를 끝내면 이슈도 자동 완료.** 컨텍스트가 차서 새로 시작하거나 접근을 접을 때도 대화를 끝낸다.

## 미해결 질문 (Design에서 다룬다)

- [ ] **할당이 맥락 담기를 겸하는가?** 할당하면 그다음 턴에 이슈 본문이 실리는가, 아니면 표시뿐인가.
      (추정: 겸한다 — 할당한 다음 턴에 실린다. 첫 턴이면 첫 턴에.)
- [ ] **대화 중간에 할당·변경·해제가 되는가?** (추정: 된다, 한 번에 하나.)
- [ ] **이슈에 대화가 여럿일 때 이슈 상세의 모양.** 상세의 메타 줄은 본문을 밀지 않으려고 한 줄이다
      — 목록을 펼치지 않고 그 줄 안에서 고르게 할지.
- [ ] **repo를 고르지 않은 "전체" 보기에서 이슈를 추가하면?** 추가 칸에 repo 고르기가 붙는가, 아니면
      repo를 먼저 고르게 하는가.
- [ ] **MCP `create_issue`에 repo를 안 주면?** (추정: 그 run의 repo를 쓴다 — 회의 메모를 이슈로 쪼갤 때
      매번 id를 찾게 하지 않으려고.)
- [ ] **보관함에서 영구 삭제를 두는가.** 둔다면 그때는 이슈도 함께 지운다.
- [ ] **보관된 repo의 대화가 돌고 있으면?** 보관을 막을지, 돌게 두고 목록에서만 뺄지. 인박스·배지에는
      남을지.
- [ ] **"다시 실행"(새 대화)은 할당을 따라가는가?**
- [ ] **core가 "대화의 cwd = 등록된 repo"를 강제하는가?** 지금은 화면만 그렇게 한다. 강제하면
      `docs/ideas.md`의 "workspace 공통 대화"와 부딪힌다 — 그 아이디어를 살릴 때 다시 본다.
- [ ] **인박스의 "관련 이슈 닫기"는 담긴 이슈와 할당된 이슈 중 무엇을 보는가.**
