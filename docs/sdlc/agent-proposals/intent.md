# Intent: agent가 알아채 제안하고, 사람은 한 번 누른다 — 대화의 이슈화 · workspace 정리

- 출처: 대화 (2026-10-27) — "나는 그냥 편하게 이슈 새로운 대화로 쓰고 싶은데 그럼 그냥 이슈화가 잘 안됨 그냥 그 대화로
  남는거야. 알아서 자동으로 이게 이슈다 싶으면 이슈화 시켰으면 좋겠어" → 안 1(완전 자동)·안 2(알아채고 한 번 누르기) 중
  "자동으로 알아채고 한번만 누르기 좋은거 같아. 그리고 각 워크 스페이스에서 쌓여있는 이슈와 대화를 정리하는 것도 에이전트로
  만들어 줬으면 좋겠어"
- 작성자: 권용현 (초안: Claude)
- 상태: **승인됨** (2026-10-27, 사용자 "spect 만들어줘 개발") — 첫째 사이클의 spec·plan은 `spec.md`·`plan.md`
- 작성일: 2026-10-27
- 관계: `docs/sdlc/issue-flow/` intent의 (3) "흐릿한 이슈를 agent가 다듬어 제안하고, 사람이 고른다"(둘째 사이클, 아직 spec 없음)를
  **이 intent가 넓혀 가져온다** — 승인되면 issue-flow의 (3)은 이쪽을 가리키게 고친다(아래 "뒤집는 결정"). `docs/sdlc/home-conversation/`의
  범위 밖 "다른 대화를 조종 … issue-flow의 'agent가 정리를 제안한다'와 함께 따로 본다"가 말한 그 자리다.

## 문제

1. **이슈 없이 시작한 대화는 끝까지 이슈가 없다.** 사용자는 이슈를 먼저 적지 않고 새 대화에 바로 일을 쓴다 — 그게 편하다. 그 대화가
   실제로는 "처리해야 할 일"이어도 이슈 패널·홈·리포트의 이슈 칸 어디에도 오르지 않고 "공통" 대화로만 남는다. 나중에 "무엇이
   남았나"를 볼 때 그 일은 보이지 않는다.
2. **쌓인 이슈와 대화를 정리할 손이 없다.** workspace마다 정리 안 된 이슈, 끝났는데 열린 이슈, 끝내지 않고 방치된 대화, 같은 일을
   하는 이슈 둘이 쌓인다. 하나씩 열어 읽고 판단하는 것이 사람에게 가장 귀찮은 일이고, agent가 가장 잘하는 일이다(읽고 요약하기).
   사용자의 앞선 말로는 "이슈만 자꾸 쌓이고 일은 처리가 안 되고 있다"(issue-flow intent).

둘은 같은 모양이다 — **agent가 읽고 판단해 제안하고, 사람이 한 번 눌러 받는다.** 그래서 한 intent로 묶는다.

## 현황 (읽고 확인한 것)

- **대화와 이슈가 이어지는 길은 셋이고 전부 사람이 이슈를 먼저 고른다** — 이슈 상세의 `대화 시작`, 첫 턴에 이슈 칩을 하나만 담은
  자동 할당(`core/execution.ts` 571의 `soleIssueOf`, 이어 가는 턴에는 하지 않는다), 대화 헤더 `⋯`의 할당. 이슈 없이 시작한 대화를
  나중에 다시 보는 곳은 없다.
- **할당은 뿌리 행의 `run.issue_id`**(`core/db/schema.ts` 142)이고, 이어 가는 대화의 할당은 `runs.assignIssue(rootRunId, issueId)`
  (`core/db/repositories/run.ts` 642)다. 사람이 버튼으로 이슈를 만들고 붙이는 재료(`issues.create` + `assignIssue`)는 이미 있다.
- **agent가 결과를 앱에 알리는 규약은 하나다** — 프롬프트 끝의 `NEEDS_ANSWER_GUIDE`(`core/context/assemble.ts` 54)가 "답의 첫 줄에
  `[NEEDS_ANSWER]`"를 시키고, 어댑터의 `stripNeedsAnswer`(`core/runner/adapters/common.ts` 220)가 떼어 `needsAnswer`로 만든다.
  같은 모양의 두 번째 표식을 둘 자리가 있다.
- **MCP의 읽기 도구는 읽기 전용 run에도 선다** — `list_issues`·`get_issue`·`list_memos`·`list_conversations`·`get_conversation` 등.
  쓰기 도구(`create_issue`·`update_issue`·`create_memo`·`update_memo`)는 읽기 전용에서 등록되지 않는다(`core/mcp/tools.ts` 227).
  그래서 **읽기 전용 run은 workspace의 이슈와 대화를 다 읽을 수 있지만 아무것도 바꾸지 못한다** — 제안을 받는 run의 경계가 구조로
  이미 있다.
- **MCP 쓰기는 고치는 즉시 저장된다. "제안"이라는 중간 상태가 없다**(issue-flow intent 현황). 제안을 담아 둘 저장소도 없다.
- 홈의 할 일은 넷(답변 필요 · 실패·중단 · 정리 안 됨 · 오래 안 봄)이고, issue-flow 첫째 사이클이 다섯째("끝났는데 열린 이슈")를
  더하기로 승인돼 있다(아직 구현 전).

## 원하는 결과

**(1) 대화가 "할 일"이면 앱이 알아채고, 한 번 눌러 이슈로 만든다.**
- 이슈가 할당되지 않은 대화에서 agent가 "이건 처리할 일이다"라고 판단하면 이슈 **후보**(제목 · 한두 줄 본문 · 가능하면 repo와 분류 축)를
  낸다. 앱은 그 대화 위에 `이 대화를 이슈로 만들까요? 「<제목>」`을 띄우고 `이슈로 만들기` · `아니요`를 세운다.
- `이슈로 만들기`는 이슈를 만들고 **그 대화에 할당한다** — 한 번에. 할당되면 그 대화는 이슈 상세의 `대화 열기`에도, issue-flow의
  "끝낼 때 묻기"에도 걸린다.
- **이미 비슷한 이슈가 있으면 새로 만들지 않고 그것을 제안한다** — `기존 이슈 「<제목>」에 붙일까요?`. 이슈가 더 쌓이는 것을 막는 쪽이
  기본이다(agent는 읽기 도구로 이 workspace의 이슈를 볼 수 있다).
- **권한과 상관없이 된다.** 쓰기는 사람이 누른 버튼이 하므로 읽기 전용 대화에서도 이슈화할 수 있다.
- 잡담·질문·일회성 확인은 후보를 내지 않는다. `아니요`를 누른 대화에는 다시 묻지 않는다.

**(2) workspace의 이슈와 대화를 agent가 훑어 정리 제안을 내고, 사람이 골라 받는다.**
- workspace 하나를 골라 `정리 제안 받기`를 누르면 읽기 전용 run 하나가 그 workspace의 이슈·대화를 읽고 **제안 목록**을 돌려준다. 예:
  - 흐릿한 이슈의 제목·본문을 다시 쓰기, 분류 축 채우기 (issue-flow (3)의 그것)
  - 같은 일을 하는 이슈 합치기
  - 할 일이 아닌 이슈를 메모로 옮기기
  - 할당된 대화가 다 끝났고 내용상 끝난 이슈를 완료하기
  - 오래 멈춘 대화를 끝내기
  - 이슈 없는 대화를 어떤 이슈에 붙이거나 새 이슈로 만들기 ((1)을 한꺼번에)
- 제안마다 **무엇을 왜** 바꾸는지와 **바꾸기 전·후**가 보이고, 사람이 하나씩(또는 골라서 한꺼번에) `받기` · `버리기`를 누른다.
- **사람이 받기 전에는 아무것도 바뀌지 않는다.** 원문은 지우지 않는다(합치기·메모로 옮기기도 원본을 어떻게 남길지 spec에서 정한다).

## 뒤집는 결정

- **issue-flow intent (3)의 범위** — "훑기에서 정리 안 된 이슈를 agent에게 넘긴다"를 이 intent의 (2)가 넓혀 가져온다: 정리 안 된 이슈만이
  아니라 workspace의 이슈 전부와 대화까지, 훑기 화면만이 아니라 workspace 단위의 버튼으로. issue-flow의 첫째 사이클((1)·(2)·(4))은
  그대로다. **승인되면 issue-flow intent의 (3)과 "진행 방식"의 둘째 사이클을 이 문서를 가리키게 고친다.**
- **"대화 쪽에서 이슈 상태를 쓰지 않는다"(conversation-issue)** — issue-flow가 이미 "사람이 누른 버튼으로는 쓴다"로 좁혔다. 이 intent도
  그 안에 있다: 이슈 상태·할당·대화 끝내기는 전부 사람이 누른 `받기`로만 바뀐다.

## 영향 범위 (추정 — spec에서 확정)

- **프롬프트 조립**(`core/context/assemble.ts`) — 이슈 없는 대화에 붙는 안내 한 겹. 정리 run의 지시.
- **어댑터의 표식 처리**(`core/runner/adapters/common.ts`) — `stripNeedsAnswer`와 같은 자리, 또는 다른 전달 방식(아래 미해결).
- **제안을 담는 곳** — 앱을 다시 켜도 남아야 하면 저장소(마이그레이션)가 필요하다.
- **도크**(이슈화 배너), **이슈 패널 또는 홈**(정리 제안 목록과 받기 화면), **App의 배선**.
- **건드리지 않는 것**: MCP 쓰기 도구의 권한 경계, 이슈·메모·대화의 데이터 모델, 인박스·배지 판정 표(`INBOX_RULES`), 어댑터의 성패 판정.

## 제약

- **agent는 제안만 한다. 바꾸는 것은 늘 사람이 누른 버튼이다.** 제안을 내는 run은 (1)이든 (2)든 데이터를 고치지 못해야 하고, 그것을
  지시문이 아니라 구조로 지킨다 — (2)의 정리 run은 **읽기 전용**이다.
- **이슈를 더 쌓지 않는 쪽이 기본이다.** (1)은 비슷한 기존 이슈를 먼저 찾고, 후보를 내는 문턱은 높게 둔다(애매하면 내지 않는다).
  `아니요`는 기억한다.
- **대화 기록을 지우지 않는다.** 대화를 끝내는 제안은 `closed_at`을 찍는 것이지 지우는 것이 아니다.
- **workspace를 넘지 않는다.** 정리는 workspace 하나 단위다(workspace를 넘는 읽기는 `home-conversation`의 몫이고, 그것은 쓰지 않는다).
- 세 경계(`core/`는 electron 없음 · renderer는 core 없음 · IPC는 얇다), App이 내리는 prop은 필수, 짧은 새 이름은 e2e 부분 일치를 본다
  (`만들기`·`받기`·`버리기`·`정리`는 기존 이름과 부딪힐 수 있다 — spec에서 고른다).
- 정리 run은 사용량이 든다 — 사람이 누를 때만 돈다. 저절로 도는 정리는 없다.

## 범위 밖

- **제안을 자동으로 받는 것**(완전 자동) — 사용자가 안 2를 골랐다.
- 정해진 시각에 저절로 도는 정리.
- workspace를 넘는 정리.
- 이슈·대화를 **지우는** 제안(issue-flow: MCP로 이슈를 지우지 않는다는 사용자 결정과 같은 결).
- 정리 run이 이슈를 직접 처리(코드 수정)하는 것 — issue-flow 범위 밖 "이슈를 자동으로 처리하는 것"과 같다.

## 성공 기준

- 이슈 없이 시작한 새 대화에서 "로그인 버튼이 모바일에서 안 눌려, 고쳐줘"를 보내면 턴이 끝난 뒤 그 대화 위에 이슈화 배너가 서고,
  `이슈로 만들기` 한 번으로 이슈가 생기며 그 대화에 할당된다. 이슈 상세의 `대화 열기`가 그 대화를 연다.
- 같은 workspace에 비슷한 이슈가 이미 있으면 배너가 새 이슈 대신 그 이슈에 붙이기를 제안한다.
- "이 함수 뭐 하는 거야?" 같은 질문 대화에는 배너가 서지 않는다. `아니요`를 누른 대화에는 다시 서지 않는다.
- 읽기 전용 대화에서도 이슈화가 된다.
- workspace에서 `정리 제안 받기`를 누르면 제안 목록이 오고, 받은 것만 바뀌고 버린 것과 손대지 않은 것은 그대로다. 정리 run 자신은
  어떤 이슈·대화도 바꾸지 못한다.
- `pnpm test` · `pnpm typecheck` · `pnpm lint` · `pnpm test:e2e` 전부 통과.

## 진행 방식

intent 하나에 spec → plan → 구현을 **둘로** 돈다.

- **첫째 사이클 — (1) 대화의 이슈화.** 작고, 사용자가 먼저 꺼낸 불편이다. 제안 전달 방식(미해결 첫째)을 여기서 정하고 둘째가 그대로 쓴다.
- **둘째 사이클 — (2) workspace 정리.** 제안의 종류가 많아 크다. issue-flow 첫째 사이클("끝났는데 열린 이슈"·MCP `update_issue` 확장)이
  먼저 들어가 있으면 판정·쓰기 재료를 같이 쓸 수 있다.
