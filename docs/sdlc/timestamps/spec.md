# Spec: 시각으로 정리하기 — "이번 주에 생긴 것·시작한 것·끝낸 것"

- 출처: 사용자 요청(2026-09-29) — "모든 메모·이슈·대화에 시간 정보를 저장할 수 있어? 이번 주에 생긴 이슈, 이번 주에
  한 일 같은 정리를 하고 싶다".
- 작성자: 권용현 (초안: Claude)
- 상태: 승인 (2026-09-29). 처음 승인한 "활동 기록 테이블"안은 사용자가 복잡하다고 보아 **이슈 컬럼 하나**로 줄였다 —
  누가(사람/agent) 손댔나·편집 이력은 이번 범위가 아니다(§4).

## 1. 지금 있는 것

시각은 처음부터 전부 저장된다 — 이슈 `createdAt`·`updatedAt`·`closedAt`·`triagedAt`·`seenAt`, 메모 `createdAt`·`updatedAt`,
턴 `createdAt`·`startedAt`·`endedAt`, 대화 뿌리의 `closedAt`. "이번 주에 생긴 이슈·끝낸 이슈·돌린 대화"는 이것으로 답이
나온다. 빈 곳은 셋이다: 언제 작업을 시작했는지(doing)가 없고, agent가 MCP로 시각을 보지 못하며(요약에 `createdAt`·
`closedAt`이 없고 대화는 조회조차 안 된다), 화면에 시각이 없다.

## 2. 결정

### 이슈의 `startedAt` (마이그레이션 `0009`, 컬럼 하나)

- **FR-1.** `issue.started_at`(nullable). **상태가 `doing`이 아니던 이슈가 `doing`이 되는 순간** 찍는다 — 마지막으로 시작한
  때다. 되돌려도(open·done) 지우지 않는다. `closedAt`처럼 저장소가 상태에서 파생하고 호출자는 넘기지 않는다.
- **FR-2. 상태가 실제로 바뀔 때만 파생 시각을 건드린다.** 지금은 done인 이슈를 done으로 다시 저장해도 `closedAt`이 새로
  찍힌다 — 충돌 배너의 "덮어쓰기"가 상태를 늘 함께 보내고, MCP `update_issue`도 같다. 그러면 "언제 완료했나"가 거짓이
  된다. 이전 상태를 읽어 같으면 `closedAt`·`startedAt`을 그대로 둔다.
- **FR-3. 백필하지 않는다.** 기존의 doing 이슈가 언제 시작됐는지는 어디에도 없다 — 지어내지 않는다(null).

### agent가 정리할 수 있게 (MCP)

- **FR-4. MCP가 내보내는 시각은 전부 시간대가 붙은 ISO 8601이다**(`2026-09-29T14:03:00.000+09:00`) — 목록 요약, `get_*`,
  `create_*`·`update_*`의 응답 모두. 예전에는 epoch ms였는데 모델은 그 수로 요일·"이번 주"를 계산하다 틀린다. 시간대는 앱
  프로세스의 것이다(사용자의 장비).
- **FR-5.** `list_issues` 요약에 `createdAt`·`startedAt`·`closedAt`, `list_memos` 요약에 `createdAt`을 더한다.
- **FR-6.** 두 목록에 `since`·`until`(선택). **그 기간에 무슨 일이 있었던 항목**만 준다 — 이슈는 만듦·시작·완료·수정 중
  하나, 메모는 만듦·수정 중 하나가 기간 안이다. 값은 ISO 날짜(`2026-09-28`, 그 날 0시 — 앱의 시간대) 또는 날짜시각이고
  `until`은 그 시각 **전까지**다. 못 읽는 값은 오류로 알린다.
- **FR-7. 새 도구 `list_conversations({ since?, until? })`** — 읽기 전용에서도 된다. 대화마다 `id`(뿌리)·`title`(붙인 이름,
  없으면 첫 지시의 첫 줄 60자)·`startedAt`·`lastActivityAt`·`status`(대표 턴 — `representativeTurn`, 인박스와 같은 판정)·
  `needsAnswer`·`turns`·`closed`·`firstPrompt`(앞 200자)·`lastAnswer`(대표 턴 답의 앞 300자). 기간은 `[startedAt,
  lastActivityAt]`이 겹치면 든다. 최신 활동순. 지시·답 전체와 맥락은 싣지 않는다(크다).

### 화면

- **FR-8.** 이슈 상세의 id 알약 곁에 `만듦 9월 28일 · 시작 9월 28일 · 완료 9월 29일`(있는 것만), 메모 상세에 `만듦 9월 28일`.
  올해가 아니면 연도를 붙인다. `title`에 각 시각의 날짜·시·분. 수정 시각은 싣지 않는다 — agent 편집과 섞여 뜻이 흐리다.

- **FR-9. 새 도구 `get_conversation({ id })`** (2026-10-01 추가 요청 — "agent가 턴 하나하나의 시각을 받을 수 있게").
  읽기 전용에서도 된다. `id`는 `list_conversations`의 뿌리 id나 그 대화의 아무 턴 id다. 대화의 턴 전부를 **오래된 순**으로,
  턴마다 `requestedAt`(지시를 보낸 때 = `run.created_at`)·`startedAt`(실행 시작)·`endedAt`(끝)과 `waitSeconds`(시작 − 보냄)·
  `durationSeconds`(끝 − 시작, 초·소수 한 자리)·`status`·`needsAnswer`·`agent`·`model`(관측값, 없으면 요청값)·`prompt`(500자)·
  `answer`(1,000자)·`error`(300자). 모르는 값은 null이다 — 시작하지 못하고 취소된 턴은 `startedAt`이 없다. 저장된 것을 읽기만
  한다(새 컬럼 없음 — 세 시각은 원래 run 행에 있었다). 다른 workspace의 대화는 없는 id와 같은 말로 떨군다.

## 3. 우려

1. `startedAt`은 "마지막으로 시작한 때"다 — 여러 번 doing을 오간 이슈의 첫 시작은 남지 않는다.
2. ISO로 바꾼 것은 기존 MCP 응답 모양의 변경이다. 이 앱 밖의 소비자는 없다(agent가 그때그때 읽는다).
3. 앱 밖(터미널 claude)에서 한 일은 없다.

## 4. 이번 범위가 아닌 것

- **활동 기록(누가 언제 무엇을)** — 행위자를 모든 쓰기 경로에 끼워야 하고 자동 저장 묶기가 필요해 무겁다. 필요해지면 그때
  붙인다(기록은 그날부터만 쌓인다).
- "이번 주" 같은 기간 보기 화면 — agent에게 시키는 것이 먼저다.
