# Intent: 슬래시 커맨드

- 작성자: 권용현
- 상태: 승인됨
- 작성일: 2026-09-10

## 문제

**one-desk의 프롬프트 입력창이 터미널 Claude Code의 입력창이 하는 일을 못 한다.** 원작자의
말 그대로 "터미널 claude code 처럼 / 기능으로 여러 옵션을 사용 할수 없는 문제가 있어",
그리고 그 이유는 "터미널과 최대한 비슷한 환경을 사용하고 싶어서"다.

터미널에서는 `/`를 치면 지금 쓸 수 있는 커맨드가 뜨고, 이름 하나로 정해진 작업을 시킨다.
one-desk에서는 같은 글자를 쳐도 **아무 일도 일어나지 않고 그냥 평문으로 나간다.**

### 이것이 문제라는 증거

**앱에 슬래시 커맨드라는 개념 자체가 없다.** `core/`·`renderer/`·`electron/` 전체에 관련
코드가 한 줄도 없다.

**그런데 CLI 쪽은 이미 준비돼 있다.** 헤드리스 실행이 시작할 때 뱉는 `system/init` 이벤트가
`slash_commands` 배열로 쓸 수 있는 커맨드를 통째로 알려준다. 이 장비에서 실측한 결과다.

| 항목 | 실측값 |
|---|---|
| `slash_commands` | **94개** (내장 + 번들 스킬 + 개인 스킬 + 플러그인) |
| `terminal_slash_commands` | 3개 (`doctor`·`color`·`reload-plugins` — 터미널이 필요해 헤드리스에선 무의미) |
| init 도착까지 | 2.25 / 2.67 / 3.02초 (one-desk 저장소에서 3회) |
| init 도착 시점의 모델 호출 | **없음** — `assistant` 이벤트보다 먼저 온다 |

즉 **91개를 쓸 수 있는데 화면에서 하나도 고를 수 없다.**

**왜 쳐도 안 되는지도 확인됐다.** 공식 문서가 "슬래시 커맨드는 메시지 맨 앞에 와야 하며,
프롬프트 중간에 나타나면 인식되지 않는다"고 명시한다. 그런데 `core/context/assemble.ts:84`는
사용자 지시를 `<task>`로 감싸고 그 앞에 `<context>` 블록을 붙인다. 보내는 글의 첫 글자가
항상 `<`이므로 **사용자가 무엇을 쳐도 커맨드로 인식될 수 없다.** 우연한 누락이 아니라
구조적인 것이다.

### 결핍은 슬래시 하나가 아니다

원작자에게 "터미널에는 있는데 one-desk에는 없어 아쉬웠던 것"을 물어 나온 답이다.
두 종류로 갈린다.

| 원하는 것 | 지금 상태 | 근거 |
|---|---|---|
| `/` 커맨드 | **없음** | 관련 코드 0건 |
| `@`로 파일 지정 | **없음** | 왼쪽 패널의 ＋로 이슈·메모·asset만 담긴다. 파일은 담을 수 없다 |
| 이전 프롬프트 불러오기 | **없음** | `RunPanel`이 이전 프롬프트를 기억하지 않는다 |
| 실행 멈추기 | **있는데 안 보인다** | 도크의 "취소" 버튼 (`Dock.tsx:177`) |
| 다시 시작하기 | **있는데 안 보인다** | 인박스의 "다시 실행" 버튼 (`InboxPanel.tsx:74`) |

아래 둘에 대한 원작자의 말은 "취소 버튼과 다시 실행 버튼이 잘 안보였어"다. **기능이 없어서가
아니라 입력창에서 손이 닿지 않아서** 없는 것처럼 느껴진 것이다. 터미널이면 Esc 한 번과 위쪽
화살표로 끝나는 일이 여기서는 도크와 인박스로 흩어져 있다.

**이 문서는 그중 `/` 하나를 다룬다.** 나머지는 같은 뿌리에서 나왔으므로 여기 함께 기록하되
이번 범위에서 뺀다.

## 원하는 결과

실행 패널의 프롬프트에 `/`를 치면 **지금 이 작업 디렉토리에서 쓸 수 있는 커맨드가 설명과
함께 보이고**, 골라서 실행하면 CLI가 그것을 평문이 아니라 진짜 커맨드로 받는다. 터미널에서
하던 것과 같은 손놀림이다.

**커맨드를 쓴다고 one-desk가 주는 것을 잃지 않는다.** 맥락에 담은 이슈·메모는 그대로
agent에게 전달되고, 커맨드로 시작한 실행도 답이 막히면 인박스의 "답변 필요"에 뜬다. 터미널로
돌아갈 이유가 하나 줄어드는 것이 목적이지, 터미널의 반쪽을 흉내 내는 것이 목적이 아니다.

**목록이 최신인지 사람이 신경 쓰지 않는다.** 작업 디렉토리를 고르면 그 디렉토리 기준의
목록이 준비돼 있다. repo마다 쓸 수 있는 커맨드가 다르기 때문이다.

**목록을 아는 데 돈이 들지 않는다.** 커맨드 목록을 보려고 실행 요금이 나가서는 안 된다.

## 영향 범위

- **사용자**: one-desk 사용자 전부. 특히 **터미널 Claude Code를 이미 쓰던 사람**일수록
  체감이 크다 — 그 사람은 이미 쓰던 커맨드가 있고, one-desk에서 그것을 못 쓴다는 사실을
  매번 다시 만난다. 배포 대상이 Windows이므로 그 환경에서도 동작해야 한다.
- **시스템**:
  - **프롬프트 조립(`core/context/assemble.ts`)** — 지금 구조가 이 기능을 구조적으로
    막고 있는 자리다. 손대지 않고는 불가능하다.
  - **claude 어댑터(`core/runner/adapters/claudeCode.ts`)** — 커맨드 조립이 바뀐다.
  - **`RunPanel`** — `/` 피커가 붙을 자리. 지금 ⌘↵만 가로채는 키 처리와 겹친다.
  - **새 core 모듈** — 커맨드 목록을 얻고 설명을 채우는 일을 맡을 자리. 지금 없다.
  - **asset 스캔(`core/assets/`)** — `.claude/commands/`를 훑지 않는다. 설명을 채우려면
    이 스캔기와 frontmatter 파서를 재사용하게 된다.
  - **IPC / preload / `shared/client.ts`** — 목록을 렌더러로 내려보낼 통로가 새로 필요하다.
  - **`RunManager`·`RunQueue`** — 목록을 얻는 일이 동시 실행 슬롯이나 대화 직렬화를
    건드리면 안 된다.

## 제약

- **범위 밖: OpenCode.** claude만 다룬다. OpenCode가 같은 계약(`slash_commands` 같은 것)을
  주는지 확인되지 않았고, 5단계는 하위 시스템마다 사이클을 따로 도는 것이 이 저장소의 방식이다.
- **범위 밖: `@`로 파일 지정.** 같은 뿌리의 결핍이지만 별도 사이클이다.
- **범위 밖: 이전 프롬프트 불러오기.** 마찬가지다.
- **범위 밖: 취소·다시 실행 버튼의 위치.** 기능은 이미 있고 발견성 문제다. 새 기능을 만드는
  이번 작업과 성격이 다르다.
- **범위 밖: 실행 삭제.** 원작자의 판단이다 — "삭제는 없어도됨".
- **범위 밖: 앱에서 커맨드를 직접 만들고 고치는 기능.** 디스크의 것을 쓰기만 한다.
- **슬래시를 쓰지 않는 기존 실행의 동작이 바뀌면 안 된다.** 지금 잘 도는 경로를 건드려
  품질이 미묘하게 달라지는 것은 되돌리기 어렵고 어떤 테스트도 잡지 못한다.
- **`core/`는 `electron`을 import하지 않는다.** 경로가 필요하면 인자로 받는다.
- **`renderer/`는 `core/`를 import하지 않는다.** `window.oneDesk` 참조는 `main.tsx` 한 곳뿐이다.
- **IPC 핸들러는 얇다.** core 메서드 호출만 한다.
- **새 런타임 의존성을 더하지 않는다.**
- **헤드리스에는 `ask`가 없다.** 사람이 응답할 수 없으므로 모든 권한은 `allow` 아니면
  `deny`로만 떨어져야 한다. 커맨드가 이 규칙을 우회하게 해서는 안 된다.
- **Windows를 고려한다.** 인자 길이 제한(32767자)과 경로 규칙이 macOS와 다르다. 맥락은
  수십 KB가 될 수 있다.

## 성공 기준

1. 실행 패널의 프롬프트에 `/`를 치면 **그 작업 디렉토리에서 쓸 수 있는 커맨드 목록이 뜬다.**
   이 장비·이 저장소 기준 **91개**(실측 94개에서 터미널 전용 3개를 뺀 수)다. 지금은 0개다.
2. 목록의 각 항목에 **이름과 설명이 함께 보인다.** 설명을 찾을 수 없는 내장 커맨드는 이름만
   보이되 목록에서 빠지지는 않는다.
3. 고른 커맨드로 실행하면 **CLI가 그것을 커맨드로 인식한다** — 로그에 커맨드가 확장된 결과가
   나타나고, `/` 로 시작하는 글자 그대로 모델에게 전달되지 않는다.
4. **커맨드를 쓰면서 맥락에 담은 이슈·메모가 agent에게 전달된다.** 커맨드를 쓰면 맥락이
   사라지는 일이 없다.
5. **커맨드로 시작한 실행도 `[NEEDS_ANSWER]`로 멈추면 인박스의 "답변 필요"에 뜬다.**
6. **목록을 얻는 데 API 요금이 들지 않는다.** 목록을 새로 고쳐도 사용량이 늘지 않는다.
7. **슬래시를 쓰지 않는 실행은 지금과 글자 하나까지 같은 것을 CLI에 보낸다.**
8. **작업 디렉토리를 바꾸면 그 디렉토리 기준의 목록으로 갱신된다.** A repo에만 있는 커맨드가
   B repo를 골랐을 때 목록에 남아 있지 않다.

## 미해결 질문

- [ ] 대화를 이어가는 실행(`--resume`)에서도 맥락을 커맨드와 분리해 전달할 수 있는가.
      **실측하지 않았다.** 되지 않으면 대화 중에는 커맨드를 못 쓰거나 다른 방법이 필요하다.
- [ ] `[NEEDS_ANSWER]` 규약을 사용자 프롬프트가 아닌 자리로 옮겨도 모델이 지키는가.
      인박스의 "답변 필요"가 여기 달려 있다(성공 기준 5).
- [ ] 목록을 언제 갱신하는가. 작업 디렉토리를 바꿀 때만인가, 실행이 끝난 뒤에도인가.
      asset 스캔은 실행이 끝나면 다시 훑는다 — 그 규칙을 따를 것인지 정해야 한다.
- [ ] 목록이 준비되기까지 2~3초가 걸린다. 그 사이에 `/`를 치면 무엇을 보여주는가.
- [ ] 커맨드를 여러 개 이어 쓰는 것(`/a /b 인자`)을 지원하는가. CLI는 최대 6개까지 받는다.
      피커의 여는 조건에 따라 저절로 따라올 수 있는데, 의도한 동작으로 둘 것인지 정해야 한다.
- [ ] 커맨드에 딸린 설명을 어디서 읽는가. `.claude/commands/`·`.claude/skills/`·플러그인
      경로가 후보이고, 내장 커맨드는 어디에도 설명이 없다.
- [ ] 목록을 저장하는가 저장하지 않는가. 저장하면 DB 구조를 바꿔야 하고(마이그레이션),
      저장하지 않으면 앱을 켤 때마다 다시 얻어야 한다.
