- 출처: `intent.md` (2026-09-14 승인)
- 작성자: 권용현

## 요구사항

### 기능 요구사항

- **FR-1.** 실행 패널의 프롬프트 입력에서 `/`가 **줄머리 또는 공백 바로 뒤**에 입력되면
  커맨드 피커가 열린다. 이 조건은 CLI가 커맨드를 인식하는 조건과 같다.
- **FR-2.** 피커는 **지금 선택된 작업 디렉토리 기준**의 커맨드를 보여준다. init이 알려준
  `terminal_slash_commands`는 제외한다 — 제외할 이름을 코드에 박지 않는다.
- **FR-3.** 각 항목은 이름과 설명을 함께 보여준다. 설명을 찾지 못한 커맨드는 **이름만
  보여주되 목록에서 빠지지 않는다.**
- **FR-4.** `/` 뒤에 입력한 글자로 이름과 설명을 부분 일치 필터한다.
- **FR-5.** ↑↓로 이동, Enter 또는 Tab으로 삽입, Esc로 닫는다. **피커가 열려 있는 동안
  Enter는 실행을 일으키지 않는다.**
- **FR-6.** 목록은 작업 디렉토리가 정해질 때 백그라운드로 준비된다. 준비 전에 피커가 열리면
  "불러오는 중"을 보여주고, 준비되면 그 자리에서 목록으로 바뀐다.
- **FR-7.** 사용자 프롬프트가 `/`로 시작하면 **조립된 프롬프트의 첫 글자가 `/`**가 되도록
  순서를 바꾼다. 맥락(`<context>`)과 `[NEEDS_ANSWER]` 안내문은 그 뒤에 온다.
- **FR-8.** 사용자 프롬프트가 `/`로 시작하지 않으면 조립 결과가 **지금과 글자 하나까지
  같다.**
- **FR-9.** 인자 placeholder(`$ARGUMENTS`·`$0`·`$1`·`${CLAUDE_*}`)를 쓰는 커맨드를 고르면
  "이 커맨드는 뒤에 오는 글을 인자로 씁니다 — 담은 맥락이 인자로 전달됩니다"를 화면에
  보여준다. 실행을 막지는 않는다.
- **FR-10.** 목록을 얻는 동작은 **모델 호출을 일으키지 않는다.** `system/init`을 받는 즉시
  프로세스를 종료한다.
- **FR-11.** 목록을 얻는 동작은 `RunManager`의 동시 실행 슬롯과 `RunQueue`를 쓰지 않고,
  `run` 테이블에 행을 만들지 않으며, `onRunEvent`/`onRunUpdate`로 아무것도 내보내지 않는다.
- **FR-12.** 작업 디렉토리를 바꾸면 그 디렉토리 기준의 목록으로 바뀐다. 이전 디렉토리에만
  있던 커맨드가 남아 있지 않다.
- **FR-13.** 목록을 사용자가 직접 다시 얻을 수 있다(새로고침). 실행이 끝났다고 자동으로
  다시 얻지는 않는다.

### 비기능 요구사항

- **NFR-1.** 목록 준비는 정상 환경에서 **10초 이내**에 끝난다. 이 장비 실측은 2.25 ~ 5.66초로
  편차가 크며, 편차의 원인은 사용자의 `SessionStart` 훅이다.
- **NFR-2.** 목록을 얻지 못해도 **앱이 죽지 않는다.** 피커는 빈 목록과 사유를 보여주고,
  프롬프트 입력과 실행은 평소대로 동작한다.
- **NFR-3.** 목록을 얻는 프로세스는 `--tools ""`로 도구 없이, MCP 설정 없이 띄운다.
  파일을 쓰거나 네트워크를 쓰는 일이 없어야 한다.
- **NFR-4.** `core/`는 `electron`을 import하지 않는다. 작업 디렉토리와 홈 디렉토리는 인자로
  받는다.
- **NFR-5.** `renderer/`는 `core/`를 import하지 않는다. `window.oneDesk` 참조는
  `renderer/main.tsx` 한 곳뿐이다. IPC 핸들러는 core 호출만 한다.
- **NFR-6.** 새 런타임 의존성을 더하지 않는다. **DB 마이그레이션이 없다.**
- **NFR-7.** 커맨드 이름과 설명은 **신뢰할 수 없는 입력**이다(외부 repo의 파일에서 온다).
  화면에는 평문으로 그리고, 프롬프트에 실을 때는 이스케이프한다.

## 범위 밖

- **OpenCode.** claude-code 전용이다. agent가 `opencode`면 피커를 열지 않는다.
- **`@`로 파일 지정**, **이전 프롬프트 불러오기**, **취소·다시 실행 버튼의 위치 개선**.
  같은 뿌리의 결핍이지만 각각 별도 사이클이다(`intent.md`의 결핍 표).
- **실행 삭제.** 원작자 판단으로 제외했다.
- **앱에서 커맨드를 만들고 고치는 기능.** 디스크의 것을 읽기만 한다.
- **커맨드 스택 전용 UI.** 여러 개를 이어 쓰는 것(`/a /b 인자`)은 피커의 여는 조건 때문에
  저절로 동작하지만, 그것을 돕는 화면은 만들지 않는다.
- **목록을 DB에 저장하는 것.**
- **`--append-system-prompt` 계열 플래그.** 아래 설계의 근거로 검토했으나 채택하지 않았다.

## 설계

### 개요

**핵심 결정은 "맥락을 커맨드 뒤에 붙인다"이다.** 브레인스토밍에서는 맥락을 시스템 프롬프트로
분리하는 쪽(`--append-system-prompt-file`)을 골랐으나, 실측이 그것을 뒤집었다.

| 실측 | 새 세션 | `--resume` |
|---|---|---|
| 슬래시 커맨드 확장 | 된다 | **된다** |
| `--append-system-prompt-file` 전달 | 된다 | **안 된다** |
| `--append-system-prompt`(문자열) 전달 | 된다 (통제군) | **안 된다** |

one-desk의 실행은 전부 대화이므로, 시스템 프롬프트로 분리하면 **두 번째 턴부터 맥락이 조용히
사라진다.** 그래서 채택하지 않았다.

대신 프롬프트 하나에 순서만 바꿔 담는다.

```
/code-review 사용자가 덧붙인 글

<context>
  <issues> ... </issues>
</context>

사용자의 결정이 필요해 작업을 진행할 수 없으면 ... [NEEDS_ANSWER] ...
```

CLI는 커맨드 뒤의 모든 글을 인자로 본다. 인자 placeholder가 없는 커맨드는 그 글을 본문 끝에
`ARGUMENTS: ...`로 붙이므로 맥락과 안내문이 온전히 전달된다. 이 장비의 커맨드·스킬 파일
41개 중 placeholder를 쓰는 것은 **2개(약 5%)**이고, 그 2개는 맥락이 인자 자리에 치환된다 —
FR-9의 경고가 그 자리다.

`[NEEDS_ANSWER]` 안내문이 인자 자리에서도 지켜지는지 실측했다. 지켜진다(첫 줄 단독 출력
확인). **다만 1회 관측이므로 e2e로 고정한다.**

**이 결정의 큰 이점: 어댑터가 바뀌지 않는다.** 새 CLI 플래그가 없으므로
`core/runner/adapters/claudeCode.ts`와 `RunSpec`은 그대로다. 변경은 프롬프트 조립기와
새 모듈, 그리고 화면에 갇힌다.

**목록은 CLI에게 묻는다.** 작업 디렉토리에서 claude를 띄워 `system/init`만 받고 죽인다.
init은 모델 호출보다 먼저 오므로 **요금이 들지 않는다**(실측: init 도착 시점까지 `assistant`
이벤트 없음). 파일을 직접 훑는 방법은 내장 커맨드를 못 찾고 플러그인의 활성 여부를 알 수
없어 택하지 않았다.

**`--bare`는 쓰지 않는다.** 훅을 건너뛰어 0.41초로 끝나지만 커맨드가 95개에서 49개로
줄어든다. 사라지는 46개가 개인 스킬과 플러그인 스킬 — 이 기능이 쓰이게 하려던 바로 그것들이다.

**설명은 디스크에서 채운다.** init은 이름만 주므로, 아래 자리를 훑어 이름 → {설명, 인자
placeholder 사용 여부} 지도를 만든다. `core/assets/frontmatter.ts`의 파서를 재사용한다.

| 자리 | 이름 규칙 |
|---|---|
| `<cwd>/.claude/commands/*.md` | 파일명 |
| `<homeDir>/.claude/commands/*.md` | 파일명 |
| `<cwd>/.claude/skills/*/SKILL.md` | frontmatter `name` 없으면 디렉토리명 |
| `<homeDir>/.claude/skills/*/SKILL.md` | 같음 |
| init의 `plugins[].path` 아래 `commands/*.md`·`skills/*/SKILL.md` | `<플러그인>:<이름>` |

지도에 없는 이름(내장 커맨드)은 설명 없이 목록에 남는다(FR-3).

### 데이터 모델

**스키마 변경이 없다. 마이그레이션이 없다.**

목록은 `core/commands/`의 **메모리 캐시**에 작업 디렉토리 경로를 키로 담는다. 프로세스가
살아 있는 동안만 유지된다. 저장하지 않는 이유:

- 커맨드는 "발견된 사실"이지 기록해야 할 데이터가 아니다. `asset`이 `last_seen_at`으로
  과거 run의 기록을 지키는 것과 달리, 커맨드는 이름이 그 run의 `user_prompt`에 이미 남는다.
- 마이그레이션은 기존 사용자 데이터를 건드리는 작업이다. 몇 초면 다시 얻을 수 있는 것을
  위해 그 위험을 질 이유가 없다.

캐시 항목:

```ts
interface CommandInfo {
  name: string            // '/' 없이. 'code-review', 'superpowers:brainstorming'
  description: string | null
  usesArguments: boolean  // 파일을 못 찾으면 false (모른다는 뜻이 아니라 경고하지 않는다는 뜻)
}
```

### 인터페이스

**core → 새 모듈 `core/commands/`**

- `probe.ts` — 작업 디렉토리에서 CLI를 띄워 `system/init`의 `slash_commands`,
  `terminal_slash_commands`, `plugins`를 받고 **즉시 종료**한다. 실행 파일 탐색은
  `core/runner/executable.ts`를 재사용한다(Windows 포함).
- `describe.ts` — 위 표의 자리를 훑어 이름 → 설명·인자 사용 여부 지도를 만든다.
  `parseFrontmatter`를 재사용한다. **어떤 경우에도 던지지 않는다**(`scanDir`과 같은 규칙).
- `service.ts` — 둘을 합쳐 캐시한다.

**core 표면 (`core/index.ts`)**

```ts
commands: {
  list(cwd: string): Promise<CommandInfo[]>   // 캐시에 있으면 즉시, 없으면 얻어서
  refresh(cwd: string): Promise<CommandInfo[]> // 캐시를 버리고 다시
}
```

`createCore`는 이미 `homeDir`를 받는다 — `describe.ts`가 그 값을 쓴다.
`os.homedir()`를 `core/`에서 부르지 않는다.

**IPC** — `shared/channels.ts`에 `commandsList`·`commandsRefresh`를 더하고,
`electron/ipc/commands.ts`가 core 호출만 한다.

**renderer** — `useCommands(cwd)` 훅이 `useAssets`의 모양을 따른다(목록·오류·refresh).
`App.tsx`가 그 결과를 `Dock` → `ConversationPanel` → `RunPanel`로 내려보낸다.
**이 prop 배선 한 줄도 테스트 대상이다.**

**화면 흐름**

1. 작업 디렉토리가 정해진다 → `useCommands`가 배경에서 목록을 얻는다
2. 사용자가 `/`를 친다 → 피커가 열린다 (목록이 아직이면 "불러오는 중")
3. 글자를 더 친다 → 필터
4. Enter/Tab → `/이름 `이 삽입되고 피커가 닫힌다. 인자 커맨드면 경고가 뜬다
5. ⌘↵ → 조립기가 순서를 바꿔 CLI로 보낸다

### 예외 처리

| 상황 | 동작 |
|---|---|
| 실행 파일을 못 찾음 | 피커에 "claude 실행 파일을 찾을 수 없습니다". 실행 자체는 기존 preflight가 따로 막는다 |
| CLI가 init 없이 죽음 | 빈 목록 + 사유. `onError`로 흘려보낸다. 앱은 정상 |
| 목록 얻기가 10초를 넘김 | 프로세스를 죽이고 빈 목록 + "시간이 초과됐습니다". 새로고침으로 다시 시도 |
| 설명 파일을 못 읽음 | 그 커맨드는 설명 없이 목록에 남는다 (FR-3) |
| `init` JSON이 예상과 다름 | 없는 필드는 빈 배열로 본다. 던지지 않는다 |
| 사용자가 목록에 없는 `/이름`을 직접 침 | 막지 않는다. CLI가 판단한다 |

**판정과 전송이 어긋나지 않게 한다.** `userPrompt.trimStart().startsWith('/')`로 판정하고
원본을 그대로 보내면, 앞에 공백이 있을 때 우리는 슬래시로 보고 CLI는 아니라고 본다 — 맥락은
뒤로 밀렸는데 커맨드는 확장되지 않는, 조용히 반쯤 깨진 상태가 된다. **슬래시로 판정되면
`trimStart()`한 문자열을 보낸다.**

      — 필요한 판단이었던 것: **원작자가 이 부작용을 수용하는지.**
      **결정 (2026-09-14, 권용현): 수용한다. 작업 디렉토리당 1회로 간다.** 즉 FR-13이
      그대로 이 항목의 답이다 — repo를 고를 때 한 번 얻고, 실행이 끝나도 자동으로 다시 얻지
      않으며, 다시 얻는 것은 사용자가 새로고침을 눌렀을 때뿐이다. 사용자가 `/`를 쓰기 위해
      먼저 눌러야 하는 버튼은 없다.

## intent 미해결 질문에 대한 답

| 질문 | 결정 | 근거 |
| --- | --- | --- |
| `--resume`에서도 맥락을 커맨드와 분리해 전달할 수 있는가 | **불가능. 분리하지 않는다** | 실측: 새 세션은 되고 `--resume`은 안 된다(통제군 포함). 맥락을 커맨드 뒤에 붙인다 |
| `[NEEDS_ANSWER]`를 다른 자리로 옮겨도 모델이 지키는가 | **지킨다** | 인자 자리에서 첫 줄 단독 출력 확인. 1회 관측이므로 e2e로 고정한다 |
| 목록을 언제 갱신하는가 | **작업 디렉토리당 1회 + 수동 새로고침** | 자동 재탐색은 훅을 매번 실행시킨다. asset 스캔의 "run 후 재스캔" 규칙을 따르지 않는 유일한 이유다 |
| 준비되기 전에 `/`를 치면 | **피커가 열리고 "불러오는 중"을 보여준다** | 입력을 막으면 사용자가 왜 안 되는지 모른다 |
| 커맨드를 여러 개 이어 쓰는 것을 지원하는가 | **막지 않는다. 전용 UI는 없다** | 피커의 여는 조건이 CLI 인식 규칙과 같아 저절로 따라온다. 억지로 막는 코드가 오히려 위험 |
| 설명을 어디서 읽는가 | **위 표의 5개 자리** | init이 플러그인 경로를 알려주므로 플러그인 것도 읽을 수 있다 |
| 목록을 저장하는가 | **저장하지 않는다** | 마이그레이션 없음. 몇 초면 다시 얻는다 |

## 수용 기준

| 확인 | 대응 | 방법 |
| --- | --- | --- |
| `/`를 치면 피커가 열리고, 줄 중간의 `/`에서는 열리지 않는다 | FR-1 | 렌더러 단위 테스트 |
| 목록에 `terminal_slash_commands`의 3개가 없다 | FR-2 | core 단위 테스트 (가짜 init) |

| 필터·키 조작이 동작하고 **피커가 열린 동안 Enter가 실행을 일으키지 않는다** | FR-4·FR-5 | 렌더러 단위 테스트 |
| 준비 전에는 "불러오는 중"이 보인다 | FR-6 | 렌더러 단위 테스트 |
| 슬래시면 조립 결과의 첫 글자가 `/`다. **앞에 공백이 있어도 그렇다** | FR-7 | `assemble` 단위 테스트 |

| 인자 커맨드를 고르면 경고가 보인다 | FR-9 | 렌더러 단위 테스트 |
| **init 수신 후 프로세스가 죽는다** | FR-10 | 가짜 CLI 픽스처. init 뒤에도 이벤트를 계속 뱉게 해두고, 그것이 수신되면 실패 |
| 탐색이 슬롯·큐·`run` 테이블을 건드리지 않는다 | FR-11 | core 단위 테스트. 탐색 전후 `queue.snapshot()`과 `runs.list()`가 같다 |
| 작업 디렉토리를 바꾸면 목록이 바뀐다 | FR-12 | 렌더러 단위 테스트 |
| 실행이 끝나도 자동 재탐색하지 않는다 | FR-13 | core 단위 테스트. run 완료 후 탐색 호출 횟수가 늘지 않는다 |
| 탐색 실패로 앱이 죽지 않는다 | NFR-2 | core 단위 테스트 (실행 파일 없음 / 잘못된 출력 / 타임아웃) |
| 경계 세 가지 | NFR-4·5 | `grep -rn "from 'electron'" core/`, `grep -rn "window.oneDesk" renderer/ \| grep -v main.tsx` 둘 다 출력 없음 |
| 마이그레이션이 늘지 않았다 | NFR-6 | `drizzle/` 파일 수 불변 |
