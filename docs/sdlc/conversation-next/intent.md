# Intent: 설계 결정을 바꿔야 가능한 대화 기능들 (결정 대기 목록)

- 작성자: 권용현 (Claude가 초안)
- 상태: **초안 — 항목마다 사용자 결정이 필요하다.** 승인된 항목만 자기 폴더
  (`docs/sdlc/<기능>/`)로 떼어 intent → spec → plan을 돈다.
- 작성일: 2026-09-27
- 근거: 2026-09-27 OpenCode Desktop 2.0.18 비교 조사와 반박 검증(claude 2.1.280·opencode
  1.18.30 바이너리·소스·공식 문서, 모델 호출 없음). 같은 조사에서 나온 결함·화면·데이터 작업은
  `conversation-fixes`·`conversation-timeline`·`conversation-events`가 맡는다.

## 왜 한 문서로 묶었나

아래 항목은 모두 **지금 설계가 명시적으로 막아 둔 것**을 푼다 — "생성하는 권한 설정에 `ask`를
절대 넣지 않는다"(CLAUDE.md), "대화당 예약은 하나"(대화 설계 2026-08-18 §3-2), "fork·예약 여러
개·실행 중 끼어들기 제외"(같은 설계 §7), "`stdin.end()` 필수·턴마다 프로세스 하나"(실행 구조).
그래서 사용자 추천 순서("C는 항목마다 따로")대로 **구현하지 않고 결정 재료만** 모았다.
항목은 값 대비 비용 순이다.

## 1. 권한 요청 카드 (한 번 허용 / 항상 허용 / 거부)

- **무엇**: 도구가 권한에 걸리면 턴이 멈추고 대화록(또는 입력부 자리)에 카드가 뜬다. OpenCode의
  권한 도크와 같다.
- **가능한 길 (검증됨)**: claude의 숨은 플래그 `--permission-prompt-tool <mcp도구>`(print 전용,
  공식 CLI reference에 있음). 도구는 text 블록 하나에 `{"behavior":"allow","updatedInput":…}`
  또는 `{"behavior":"deny","message":…}` JSON을 돌려준다. **one-desk MCP 서버에 승인 도구를
  두면 지금의 턴 구조 그대로 붙는다.** 그 도구는 모델의 도구 목록에서 빠진다(모델이 직접 못 부름).
  대안으로 `--input-format stream-json` + `--permission-prompt-tool stdio`(control_request
  `can_use_tool`)가 있지만 장기 프로세스(6번)가 전제다.
- **부딪히는 것**: CLAUDE.md·`permission.ts`의 절대 규칙("ask 금지"). 새 권한 단계("물어보기")가
  생긴다.
- **함정 (코드로 확인)**: MCP 브리지가 요청을 직렬화한다(`bridge.mjs`의 `chain`) — 승인을 기다리는
  동안 같은 run의 다른 MCP 호출이 줄을 선다. 브리지가 fetch를 abort하지 않아 취소가 서버에 닿지
  않는다. 기다리는 동안 실행 슬롯을 쥔다. MCP 호출 타임아웃.
- **OpenCode**: `run`에서는 불가(ask를 자동 거부한다). `serve`로 가야 한다(7번).
- **추천**: **가장 먼저 할 가치가 있다.** 대신 첫 spec에서 브리지의 직렬화·취소 전파를 함께 고친다.

## 2. 구조화된 질문 카드 (지금의 `[NEEDS_ANSWER]` 규약을 대신)

- **무엇**: agent가 선택지가 있는 질문을 던지면 입력부 자리에 선택지 카드가 뜬다(OpenCode 질문 도크).
- **가능한 길**: one-desk MCP에 질문 도구(`ask_user`)를 두고, 답이 올 때까지 호출을 붙잡는다 —
  1번과 같은 기다리는 MCP 호출 문제를 공유한다. claude 바이너리에는 host가 AskUserQuestion에
  답하는 경로 흔적이 있으나 헤드리스 동작은 미확인.
- **부딪히는 것**: 없음(새 도구 추가). 다만 "턴이 끝나야 답한다"는 지금 모델이 "턴 안에서 답한다"로
  바뀐다.
- **추천**: 1번과 같은 spec에서 기다리는 MCP 호출 기반을 한 번에 만든다.

## 3. 여러 개 예약 (대기열 편집·순서 변경·회수)

- **무엇**: 실행 중에 후속 지시를 여러 개 쌓고, 칩에서 편집·순서 바꾸기·입력창으로 되돌리기·지금
  보내기를 한다(OpenCode 대기열 패널).
- **가능한 길**: 예약은 이미 DB의 진짜 pending run이고 `RunQueue`가 `groupKey`로 직렬화한다 —
  **구조 변경이 작다.** 편집은 pending run의 지시를 바꾸는 저장소 메서드가, 순서 변경은 정렬 키가
  필요하다.
- **부딪히는 것**: 설계 §3-2 "대화당 예약은 하나". 예약마다 부모(`parentRunId`)가 무엇인지 다시
  정해야 한다(지금도 예약의 부모는 "세션을 가진 최신 run"이라 선형이 아니다 — 조사에서 지적).
- **추천**: 2순위. `conversation-timeline`의 예약 칩(D3)이 그대로 목록이 된다.

## 4. 분기 (이 지점에서 새 대화)

- **무엇**: 지난 지시 하나를 골라 그 앞까지의 이력을 가진 새 대화를 연다(OpenCode `/fork`).
- **가능한 길 (검증됨)**: claude `--resume <id> --fork-session`(공개 플래그)은 새 세션 id로
  이어간다. **특정 지점까지만**은 숨은 플래그 `--resume-session-at <체인 항목 uuid>`(print 전용)
  — `conversation-events` E7이 저장하는 메시지 uuid가 재료다. opencode는 `run --fork`(전체 이력).
- **부딪히는 것**: 설계 §7 "fork 제외". 새 대화의 뿌리와 원래 대화의 관계를 저장할지(컬럼 → 마이그레이션).
- **추천**: 3순위. 숨은 플래그 의존이라 버전 감지와 함께.

## 5. 되돌리기 (지시 고쳐 다시 보내기, 파일 되감기)

- **무엇**: 지난 지시를 되돌려 입력창에 다시 채우고, 그 뒤의 턴과 (선택) 파일 변경을 되감는다
  (OpenCode "메시지 되돌리기"·`/undo`·`/redo`).
- **가능한 길**: 대화는 4번의 `--resume-session-at`으로. 파일은 `--rewind-files <user-message-uuid>`
  (숨은 플래그, `--resume` 필요) — **파일 체크포인트가 켜져 있어야 한다**: 원래 턴을 돌릴 때와
  되감을 때 모두 `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true`가 필요하고, Write/Edit/
  NotebookEdit만 추적한다(Bash·하위 에이전트의 편집은 되감지 않는다). 체크포인트 uuid는
  `--replay-user-messages`(stream-json 입출력 전제)로 얻는다. opencode는 `serve`의 revert API.
- **부딪히는 것**: "기록을 지우지 않는다"(전체 설계 §232) — 되돌린 턴을 숨길 뿐 지우지 않는 설계가
  필요하다. 남은 5단계 과제 **diff 뷰어·스냅샷과 같은 기반**이다.
- **추천**: diff 뷰어와 한 spec으로.

## 6. 장기 프로세스 — 방향 지시(steer)·죽이지 않는 중단·토큰 스트리밍·이미지 첨부

- **무엇**: 실행 중인 턴에 지시를 끼워 넣고(OpenCode 기본 "방향 지시"), 프로세스를 죽이지 않고 그
  턴만 멈추고, 답이 글자 단위로 흐르고, 이미지를 붙인다.
- **가능한 길 (검증됨)**: claude `--input-format stream-json`(print 전용, stream-json 출력 필요)으로
  대화마다 프로세스를 살려 두고 사용자 메시지를 stdin으로 더 보낸다. control_request `interrupt`가
  문서화돼 있다. 사용자 메시지의 `priority: now|next|later`는 **공개 SDK 타입에 없는 내부 필드**라
  의존하면 안 된다 — 끼어들기는 interrupt + 새 메시지로. 토큰 스트리밍은
  `--include-partial-messages`(지금 구조로도 가능, 로그 양 급증). 이미지는 SDK 메시지의 content 블록.
- **부딪히는 것**: 가장 크다 — `RunManager`(턴=프로세스), `RunQueue`와 실행 슬롯의 의미,
  `stdin.end()` 원칙(CLAUDE.md 함정), 충돌 복구, `claude --resume` 직렬화 전제.
- **OpenCode**: `run`으로는 불가. `serve`(7번).
- **추천**: 1~3번을 한 뒤. 토큰 스트리밍만 떼어 작은 과제로 할 수 있다.

## 7. OpenCode를 `serve` + SSE로

- **무엇**: OpenCode 쪽에서 1·2·3·5·6을 얻는 유일한 길(라이브 델타, 권한·질문 응답, 대기열·끼어들기,
  되돌리기·분기·압축·diff API).
- **부딪히는 것**: 어댑터 인터페이스가 양방향이 된다(설계 2026-09-06 §10-2). `OPENCODE_PERMISSION`은
  서버 프로세스 환경이라 권한 단계마다 서버를 따로 띄우거나 세션 규칙으로 바꿔야 한다. 서버 수명 관리.
  **1.18의 `/session` 계열과 2.0의 `/api` 계열이 달라** 버전을 고정해야 한다(2.x는
  `conversation-fixes` FR-17이 지금 막는다).
- **추천**: 가장 뒤. 2.x 이행을 먼저 정한다.

## 8. 작은 후속 (설계 변경은 아니지만 이번 범위에서 뺀 것)

- **로그 보존 정책**: 지금도 없다. `conversation-events`로 run당 정규화 로그가 5~10배 커지고
  `raw.jsonl`(run당 상한 32MiB)이 더해진다. 오래된 run의 로그를 줄이거나 지우는 규칙이 필요하다 —
  "기록을 지우지 않는다"(전체 설계 §232)와의 경계를 정해야 한다.
- **하위 에이전트의 말·생각**: `--forward-subagent-text`(공개 플래그)를 붙이면 카드 안에 들어온다.
  로그 크기와 함께 본다.
- **토큰 단위 스트리밍**: `--include-partial-messages`는 지금 구조로도 된다(6번에서 떼어 낼 수 있다).
  델타는 로그에 쓰지 않고 화면에만 흘리는 설계가 필요하다.
