# Spec: 이슈·메모·skill 패널을 repo마다 별도 창으로 연다

- 출처: 사용자 요청(2026-10-01)
  - "메모와 이슈 스킬을 각각 팝업으로 열어서 가독성 좋게, 더 쉽게 처리하게"
  - 모양은 **별도 OS 창**(앱 안 모달이 아니다).
  - "이슈 팝업 하나, 메모 팝업 하나, 스킬 팝업 하나로 하고 각각은 해당 repo의 여러 이슈·메모·스킬을 볼 수
    있어야 함. 다른 repo가 선택될 경우에 이 팝업을 연 repo 항목으로 남아 있어야 해. 결국 repo마다 팝업이
    생성될 수 있는 구조"
- 바꾸는 설계: 전체 설계의 "창은 하나"라는 암묵 가정. `electron/main.ts`의 `mainWindow` 하나, `registerIpc`의
  `getWindow` 하나가 그 가정 위에 서 있다. 앱 창의 세 패널(동적 3컬럼, 2026-09-22)은 그대로 둔다 — 창은
  **더하는** 길이다.
- 작성자: 권용현 (초안: Claude)
- 상태: 구현 (2026-10-01 — 우려 1·2는 넣고, 3은 알려진 제약으로 기록)

## 1. 지금

- 이슈·메모·asset 패널은 앱 창 가운데에 셋이 나란히 있고, 사이드바에서 고른 repo(`repoId`)를 따라 거른다.
  repo를 바꾸면 세 패널이 전부 그 repo로 바뀐다.
- 항목을 열면 그 패널이 남는 폭을 다 쓰고 **목록은 숨는다** — 상세를 보는 동안 다른 항목을 고를 수 없다.
- 패널 셋은 이미 `workspaceId`·`repoId`를 prop으로 받는 독립 컴포넌트다(`IssuePanel`·`MemoPanel`·`AssetPanel`).
  맥락 담기(`chipKeys`·`onToggleContext`)만 앱 창의 state에 묶여 있다.
- 창은 하나다. run 이벤트·큐·인박스·MCP 상태·요금제 push가 전부 `getWindow()` 한 창으로만 간다.
- 상세의 쓰기는 600ms 디바운스 자동 저장이다(`useDebouncedSave`). 대기 중인 저장은 **React 언마운트**에서
  흘려보낸다 — 창을 닫는 것은 언마운트가 아니다.

## 2. 요구

### 창의 단위

- **FR-1. 창 하나 = (종류, repo).** 종류는 이슈·메모·skill(asset 패널 — skill·agent·instructions) 셋이다.
  repo를 고르지 않은 상태(workspace 전체)도 하나의 범위다 — `(종류, workspace, 전체)`.
- **FR-2. 창은 연 순간의 repo에 고정된다.** 앱 창에서 다른 repo나 다른 workspace를 골라도 창의 범위는 바뀌지
  않는다. 그래서 repo마다 창이 생길 수 있다 — `api`의 이슈 창과 `web`의 이슈 창이 나란히 선다.
- **FR-3. 같은 범위의 창은 하나다.** 이미 열린 (종류, repo)를 다시 열면 새로 만들지 않고 그 창을 앞으로
  가져온다(최소화돼 있으면 복원).
- **FR-4. 창 제목은 `<종류> · <repo 이름>`** — 전체면 `<종류> · <workspace 이름> 전체`. 이름을 바꾸면 따라간다.

### 여는 길

- **FR-5. 여는 자리는 각 패널의 헤더 아이콘 하나다** — 이름 `<종류> 새 창으로 열기`(예: `이슈 새 창으로 열기`).
  누르면 그 순간 앱 창이 고른 workspace·repo로 연다.

### 창의 내용

- **FR-6. 창은 같은 패널 컴포넌트를 그린다** — `IssuePanel`·`MemoPanel`·`AssetPanel`에 고정된
  `workspaceId`·`repoId`를 준다. 그래서 묶기·접기·훑기·추가·상세 편집·삭제가 앱 창과 똑같이 된다. 이슈 창은
  그 workspace의 repo 목록도 읽는다(태그 후보).
- **FR-7. 창에서는 목록과 상세가 나란히 선다.** 앱 창처럼 목록을 숨기지 않는다 — 왼쪽 목록(고정 폭), 오른쪽
  상세. 여러 항목을 넘겨 보며 처리하는 것이 창의 목적이다. 항목을 고르지 않았으면 오른쪽은 안내 한 줄이다.
- **FR-8. 창에는 맥락 담기가 없다.** 맥락은 앱 창 도크의 state다 — 패널은 담기 토글을 그리지 않는 모드를 받는다.
  창에서 담으려면 창 사이 통로가 하나 더 필요하다(§4).
- **FR-9. Esc는 열린 상세를 닫는다**(대기 중인 저장을 흘려보낸 뒤 — 지금 상세 규칙 그대로). 창 자체는 Esc로
  닫지 않는다 — 상세를 닫으려다 창이 사라지면 안 된다.
- **FR-10. 범위가 사라지면 창이 말한다.** repo가 지워지면 "이 repo는 삭제됐습니다", workspace가 지워지면 같은
  문구로 workspace를 말하고 목록을 비운다.
- **FR-11. 같은 항목을 두 곳에서 고치면 지금의 충돌 배너가 뜬다.** 새 규칙이 없다 — agent가 MCP로 고친 것과 같은
  길이다.

### 통로와 보안

- **FR-12. 여는 IPC는 `{ kind, workspaceId, repoId | null }`만 받는다.** URL·경로를 넘기는 통로를 만들지 않는다
  (`core/app/reveal.ts`가 이름만 받는 것과 같은 원칙). main은 core로 그 workspace·repo가 있고 repo가 그
  workspace 소속인지 확인한 뒤에만 창을 만든다.
- **FR-13. 창이 무엇을 그릴지는 앱 문서의 해시로 정한다** — `#panel/<kind>/<workspaceId>/<repoId|all>`. 해시를
  만들고 읽는 것은 `shared/`의 순수 함수 한 쌍이다(main에는 테스트가 없다). 해시가 틀리면 창은 "열 수 없는
  창입니다"를 그린다.
- **FR-14. 모든 창이 같은 가드를 받는다.** `webPreferences`·`setWindowOpenHandler`·`will-navigate`를 창마다
  따로 적지 않고 함수 하나로 건다 — 새 창에 하나라도 빠지면 그 창이 원격 문서로 넘어갈 수 있다.
  `nav-guard.e2e`의 검사를 패널 창에도 돌린다.

### 닫기와 저장

- **FR-15. 창을 닫아도 친 글자를 잃지 않는다.** 대기 중인 저장이 있으면 `beforeunload`가 닫기를 한 번 미루고,
  저장을 흘려보낸 뒤 스스로 닫는다. 저장이 실패하면 닫지 않고 오류를 보인다. 대기 중인 저장이 없으면 바로
  닫힌다.
- **FR-16. 앱 창이 닫히면 패널 창도 닫는다** — 각자 FR-15를 탄다. 패널 창만 남은 앱은 만들지 않는다.
- **FR-16a. 앱 창도 같은 장치를 탄다** (우려 2 결정). 지금은 앱을 끄기 600ms 안에 친 글자를 잃는다. 대기 중인
  저장의 목록은 창마다 하나이고, 앱 창·패널 창이 같은 `beforeunload` 처리를 쓴다.
- **FR-16b. 저장의 실패를 닫기가 안다.** 지금 저장 콜백은 오류를 스스로 잡아 화면에 둔다 — 그래서 흘려보내기가
  "성공"으로 끝난다. 닫기를 미룬 흘려보내기만은 실패를 알아야 하므로, 저장 콜백이 실패를 결과로 돌려준다.

### 본문 읽기 (우려 1 결정)

- **FR-20. 상세 본문에 `읽기 / 편집` 전환이 붙는다** — 이슈·메모·asset 모두, 앱 창과 패널 창 모두. 읽기는 본문을
  마크다운으로 그리고, 편집은 지금의 평문 편집칸이다. discovered asset은 편집할 수 없으므로 `읽기 / 원문`이다.
- **FR-21. 본문이 있으면 읽기로 시작하고, 비어 있으면 편집으로 시작한다.** 고른 모드는 그 상세가 열려 있는
  동안만 간다(저장하지 않는다). 읽기에서 본문을 두 번 누르면 편집으로 간다(링크는 한 번 누르면 연다).
- **FR-22. 마크다운은 `renderer/components/Markdown.tsx`를 그대로 쓴다** — 원시 HTML은 글자, 링크는 http(s)만,
  이미지는 그리지 않는다, 파싱 예산을 넘으면 평문. asset 본문은 남의 repo에서 온 신뢰할 수 없는 입력이라
  규칙을 우회하는 별도 렌더러를 만들지 않는다.
- **FR-23. 읽기는 지금 친 글자를 그린다** — 저장된 값이 아니라 편집칸의 state다. 저장 대기 중에 읽기로 바꿔도
  방금 친 것이 보이고, 저장은 그대로 흘러간다.
- **FR-24. 전환 버튼의 이름은 `마크다운으로 보기`·`원문 편집`이다**(discovered는 `원문 보기`). 편집칸의 이름
  `본문`·권한의 `편집 허용`과 부분 일치로 부딪히지 않게 고른 것이다.

- **FR-25. frontmatter는 따로 평문으로 선다** (구현 중 더함, 2026-10-01). SKILL.md·agent 파일 맨 앞의
  `---` … `---`를 마크다운에 넘기면 첫 줄은 가로줄, `name:`·`description:`은 setext 제목(h2)으로 뭉개진다 — 읽기
  화면 맨 위에 큰 제목 한 줄이 선다. 읽기만 그것을 떼어 위에 평문 칸으로 두고(`renderer/frontmatter.ts`),
  저장하는 값은 손대지 않는다. e2e가 같은 이름의 제목 두 개로 strict 위반을 내며 드러났다.

### 목록 숨기기와 폭 (2026-10-01 추가 요청 — "새 창의 이슈 목록을 최소화하고, 마우스로 줄일 수 있게")

- **FR-26. 패널 창의 목록을 숨길 수 있다.** 패널 헤더의 `목록 숨기기` / `목록 보이기` 버튼 하나다. 숨기면 상세가 창을
  다 쓴다. **언마운트하지 않고 CSS로 숨긴다** — 추가 칸에 치던 글자가 남는다(도크 최대화와 같은 이유). 이름에
  "접기"·"펼치기"를 쓰지 않는다(턴의 `접기`와 부분 일치 — CLAUDE.md).
- **FR-27. 목록과 상세 사이의 경계를 끌어 목록 폭을 바꾼다.** `role="separator"`(이름 `목록 폭 조절`, 세로)이고
  키보드 ←→로 16px씩, 두 번 누르면 기본 폭(340px)으로 돌아간다. 폭은 200px ~ 창 폭의 60%로 자른다 — 상세가 사라지지
  않게. 창 크기가 바뀌어 상한을 넘으면 그리는 폭만 자른다.
- **FR-28. 폭과 숨김은 종류마다 이 장비에만 남는다**(`localStorage`, 도크 높이와 같은 이유 — core가 알 필요 없는
  화면 기하값이다). 저장소를 못 쓰면(접근이 막히면) 기본값으로 돈다. 앱 창의 세 칸에는 붙지 않는다.

### 창 사이 동기화

- **FR-17. 이슈·메모·asset이 바뀌면 모든 창에 알린다** — 새 push `event:itemChanged { workspaceId, kind }`.
  core가 쓰기 경로에서 낸다: IPC로 온 쓰기와 **MCP로 온 쓰기 둘 다**(MCP는 저장소를 직접 쓰므로, 알림을 내는
  저장소 래퍼를 core가 한 번 만들어 IPC 쪽과 MCP `deps`에 같이 넘긴다). asset 재스캔이 끝날 때도 낸다.
- **FR-18. 모든 창의 목록이 그 알림으로 다시 읽는다** — 같은 workspace, 같은 종류일 때. 창에서 고친 것이 앱
  창에, 앱 창에서 고친 것이 창에 곧바로 보인다. 지금의 "run이 끝나면 다시 읽기"는 남긴다. repo·workspace 변경
  (FR-10, FR-4의 이름)도 같은 push에 `kind: 'repo' | 'workspace'`로 싣는다.
- **FR-19. 다른 push는 앱 창에만 간다** — run 이벤트·큐·인박스·MCP 상태·요금제. 패널 창은 그것을 그리지 않는다.
  `getWindow`는 `getMainWindow`가 되고, `itemChanged` 하나만 모든 창으로 간다.

## 3. 검증

- 단위:
  - 해시 함수 한 쌍(틀린 kind·빈 id·`all`·인코딩).
  - 창 뿌리가 kind마다 맞는 패널을 고정된 범위로 그리는지, 담기 토글이 없는지.
  - `itemChanged` 구독으로 목록을 다시 읽는지(다른 workspace·다른 kind는 무시).
  - core 래퍼가 IPC 쓰기와 MCP 쓰기 둘 다에서 알림을 내는지.
- e2e(`e2e/panel-window.e2e.ts`, Playwright의 `app.waitForEvent('window')`):
  1. repo `api`를 고르고 `이슈 새 창으로 열기` → 새 창에 `api`의 이슈만 있다.
  2. 앱 창에서 repo `web`을 고른다 → 창은 여전히 `api`의 이슈다.
  3. `web`에서 다시 연다 → 창이 둘이다. `api`에서 다시 연다 → 둘 그대로이고 `api` 창이 앞으로 온다.
  4. 창에서 이슈 하나를 열어 본문을 고친다 → 목록이 그대로 보이고, 앱 창의 목록에도 반영된다.
  5. 디바운스가 끝나기 전에 창을 닫는다 → 앱 창에서 연 상세에 그 글자가 있다(FR-15).
  6. 앱 창에서 repo `api`를 지운다 → 그 창이 "이 repo는 삭제됐습니다".
  7. skill 창에서 discovered 본문이 보인다.
  8. 패널 창에서 `window.open`·`location` 탐색이 막힌다(FR-14).
- 변이: 가드 함수를 패널 창에서 빼기, 알림을 MCP 쪽 deps에서 빼기, `beforeunload` 미루기 빼기, 범위 하나에 창
  하나 지도 빼기, 창의 범위를 앱 창의 repo 선택에 묶기 — 각각 위 테스트 하나가 빨개져야 한다.

## 4. 범위 밖

- 창에서 맥락 담기(FR-8), 창 위치·크기 기억, 창 안에서 범위(repo) 바꾸기, 대화를 창으로 떼기.

## 5. 우려 — 결정 (2026-10-01)

1·2는 넣었다(FR-20~24, FR-16a·b). 3은 고치지 않고 알려진 제약으로 남긴다 — 여기와 CLAUDE.md의 함정 절에 적는다.

아래는 결정 전의 서술이다.

1. **"가독성"이 마크다운 렌더링을 뜻하는가.** 이 spec은 넓은 창과 나란한 목록·상세까지이고 본문은 지금처럼
   평문 편집칸이다. SKILL.md·긴 메모는 마크다운으로 그려야 읽기 좋은데, 그것은 백로그의 "이슈·메모·asset 본문
   마크다운"이고 `Markdown.tsx`의 보안 규칙을 그대로 쓰면 된다. **권고: 상세에 `읽기 / 편집` 전환을 두고 읽기가
   마크다운** — 창과 앱 창 모두에 붙는다. 이 spec에 넣으면 FR이 셋쯤 는다. 빼면 다음 작업.
2. **앱 창을 닫을 때의 같은 구멍.** FR-15의 구멍(창을 닫으면 대기 중인 저장이 사라진다)은 지금 앱 창의 상세에도
   있다 — 앱을 끄기 600ms 안에 친 글자는 잃는다. 같은 장치로 같이 막을 수 있다. 권고: 같이 막는다.
3. **macOS의 Cmd+Q.** 창 하나가 `beforeunload`로 닫기를 미루면 종료 전체가 취소된다(Electron 규칙). 그 창은 저장
   뒤 스스로 닫히지만 앱은 다시 종료를 시작하지 않는다. Windows의 창 닫기는 `window-all-closed`로 이어져 문제가
   없다. 권고: macOS는 지금 받는 사람이 없으니 알려진 제약으로 남긴다.
