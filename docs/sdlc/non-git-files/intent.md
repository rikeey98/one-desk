# Intent: git이 아닌 폴더에서도 코드 칸이 파일을 보이고 고친다

- 출처: 대화 (2026-10-29) — "파일 보기 기능이 지금은 git 으로 관리되고 있는것만 보는데 꼭 그래야해? 그냥 폴더 그대로 보여주면 안됨?"
  → 막힌 경우를 묻자 "git이 아닌 폴더였어."
- 작성자: 권용현 (초안: Claude)
- 상태: **승인됨** (2026-10-29, 사용자 "spec") — spec은 `spec.md`
- 작성일: 2026-10-29
- 관계: 코드 칸 첫 사이클(`docs/sdlc/code-editor/spec.md`)의 §4의 1 "git repo만 지원으로 좁힌다"(사용자 승인 2026-10-09)를 뒤집는다.
  `@` 파일 참조(`docs/sdlc/input-triggers/`)의 "git이 아닌 repo에서는 `@`가 아무것도 싣지 않는다"도 같이 뒤집는다(아래 "같은 목록").

## 문제

git으로 관리하지 않는 폴더를 repo로 등록하면 코드 칸의 파일 트리가 비고 `git 저장소가 아니라 파일 목록을 만들 수 없습니다`만 보인다.
파일을 보거나 고치려면 앱 밖의 편집기를 열어야 한다. 메모·문서 폴더, 아직 `git init`하지 않은 새 프로젝트, 받아 둔 예제 같은 폴더가
여기에 걸린다.

## 현황 (읽고 확인한 것)

- 목록은 `core/files/list.ts`의 `listRepoFiles` 한 함수다 — `git ls-files -co --exclude-standard -z`. git이 아니면 `ok: false`.
- 그 목록 하나를 넷이 같이 쓴다(`core/files/service.ts`): 트리(`tree`), 열기(`open` — 목록에 있는 파일만), 저장(`save` — **새 목록**에 있는
  파일만, `.git/hooks`·무시된 파일을 쓰는 길을 막는 자리), `@` 피커와 보낼 때의 해석(`search`·`resolveMentions`).
- repo 밖으로 나가는 읽기·쓰기는 목록과 별개로 `read.ts`·`write.ts`가 양쪽 realpath로 막는다.
- 목록 상한은 20만 개(`MAX_LISTED_FILES`), git 조회 시간 상한은 5초다.
- git이 아닌 폴더를 막은 이유(code-editor spec §4의 1): 디렉토리를 직접 훑으면 `.gitignore`를 따를 수 없어 `node_modules`·빌드 산출물이
  트리를 채우고, 쓸 수 있는 범위가 "repo 안 아무거나"로 넓어진다.

## 원하는 결과

- git이 아닌 폴더에서도 트리가 선다. 폴더를 직접 훑은 목록이고, 흔한 무거운 폴더(`node_modules`·`.git`·`dist`·`build`·`out`·`.venv`·`venv`·
  `__pycache__`·`target`·`.next` 등 — spec에서 확정)는 건너뛴다. 심링크·junction은 따라가지 않는다.
- 그 목록 안의 파일은 git repo와 똑같이 열고 Ctrl+S로 저장한다(해시 충돌·줄바꿈·BOM 규칙 그대로).
- 트리 위에 이 폴더가 git이 아니라 폴더를 직접 보여 준다는 안내가 한 줄 선다 — 무시 규칙이 없다는 것을 사람이 안다.
- **건너뛸 이름은 설정에서 고친다** (2026-10-29, 사용자 "설정에 폴더에서 읽지 않는 이름 관리할수 있도록 하자"). 설정 **앱 탭**에
  `폴더에서 읽지 않는 이름` 절이 서고, 처음에는 기본 목록이 채워져 있다. 이름을 더하고 빼고, `기본값으로` 되돌릴 수 있다. 절마다
  저장이 따로인 규칙 그대로다.
  - 범위는 앱 전체다(`app_setting`, 마이그레이션 없음) — 이름은 장비의 습관이지 workspace마다 다른 것이 아니다(추정). repo마다
    다르게 둘 필요가 보이면 그때 repo 탭에 예외를 더한다(`agent-path-default`의 앱 기본값 + 예외 모양).
  - 이름은 **정확히 같은 이름**과만 맞는다(대소문자는 spec에서). 와일드카드·경로 패턴은 받지 않는다 — 그것이 필요하면 `.gitignore`
    읽기가 맞는 답이다(범위 밖).
  - 폴더 이름과 파일 이름 둘 다에 걸린다(`.DS_Store`·`Thumbs.db` 같은 것도 뺄 수 있게).
  - 설정을 바꾸면 다음 목록 조회부터 따른다(목록 캐시 10초를 비운다).
  - git repo에는 걸리지 않는다 — git repo의 목록은 `.gitignore`가 정한다. 화면의 안내문이 그것을 말한다.
- **git repo는 지금 그대로다.** 무시된 파일은 여전히 안 보이고 못 고친다.

## 같은 목록 — `@`도 따라온다

트리와 `@`가 한 목록을 쓰는 규칙은 지킨다. 그래서 git이 아닌 폴더에서는 `@` 피커도 그 훑은 목록에서 고르고, 보낼 때도 그것으로 해석한다.
목록을 둘로 가르면 "트리에는 보이는데 `@`로는 안 실리는" 파일이 생긴다. 노출이 새로 넓어지지는 않는다고 본다(추정) — 그 폴더에서 도는
agent는 Read 도구로 폴더 안 아무 파일이나 이미 읽을 수 있고, 무시 규칙이 없는 폴더라 비밀이 따로 표시돼 있지도 않다.

## 제약

- 목록 함수는 여전히 하나다 — `listRepoFiles`가 git이 아니면 훑기로 넘어간다. 호출자 넷은 바뀌지 않는다.
- 훑기도 비동기이고(메인 프로세스의 MCP 서버를 멈추지 않는다), 개수 상한(20만)과 시간 상한을 지키며, 넘으면 `truncated`다.
- 저장의 "새 목록에 있는 파일만" 규칙은 그대로다. 훑은 목록에는 `.git`이 없으므로 `.git/hooks`를 쓰는 길은 여전히 없다.
- "git이 아니다"의 판정은 git이 그렇다고 말할 때뿐이다. git 실행 파일이 없거나, 시간이 넘었거나, 다른 이유로 실패하면 지금처럼 이유를
  보인다 — git repo가 git 고장 때문에 무시 규칙 없는 목록으로 조용히 바뀌면 안 된다.
- WSL repo는 Windows 쪽에서 UNC 경로로 훑는다(파일 읽기·쓰기가 이미 그렇게 한다). 느릴 수 있다 — spec에서 잰다.
- 세 경계, 색 토큰·아이콘 규칙, 짧은 새 이름의 부분 일치.

## 범위 밖

- git repo에서 무시된 파일(`.env` 등)을 보이거나 고치는 것. 따로 원하면 다른 작업이다.
- repo마다 다른 건너뛸 목록(앱 전체 설정 하나로 시작한다).
- 와일드카드·경로 패턴, 폴더 안의 `.gitignore`를 읽어 따르는 것.
- 큰 폴더를 위한 지연 로딩(펼칠 때 하위 폴더를 읽기). 상한으로 시작하고 써 보고 다시 본다.

## 미해결 질문 (spec에서 다룬다)

- [ ] 기본 목록의 최종본. 숨김 폴더(`.`으로 시작)를 통째로 건너뛸지(`.vscode`·`.claude`는 보고 싶을 수 있다 — 설정이 생겼으니 기본은
  이름을 하나씩 대는 쪽으로 기운다).
- [ ] 이름 비교의 대소문자(Windows 파일 시스템은 대소문자를 가리지 않는다).
- [ ] 설정 절의 모양 — 한 줄에 하나인 글 칸인지, 칩 목록 + 추가 칸인지.
- [ ] 훑기 시간 상한과, 넘었을 때 목록을 버릴지 거기까지 보일지.
- [ ] 폴더가 홈 디렉토리나 드라이브 루트처럼 거대하면 — 상한으로 충분한지.
- [ ] 안내 문구와 자리.

## 성공 기준

- git이 아닌 폴더를 repo로 등록하고 코드 칸을 열면 트리가 서고, `node_modules` 안 파일은 없다.
- 그 폴더의 파일을 열어 고치고 Ctrl+S로 저장하면 디스크에 쓰인다(CRLF·BOM 보존 — 지금 `code-pane.e2e`의 방식).
- 같은 폴더에서 `@`로 그 파일을 골라 보내면 맥락에 실린다.
- 설정 앱 탭에서 이름 하나를 더해 저장하면, 그 이름의 폴더가 다음 트리 새로고침에서 사라진다. `기본값으로`를 누르면 돌아온다.
- git repo에서는 무시된 파일이 여전히 트리에 없고 저장도 거부된다(지금 테스트 그대로 초록).
- git 실행 파일을 못 찾는 경우 훑기로 넘어가지 않고 이유를 보인다.
- `pnpm test` · `pnpm typecheck` · `pnpm lint` · `pnpm test:e2e` 전부 통과.
