# Intent: 코드를 보고, 몇 줄 고치고, 명령 하나 돌리려면 앱을 떠나야 한다

- 출처: 대화 (2026-10-09)
- 작성자: 권용현 (초안: Claude)
- 상태: 승인 (2026-10-09, 사용자 — "좋아 git diff로 가고 1번 spec 시작해")

## 정해진 것 (2026-10-09, 사용자)

- **Claude Code 데스크톱의 상단 버튼처럼 셋을 둔다 — 터미널 · 변경사항 · 폴더.** 브라우저는 뺀다.
- **앱 창 안에서 연다** — 대화를 보면서 같이 볼 수 있어야 한다. 별도 OS 창이 아니다.
- **폴더**: repo를 둘러보고 아무 파일이나 열어 읽고 고친다. 편집은 가볍게(구문 강조·찾기·저장) —
  여러 탭·자동완성·정의로 이동 같은 IDE 기능은 바라지 않는다. 큰 작업은 여전히 agent나 VS Code가 한다.
- **변경사항**: 기본은 git의 커밋 안 된 변경(작업 트리 ↔ HEAD)이고, 대화에서 열면 그 대화가 건드린
  파일만 걸러 본다. 바뀐 파일을 열어 바로 고칠 수 있다.
- **터미널**: 그 repo에서 셸을 열어 명령을 돌린다.
- **diff는 git diff로 간다** — 전체 설계 §10의 스냅샷 방식(`logs/<run_id>/before/`)은 만들지 않고 §10을 고친다.
  §10의 본문은 변경사항 spec에서 고친다.
- **셋을 따로 돈다** — intent는 하나, spec → plan → 구현은 셋으로. 순서는 ① 상단 버튼과 패널 틀 + 폴더
  ② 변경사항 ③ 터미널(네이티브 모듈 위험을 따로 뗀다).
- 아래 미해결 질문의 "범위 밖" 목록을 그대로 받는다.

## 문제

agent가 일을 끝낸 뒤 사람이 하는 일은 대개 셋이다 — 무엇이 바뀌었나 보고, 틀린 몇 줄을 고치고, 테스트나
git 명령을 돌려 본다. one-desk에서는 셋 다 앱 밖에서 한다.

- **보기**: 대화록의 편집 줄을 펼치면 도구 호출 하나의 hunk만 보인다. 파일 전체의 맥락도, 대화 전체가 바꾼
  것을 한데 모은 모습도 없고, 셸 명령으로 바꾼 파일은 아예 안 보인다. 지시를 쓰기 전에 "이 함수가 지금 어떻게
  생겼더라"를 확인할 자리도 없다.
- **고치기**: agent가 거의 맞게 했는데 한두 줄이 틀렸으면 VS Code로 넘어가거나(repo 줄의 "열기") agent에게
  다시 시켜야 한다. 직접 고치는 편이 빠른데 그 길이 앱 밖에 있다.
- **돌려 보기**: `pnpm test`, `git status` 하나를 치려고 따로 띄운 터미널 창으로 간다. 작업 디렉토리도 손으로
  맞춘다.

앱을 떠나는 것 자체가 비용이다. 창이 바뀌고, 보던 대화가 가려지고, 돌아오면 어디까지 봤는지 다시 찾는다.
전체 설계의 출발점("터미널 창 수십 개 … 편집기 여러 개 … 흩어진 맥락을 다시 모아야 한다")과 §10의
"편집기를 여는 것 자체가 맥락 전환"이 말하던 바로 그 비용이다. 남은 5단계 과제인 diff 뷰어가 이 중
"보기"를 풀려던 자리였다.

## 원하는 결과

앱 창을 떠나지 않고, 대화를 옆에 둔 채로

- repo의 파일을 골라 열어 읽고, 몇 줄 고쳐 저장할 수 있다.
- 커밋 안 된 변경을 파일별로 보고, 대화에서는 그 대화가 건드린 파일만 모아 보고, 틀린 곳을 고칠 수 있다.
- 그 repo를 작업 디렉토리로 한 셸에서 명령을 돌릴 수 있다.

그리고 **사람과 agent가 서로의 수정을 조용히 덮어쓰지 않는다** — 덮어쓰게 되는 상황이면 저장하기 전에
알 수 있다.

## 영향받는 것

- 사람: agent에게 코드 작업을 맡기고 결과를 확인·손보는 사용자. 주 환경은 Windows.
- 데이터: repo의 작업 트리 파일(**처음으로 앱이 repo 파일을 쓴다**)과 git 상태. DB 스키마는 아직 모른다.
- 코드
  - `core/files/` — 목록(`listRepoFiles`, `git ls-files`)·읽기(`readRepoFile`, realpath로 repo 밖 차단,
    256 KiB·바이너리·UTF-8 거부)가 `@` 참조용으로 이미 있다. 쓰기와 git diff는 없다.
  - 대화 이벤트 — 편집 도구의 `detail`(파일별 경로·hunk)이 이미 로그에 있어 "건드린 파일"의 재료가 된다.
    셸로 바꾼 파일은 거기 없다.
  - 터미널 — 의사 터미널(pty)이 필요하다. Node에는 없어서 **네이티브 모듈이 하나 더 는다**(지금은
    `better-sqlite3` 하나). 화면 쪽은 터미널 에뮬레이터 라이브러리.
  - 렌더러 — 상단 버튼과 세 패널. 편집기·터미널 라이브러리만큼 번들이 는다(conversation-timeline 때 약 1.16 MB).
  - IPC — 새 통로(파일 읽기·쓰기, diff, 터미널 입출력 스트림).
  - 릴리스 — 네이티브 모듈을 러너마다 그 플랫폼의 Electron ABI로 컴파일하는 단계(`postinstall`의
    `electron-rebuild`, `asarUnpack`).

## 제약

- 세 경계(`core/`는 electron 없음 · renderer는 core 없음 · IPC는 얇다)를 지킨다.
- **렌더러는 경로를 넘기지 않는다** — repo id + repo 안 상대 경로로만 읽고 쓴다(`readBody`·`reveal.ts`와
  같은 원칙). 쓰기와 셸은 읽기보다 위험하다: 렌더러에 구멍이 나면 이 통로로 repo 파일을 고치고 명령을
  돌릴 수 있다. 마크다운 렌더링의 규칙(원시 HTML 없음, http(s) 링크만)이 지금보다 더 무거워진다.
- 저장은 사람이 고친 부분 말고는 파일을 바꾸지 않는다 — Windows repo의 CRLF·끝 개행·인코딩이 저장 한 번에
  바뀌면 diff 전체가 바뀐 줄이 된다.
- agent가 같은 repo에서 도는 중일 수 있다. "확실하지 않으면 확실하지 않다고 말한다"(설계 §10)를 따른다.
- 파일 내용은 신뢰할 수 없는 입력이다 — 화면에 그릴 때 마크다운·HTML로 해석하지 않는다.
- 터미널이 띄운 프로세스는 앱을 끄면 트리째 죽는다 — agent 실행의 `cancelAll`이 겪은 함정(Windows에서
  비동기 taskkill이면 손자가 남는다)이 그대로 있다.
- 네이티브 모듈은 크로스 컴파일이 안 된다. Windows 빌드 도구는 VS Build Tools 2022로 고정돼 있다.

## 미해결 질문

- **전체 설계 §10의 diff 방식을 바꾸는가.** §10은 git이 아닌 repo도 다루려고 "편집 도구를 감지하면 원본을
  `logs/<run_id>/before/`에 복사"하는 스냅샷 방식을 정했다. "기본은 git diff"는 그와 다른 길이다.
  (가정: **git diff로 간다. 스냅샷 방식은 만들지 않고 §10을 고친다** — OpenCode는 도구 이벤트가 파일이 이미
  바뀐 뒤에 와서 스냅샷이 원리적으로 불가능하다. spec 전에 확인)
- **버튼은 어디에 붙나.** Claude Code는 화면이 세션 하나라 버튼의 대상이 분명하다. one-desk는 사이드바 · 세
  패널 · 도크(대화)라 "어느 repo의 터미널인가"가 갈린다 — 대화 헤더에 붙여 그 대화의 작업 디렉토리를 따를지,
  앱 상단에 붙여 사이드바에서 고른 repo를 따를지. (spec에서 시안으로 고른다)
- 셋을 동시에 열 수 있나, 하나씩 바꿔 보나. (spec에서 시안으로 고른다)
- git이 아닌 repo는? (가정: **폴더·터미널은 되고 변경사항만 "git repo만 지원합니다"** — 다만 폴더의 트리는
  지금 `git ls-files`라 git이 아니면 `.gitignore`를 따를 수 없다. `@` 참조는 git이 아니면 아무것도 안 싣기로
  했었다)
- 대화에서 거른 diff는 정확히 "그 대화의 변경"이 아니다 — 같은 파일을 사람이나 다른 대화도 고쳤다면 섞이고,
  셸로 바꾼 파일은 빠진다. (가정: **그대로 두고 화면이 그 사실을 말한다**)
- 연 뒤 디스크의 파일이 바뀌었으면(agent가 고쳤으면) 저장은? (가정: **저장을 막고 알린다** — 이슈 본문의
  충돌 배너와 같은 태도. 자동 병합은 하지 않는다)
- 터미널: 몇 개를 여나, 앱을 다시 켜면 남나, 셸은 무엇인가. (가정: **repo당 하나, 다시 켜면 새로 시작,
  Windows는 PowerShell**)
- agent가 터미널 출력을 읽을 수 있어야 하나 — Claude Code는 그런 도구가 있다. (가정: **이번엔 아니다**)
- 사람이 고친 것을 다음 턴의 agent에게 알려야 하나. (가정: **아니다** — CLI가 파일을 새로 읽는다)
- 열 수 있는 파일의 한계 — 크기·바이너리·인코딩. 지금 읽기의 256 KiB는 `@` 참조용 상한이다.
- 범위 밖으로 가정한 것: 스테이지·커밋·변경 버리기, 여러 파일 탭, 새 파일 만들기·이름 바꾸기·지우기,
  파일 트리에서 맥락에 담기, 브라우저. (가정: **전부 이번 범위 밖** — 하나라도 필요하면 spec 전에 말해 달라)
