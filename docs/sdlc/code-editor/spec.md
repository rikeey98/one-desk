## 0. 사용자가 정한 것 (2026-10-09)

| 질문 | 답 |
|---|---|
| 계기 | agent가 바꾼 것 확인 + repo 둘러보기, 둘 다 |
| 편집 수준 | 가벼운 편집 + 저장 (구문 강조·찾기·저장. 탭·자동완성·정의로 이동 없음) |
| 배치 | **안 A** — 버튼은 대화 헤더 오른쪽, 코드 칸은 도크 안 대화 오른쪽. 대상은 그 대화의 작업 디렉토리 |
| 범위 밖 | 스테이지·커밋·변경 버리기, 여러 파일 탭, 파일 만들기·이름 바꾸기·지우기, 트리에서 맥락에 담기, 브라우저 |

## 1. 요약

대화 헤더 오른쪽에 `파일` 버튼이 서고, 누르면 도크 안 대화 오른쪽에 코드 칸이 열린다. 칸은 그 대화의 repo
파일 트리와 편집기 하나다. 파일을 골라 읽고, 몇 줄 고쳐 Ctrl+S로 저장한다. 연 뒤에 디스크가 바뀌었으면(agent가
고쳤으면) 덮어쓰지 않고 알린다. 대화록의 편집 파일 줄에서도 그 파일을 그 줄에 연다. 도크를 최대화하면 대화
목록 · 대화 · 코드 칸이 창 높이를 다 쓴다.

**앱이 repo 파일을 쓰는 첫 통로다.** 그래서 읽기·쓰기 모두 `@` 참조와 같은 목록(`git ls-files -co
--exclude-standard`)에 있는 파일만 받는다 — `.git/`·무시된 파일은 보이지도 고쳐지지도 않는다.

## 2. 기능 요구사항

### (A) 틀 — 버튼과 칸

- **FR-1** 대화 헤더(`ConversationHeader`)의 오른쪽 끝에 코드 칸 버튼 줄이 선다. 이번 사이클에는 `파일` 하나다.
  버튼은 눌림 상태(`aria-pressed`)를 가진 토글이고, 아이콘 + 글자 `파일`이다. 변경사항·터미널은 각자의 사이클에서
  이 줄에 더해진다 — 이번에 자리표시자(비활성 버튼)를 두지 않는다.
- **FR-2** 칸은 도크 본문(`.dock-split`)에서 대화(`.dock-main`) **오른쪽**에 형제로 선다: 대화 목록 · 대화 · 코드 칸.
  대화 칸을 대화마다 다시 마운트하는 key(`draftKeyOf`)의 바깥이라, 대화를 바꿔도 칸이 다시 마운트되지 않는다.
- **FR-3** 칸은 한 번에 하나의 종류만 보인다(이번에는 파일뿐). 열린 칸의 버튼을 다시 누르면 닫힌다. 칸 머리에도
  닫기(이름 `코드 칸 닫기`)가 있다.
- **FR-4** 대화와 칸 사이 경계(이름 `코드 칸 폭 조절`, `role="separator"`)를 끌어 폭을 바꾼다. 칸 최소 320px,
  대화 최소 360px. 더블클릭하면 기본(대화와 반반)으로 돌아간다. 폭과 열림 여부는 이 장비의 localStorage에 남는다
  (보기 취향 — `listWidth.ts`·`dockHeight.ts`와 같은 방식). 도크가 다시 마운트돼도(인박스·설정에 다녀오기) 열린 채다.
- **FR-5** 도크를 접으면 칸도 접힌다(도크 안이다). 최대화는 지금 그대로 세 패널을 숨기고 도크가 본문 전체를 쓴다 —
  코드 칸도 그 높이를 쓴다.
- **FR-6** 칸의 대상 repo:
  - 이어 가는 대화 — 뿌리 턴의 `cwd`와 경로가 같은 등록 repo(`repoOfConversation`, dock-repo-sections FR-1). 대화
    목록의 구획·헤더의 repo 이름과 같은 판정이다.
  - 새 대화 칸 — 입력부의 작업 디렉토리 알약이 지금 고른 repo. 알약을 바꾸면 칸도 따라간다.
  - 대상이 없으면(`기타` 대화 — 등록하지 않았거나 경로가 바뀐 repo, 또는 repo가 하나도 없는 workspace) 버튼은
    서되 비활성이고 `title`이 이유를 말한다(`이 대화의 작업 디렉토리는 등록된 repo가 아닙니다`).
- **FR-7** 대화를 바꾸면 칸은 열린 채로 새 대화의 repo를 따른다. repo마다 마지막으로 연 파일과 펼친 폴더를 기억해
  (이 앱이 켜져 있는 동안), 같은 repo의 다른 대화로 옮겨도 보던 파일이 그대로다.

### (B) 파일 트리

- **FR-8** 트리는 그 repo의 `git ls-files -co --exclude-standard` 목록이다(`core/files/list.ts`의 `listRepoFiles` —
  `@` 피커와 **같은 함수**). 폴더는 경로에서 만든다. 폴더가 먼저, 이름순(대소문자 무시). 폴더는 접힌 채 시작한다.
- **FR-9** 트리 위에 찾기 칸(이름 `파일 이름으로 찾기`)이 있다. 치면 트리 대신 퍼지 결과 목록이 된다 — `@` 피커와
  같은 `matchFiles`(상한 50). ↑↓·Enter로 연다. 비우면 트리로 돌아간다.
- **FR-10** 트리는 칸을 열 때, 대상 repo가 바뀔 때, 같은 workspace의 run이 끝날 때, 그리고 머리의 `파일 목록 새로고침`을
  누를 때 다시 읽는다. 새로고침은 core의 10초 캐시를 건너뛴다.
- **FR-11** 목록을 못 얻으면(git 저장소가 아님 · git 없음 · 시간 초과) 트리 자리에 이유(`listRepoFiles`의 `reason`)와
  `VS Code에서 열기`(기존 `repos.openInEditor`)를 보인다. 상한(20만 개)에 걸렸으면 트리 아래에 그 사실을 말한다.

### (C) 편집기

- **FR-12** 편집기는 CodeMirror 6이다 — 줄 번호, 구문 강조, 괄호 짝, 들여쓰기, 실행 취소, 찾기·바꾸기(Ctrl+F로 여는
  찾기 창 하나에 바꾸기 칸이 같이 있다).
  자동완성·린트·접기·미니맵은 없다. 언어는 확장자로 고르고 **필요할 때 불러온다**(언어 패키지를 첫 번들에 넣지 않는다).
  모르는 확장자는 평문이다. 마크다운 파일도 원문으로만 보인다(이번에 미리보기 없음).
- **FR-13** 색은 `renderer/index.css` 토큰에서만 온다 — 다크 스킴이 따라간다. 글꼴은 `--font-mono`.
- **FR-14** 칸 머리에 연 파일의 경로(모노, `.path-text`)와 상태가 선다: 고친 것이 있으면 `●`(이름 `저장하지 않음`),
  저장 중·저장됨·실패.
- **FR-15** 열 수 있는 것은 목록에 있는 **UTF-8 텍스트 파일, 2 MiB 이하**다. 바이너리·UTF-8 아님·너무 큼·없음(목록에는
  있지만 작업 트리에서 지워짐)은 편집기 대신 이유와 `VS Code에서 열기`를 보인다. 판정은 `readRepoFile`의 규칙
  그대로이고 상한만 인자로 받는다(`@`는 256 KiB 그대로).
- **FR-16** 줄바꿈이 섞인 파일(CRLF와 LF가 둘 다 있는 파일)은 **읽기 전용**으로 연다 — 머리에 `줄바꿈이 섞여 있어 고칠
  수 없습니다`. 저장하면 파일 전체의 줄바꿈이 한쪽으로 바뀌어 diff 전체가 바뀐 줄이 되기 때문이다.

### (D) 저장

- **FR-17** 저장은 **명시적**이다 — 편집기에서 Ctrl+S(macOS ⌘S) 또는 머리의 `파일 저장`. 자동 저장하지 않는다:
  치는 도중의 코드가 repo에 써지면 dev 서버가 반쯤 고친 파일로 다시 빌드하고, 같은 repo에서 도는 agent가 그것을 읽는다.
- **FR-18** 저장은 **사람이 고친 것 말고 파일을 바꾸지 않는다.** 렌더러는 `\n` 텍스트만 다루고, core가 디스크 파일의
  줄바꿈(CRLF/LF)과 UTF-8 BOM 유무를 그대로 되살려 쓴다. 끝 개행은 텍스트에 있는 그대로다.
- **FR-19** 저장은 **연 때의 디스크 내용과 지금의 디스크 내용이 같을 때만** 쓴다(내용 해시 비교 — 이슈 본문의
  `updateIfUnchanged`와 같은 태도). 다르면 쓰지 않고 충돌로 돌려준다. 칸은 충돌 배너를 띄운다 — `이 파일이 디스크에서
  바뀌었습니다` + `디스크 내용 불러오기`(내 고침을 버린다) + `내 것으로 덮어쓰기`(지금 디스크 해시를 기대값으로 다시
  저장). 자동 병합은 하지 않는다.
- **FR-20** 고친 것은 저장하기 전까지 **잃지 않는다** — 칸을 닫아도, 다른 파일을 열어도, 대화·workspace를 바꿔도,
  인박스·설정에 다녀와도 남는다(렌더러 스토어, 초안 스토어와 같은 자리 — `main.tsx`). 트리의 그 파일 줄에 `●`가 서고,
  칸 머리가 `저장하지 않은 파일 N`을 말한다. 버리는 것은 머리의 `고친 것 버리기`(두 번 누르기, `ConfirmButton`)뿐이다.
- **FR-21** 저장하지 않은 파일이 있는데 앱 창을 닫으면 닫기를 멈추고 **앱 안에서** 묻는다: `모두 저장하고 닫기` ·
  `저장하지 않고 닫기` · `취소`. 저장 중 하나라도 충돌·실패하면 닫지 않고 그 파일을 칸에 연다. 지금의 대기 중 저장
  흘려보내기(`guardUnload`)와 같은 `beforeunload` 자리에서 한 번에 판정한다.

### (E) 디스크가 바뀔 때

- **FR-22** 칸이 보이는 동안 연 파일이 디스크에서 바뀌었는지 몇 초(목표 2초) 안에 안다. 칸이 안 보이면 보일 때 확인한다.
  - 고친 것이 없으면 새 내용으로 조용히 바꾼다(커서 줄은 최대한 지킨다). agent가 고치는 동안 칸이 따라간다.
  - 고친 것이 있으면 바꾸지 않고 머리에 `디스크에서 바뀜`을 세운다. 그대로 저장하면 FR-19의 충돌이 된다.
  - 지워졌으면 `디스크에서 지워졌습니다`를 세우고 저장을 막는다(만들기는 범위 밖). 고친 글은 복사할 수 있게 남긴다.

### (F) 대화록에서 열기

- **FR-23** 펼친 턴의 편집 파일 줄(`TimelineBlocks`의 `.tl-file`)에 `파일 열기`(이름 `<경로> 코드 칸에서 열기`) 아이콘이
  선다. 누르면 코드 칸을 열고 그 파일을 **그 편집의 첫 hunk 줄**로 연다(hunk가 없으면 첫 줄). 경로가 그 대화 repo 밖이면
  (절대 경로가 repo 경로로 시작하지 않으면) 아이콘이 없다. 경로 비교는 FR-6의 규칙(끝 구분자 무시, Windows 대소문자
  무시)이고, 상대 경로는 repo 기준으로 본다.

### 3-2. 데이터

- **DB에 아무것도 쓰지 않는다.** 파일 내용은 렌더러 메모리(고친 버퍼)와 IPC로만 오간다 — 로그·DB에 남지 않는다.
  tracked 파일에 비밀이 있을 수 있으므로 이 성질을 지킨다.
- localStorage(이 장비): 칸 열림 여부·종류·폭. 보기 취향이라 잃어도 된다(try/catch).
- 렌더러 스토어(앱이 켜진 동안): repo마다 열린 파일·펼친 폴더, (repo, 경로)마다 고친 버퍼와 그 기대 해시. 앱을 다시
  켜면 비어 있다 — 닫을 때 FR-21이 묻기 때문에 조용히 잃지 않는다.

### 3-3. 인터페이스 (모양만 — 이름과 시그니처는 plan)

모든 요청은 `{ workspaceId, repoId, path }`로 파일을 가리킨다. `path`는 repo 상대, `/` 구분이다. **절대 경로를 받는
통로는 없다**(`assets.readBody`·`reveal.ts`와 같은 원칙).

- **목록**: `{ ok: true, files, truncated } | { ok: false, reason }` — `files.search`와 같은 모양에서 퍼지만 뺀 것.
- **열기**: `{ ok: true, content, hash, eol: 'lf'|'crlf'|'mixed'|'none', bytes } | { ok: false, reason }`. `content`는
  `\n` 줄바꿈, BOM 없음.
- **저장**: 요청에 `content`(`\n` 텍스트)와 `expectedHash`. 응답은 `{ ok: true, hash } | { ok: false, conflict:
  { hash, deleted } }`. 충돌의 지금 내용은 다시 열기로 받는다.
- **바뀜 확인**: 열린 파일의 지금 해시(또는 지워짐)만 돌려주는 가벼운 질의.
- **던지는 것**(잘못된 호출 — 화면이 만들 수 없는 요청): 다른 workspace의 repo, 목록에 없는 경로, repo 밖(realpath),
  일반 파일이 아님, 줄바꿈이 섞인 파일의 저장. 사람이 만날 수 있는 실패(충돌·지워짐·권한·잠김·디스크 가득)는 던지지
  않고 결과로 온다.

### 3-4. 저장의 판정 순서 (core)

1. repo가 그 workspace 소속인가(`files.search`와 같다).
2. 경로가 **지금** 목록(`listRepoFiles`, 캐시 아님)에 있는가 — `.git/hooks/*`나 무시된 파일을 쓰는 길을 막는다.
3. 양쪽 realpath로 repo 안인가, 일반 파일인가(`readRepoFile`의 검사 그대로).
4. 디스크 내용의 해시가 `expectedHash`와 같은가. 아니면 충돌.
5. 디스크 파일의 줄바꿈·BOM으로 텍스트를 되돌려 **제자리에** 쓴다(임시 파일 + 이름 바꾸기가 아니다 — Windows에서
   다른 프로세스가 연 파일의 이름 바꾸기가 실패하고, 파일의 권한·하드링크가 바뀐다).

4와 5 사이는 원자적이지 않다 — 그 틈에 agent가 쓰면 사람이 덮어쓴다. 틈은 해시 한 번과 쓰기 한 번 사이(밀리초)다.

### 3-5. 실패할 때

| 상황 | 동작 |
|---|---|
| git 없음·git 저장소 아님·목록 5초 초과 | 트리 자리에 이유 + `VS Code에서 열기`. 열기·저장도 같은 이유로 막힌다(목록이 판정의 첫 칸이다) |
| 파일을 열 수 없음(크기·바이너리·인코딩·없음) | 편집기 자리에 이유 + `VS Code에서 열기` (FR-15) |
| 저장 충돌 | 충돌 배너 (FR-19). 고친 버퍼는 그대로 |
| 쓰기 실패(권한·읽기 전용 속성·다른 프로세스가 잠금·디스크 가득) | 머리에 실패와 OS 메시지. 고친 버퍼는 그대로, 다시 저장할 수 있다 |
| 저장 중 앱 창 닫기 | FR-21 — 끝날 때까지 닫지 않는다 |
| 대상 repo가 지워짐 | 칸에 `이 repo는 삭제됐습니다`. 그 repo의 고친 버퍼는 남아 닫기 판정에 세지고, 복사만 된다 |
| 대상 repo의 경로가 바뀜 | 같은 repo id라 그대로 새 경로를 본다. 연 파일이 새 경로에 없으면 FR-22의 지워짐이 된다 |
| 렌더러 구멍(악성 마크다운 등) | 이 통로로 목록에 있는 파일을 고칠 수 있다 — §4의 2 |

## 4. 우려 (정해야 할 것)

1. **git이 아닌 repo에서는 파일 칸이 아무것도 못 한다.** intent는 "폴더는 git이 아니어도 된다"로 가정했지만, 트리를
   `git ls-files`로 만들고 읽기·쓰기를 그 목록으로 막기 때문에 git이 아니면 트리도 열기도 없다(`@` 참조와 같은 결정).
   디렉토리를 직접 훑으면 `.gitignore`를 못 따라 `node_modules`·빌드 산출물이 트리를 채우고, 무엇을 쓸 수 있는지의
   경계가 "repo 디렉토리 안 아무거나"로 넓어진다. → **사용자**: git repo만 지원으로 좁혀도 되는가.
2. **쓰기 통로가 생기는 대가.** 렌더러에 구멍이 나면(마크다운 규칙이 뚫리면) 그 스크립트가 tracked 파일을 고칠 수
   있다 — `package.json`의 scripts를 고치면 다음 `pnpm` 실행에 코드가 돈다. 다만 같은 구멍으로 이미 `runs.start({
   permission: 'full' })`을 부를 수 있어 **새 등급의 위험은 아니다.** 목록 제한(§3-4의 2)이 `.git/hooks`를 막는다.
   → **사용자**: 이 수준으로 받아들이는가.
3. **무시된 파일은 안 보인다.** `.env`·로컬 설정처럼 `.gitignore`된 파일은 트리에 없고 대화록에서도 못 연다. 비밀을
   화면에 끌어오지 않는 쪽으로는 장점이지만, "`.env.local` 좀 고쳐야지"는 여전히 VS Code다. → **사용자**.
4. **번들이 는다.** CodeMirror 6 본체(상태·뷰·명령·찾기·언어 기반·강조)가 첫 번들에 들어간다. 압축하지 않은 크기로
   수백 KB대로 어림하지만 재보지 않았다 — plan의 완료 증명에서 잰다. 언어 패키지는 FR-12대로 나눠 싣는다. 대안인
   Monaco는 몇 MB이고 VS Code의 무게를 그대로 들여 "가벼운 편집"에 맞지 않는다. → **사용자**(새 의존성 승인).
5. **기본 높이에서 칸이 낮다.** 1440×900, 도크 50%에서 약 470×400px다. 시안에서 알고 고른 안이다 — 최대화가 답이다.
6. **닫기 확인과 기존 가드의 겹침.** FR-21은 `guardUnload`(대기 중 저장 흘려보내기)와 같은 `beforeunload`에서 돈다.
   둘이 같이 걸리면 순서가 필요하다(먼저 흘려보내고 그다음 묻는다). macOS Cmd+Q가 한 번 취소되는 기존 제약(item-windows
   §5-3)이 여기도 그대로다.
7. **패널 창에는 코드 칸이 없다.** 이슈·메모·skill 창(`item-windows`)은 도크가 없어 이 칸이 서지 않는다. 그 창의
   스토어는 앱 창과 따로라 고친 버퍼를 나누지 않는다 — 문제 될 일이 없다(칸이 앱 창에만 있다).
8. **SKILL.md를 칸에서 고쳐도 skill 패널이 곧바로 따라오지 않는다.** asset 본문은 읽을 때마다 파일에서 오므로 상세를
   다시 열면 보이지만, 이름·설명(frontmatter)이 바뀐 것은 다음 스캔(run이 끝날 때·`다시 훑기`)에 반영된다.

| 질문 | 이 spec에서 |
|---|---|

| 버튼 위치 | 정해짐 — 안 A (§0) |

## 6. 비기능

- **NFR-1** 세 경계를 지킨다. 트리 만들기(경로 → 폴더), 대상 repo 판정, 편집 줄 경로 → repo 상대 경로, 줄바꿈 판정·
  되살리기는 전부 순수 함수다 — 컴포넌트와 IPC 핸들러는 그것을 부르기만 한다.
- **NFR-2** 파일을 읽는 자리는 여전히 `readRepoFile` 하나다(input-triggers NFR-2). 쓰는 자리도 하나다.
- **NFR-3** git·파일 IO는 비동기다 — 메인 프로세스의 MCP 서버를 멈추지 않는다(CLAUDE.md의 `execFileSync` 함정).
- **NFR-4** 새 접근성 이름(`파일`·`코드 칸 닫기`·`코드 칸 폭 조절`·`파일 이름으로 찾기`·`파일 목록 새로고침`·`파일 저장`·
  `고친 것 버리기`·`저장하지 않음`·`<경로> 코드 칸에서 열기`·충돌 배너의 셋·닫기 확인의 셋)이 기존 e2e와 부분 일치로
  부딪히지 않는지 전체 e2e로 본다. 특히 `파일`은 짧다 — `{ exact: true }`로 잡고, 기존의 `폴더 선택`·`사라진 파일 N`·
  `파일 · 경로` 칩과 갈리는지 본다. `저장`을 단독 이름으로 쓰지 않는다(설정 화면 e2e가 `{ name: '저장' }`을 쓴다).
- **NFR-5** 색은 토큰만, 글꼴 크기는 rem, 아이콘은 `icons.tsx`에서만(새 아이콘: 파일·새로고침·저장이 없으면 더한다).
- **NFR-6** 5만 개 파일 repo에서 칸을 열어 트리가 1초 안에 선다(접힌 폴더는 그리지 않는다).

## 7. 검증

- 단위(core): 목록에 없는 경로·repo 밖 링크·다른 workspace 저장 거부, 해시 충돌, CRLF·LF·BOM 되살리기(바이트 비교),
  섞인 줄바꿈 저장 거부, 2 MiB 경계, 지워진 파일, 쓰기 실패가 결과로 오는 것.
- 단위(renderer): 트리 만들기·정렬, 대상 repo 판정(이어 가는 대화·새 대화·기타), 편집 줄 경로 → repo 상대 경로,
  고친 버퍼 스토어(칸 닫기·대화 바꾸기·재마운트에 남음), 닫기 판정(대기 저장과 함께).
- 컴포넌트: 버튼 비활성 이유, 칸 열고 닫기·폭, 충돌 배너, 디스크 바뀜(고친 것 없음/있음/지워짐).
- 배선(App·Dock): 칸 상태가 인박스 왕복에 남음, 새 대화의 작업 디렉토리 알약을 바꾸면 칸이 따라감.
- e2e: repo를 등록하고 대화를 돌린 뒤 칸에서 파일을 열어 고쳐 Ctrl+S → 디스크 바이트 확인(CRLF 파일 포함), 열어 둔 채
  디스크를 바꾸면 따라감 · 고친 채 바꾸면 충돌 배너, 대화록 편집 줄에서 열기, 저장 안 하고 창 닫기 → 확인.
- 실제 앱 캡처(라이트·다크, 기본 높이와 최대화).
- 번들 크기 전후(plan의 완료 증명).
