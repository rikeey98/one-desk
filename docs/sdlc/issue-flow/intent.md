# Intent: 이슈 한 바퀴의 이음매를 메운다 — 어디서 시작하나 · 언제 닫히나 · 무엇을 적었나

- 출처: 대화 (2026-10-22) — "one-desk를 유저 입장에서 어떤 가치가 있는지 분석해줘" → "이슈를 잘 못 만드는 거 같아…
  이슈만 자꾸 쌓이고 일은 처리가 안 되고 있어… 뭘 해야 하고 뭐가 남았고 대화가 뭐가 끝났고 이런 게 더 잘 보이면 좋겠어" →
  "대화 시작할 때 사이드바에 선택된 repo가 기본인데 그래서 가끔 이슈의 repo와 다르게 되어 대화를 지워야 할 경우가 있었어" →
  "흐름의 문제를 처리할 걸 알려줘" → "1,2,3 처리 intent부터"

- 상태: **승인됨** (2026-10-22, spec 승인과 함께)

- 시안(참고, 범위보다 넓다): https://claude.ai/artifact/Mzjcw4dNbE2AWJJTCUPAny — 이 intent가 들이는 것은 ②·④·⑤ 보드의 일부다.
  ① 이슈 보드와 ③ 조사 버튼은 **뺀다**(아래 "범위 밖").

## 문제

사용자는 "혼자 여러 프로젝트를 돌리며 코딩 AI를 쓰는 사람"이고, 이 앱을 매일 쓴다. 아쉬움은 기능이 없어서가 아니라
**이슈 → 대화 → 마무리 한 바퀴의 이음매 셋**에서 나온다. 셋은 따로가 아니라 한 줄로 이어져 있다 — 흐릿하게 적힌 이슈는
착수가 미뤄지고, 끝난 일은 닫히지 않아 쌓이고, 쌓이니 무엇이 남았는지 안 보인다.

1. **대화가 엉뚱한 repo에서 시작된다.** 이슈 상세의 `대화 시작`을 눌러도 작업 디렉토리는 사이드바에서 고른 repo다.
   이슈는 api인데 사이드바가 web이면 web에서 돈다. 사용자는 이것 때문에 **대화를 지워야 했던 적이 있다** — 보낸 뒤에
   알면 되돌릴 길이 없다. 사용자가 꼽은 "지금 쓰면서 제일 큰 문제"다.
2. **끝난 일이 닫히지 않는다.** 대화를 끝내도 할당된 이슈는 `열림`/`진행 중` 그대로다. 이슈를 닫으려면 이슈 상세를
   찾아가 상태를 바꿔야 하는데, 그 걸음이 빠지면 이슈가 "손 안 댄 것"과 구별되지 않은 채 쌓인다. 사용자의 말로는
   "이슈만 자꾸 쌓이고 일은 처리가 안 되고 있다."
3. **이슈가 흐릿하게 적힌다.** 제목 한 줄로 던져 넣고 분류는 훑기로 미루는 것이 이 앱의 방식인데(issue-triage 설계),
   던져 넣은 한 줄이 나중에 읽으면 무엇을 하라는 것인지 모호하다. 사용자의 말로는 "글을 조리 있게 못 써서 이슈를 잘
   못 만드는 것 같다." 흐릿한 이슈는 착수도, 대화의 맥락으로 싣기도, "끝났나"를 판단하기도 어렵다.
4. **agent가 이슈를 반만 고칠 수 있다.** 대화에서 "이 이슈 정리해 줘"라고 시켜도 MCP `update_issue`는 상태·본문·분류만 받는다.
   **제목도, repo 태그도 못 고친다.** 이슈의 첫 줄이 제목이라(first-line-title) 제목이 흐릿하면 목록에서 흐릿한 채로 남는다.
   그리고 repo 태그를 못 고치니 (1)이 기대는 "이슈의 repo"를 agent가 바로잡을 수 없다. 사용자 결정(2026-10-22): "MCP가 이슈의
   모든 걸 수정할 수 있도록 해야 한다."

## 현황 (읽고 확인한 것)

- **작업 디렉토리는 `RunPanel`의 effect 하나가 정한다** (`renderer/components/RunPanel.tsx` 286–324). 순서는 "다시 실행"이
  넘긴 경로(`draftCwd`) → 사이드바에서 고른 repo(`selectedRepoId`) → 지금 값이 그 workspace의 repo면 유지 → 첫 repo.
  **담은 이슈나 할당 예정인 이슈의 repo는 이 순서 어디에도 없다.**
- **그것은 의도된 결정이었다** — conversation-issue spec FR-16 "새 대화의 작업 디렉토리는 지금 규칙 그대로다… 이슈의
  repo 태그로 정하지 않는다"(intent 제약 "규칙을 늘리지 않는다"). 그때 이 장비의 workspace는 셋 다 repo가 하나뿐이라
  두 규칙이 같은 결과를 냈다. 지금은 어긋나는 일이 실제로 생겼다.
- **이어 가는 대화는 첫 턴의 cwd를 그대로 쓴다**(`conversation.last.cwd`) — 대화를 지우지 않고 repo를 바꿀 길이 없다.
  "다시 보내기"(`runs.resume`)는 같은 대화에 같은 지시·맥락·조건을 다시 보낸다. 다른 cwd로 새 대화를 여는 길은 없다.
- **"대화 쪽에서 이슈 상태를 쓰지 않는다"도 의도된 결정이다** — conversation-issue intent 제약과 spec §1 "빠지는 것".
  이유는 둘이었다: 상세를 열어 둔 채 도크에서 대화를 보는 흐름에서 상세 밖의 쓰기가 충돌 배너를 터뜨린다(본문 설계
  §137), 그리고 **자동 완료는 틀린다**(컨텍스트가 차서 새로 시작할 때도 대화를 끝낸다).
- **그런데 상세 밖의 상태 쓰기가 이미 하나 있다** — 인박스의 `관련 이슈 닫기`(`renderer/App.tsx`의 `closeIssue` →
  `issues.update({ status: 'done' })`). 사람이 누르는 버튼이고, 충돌은 열린 상세가 낙관적 잠금으로 받는다. 그 버튼은
  할당이 아니라 **담긴** 이슈를 본다(conversation-issue §6 우려 4).
- **대화 끝내기**는 줄 끝 체크와 헤더 `⋯`의 `대화 끝내기`다(lifecycle). 끝내기는 `closed_at`을 찍고 확인을 겸한다.
- **홈의 할 일은 넷이다** — 답변 필요 · 실패·중단 · 정리 안 된 이슈 · 오래 안 본 이슈(`core/home/summary.ts`). "끝낸 대화만
  있고 이슈는 열린 것"은 어디에도 없다.
- **훑기**는 정리 안 된 이슈(`triagedAt IS NULL`)를 하나씩 넘기며 사람이 축을 고르는 화면이다. agent가 거드는 자리는 없다.
- **MCP `update_issue`는 상태·본문·분류 셋(source·kind·priority)만 받는다**(`core/mcp/tools.ts` 248–270). 제목과 repo 태그가 없다.
  그런데 **저장소의 `UpdateIssueInput`은 이미 `title`·`repoIds`를 받는다**(`shared/models.ts` 315) — 화면의 상세가 그것으로 쓴다.
  막힌 것은 MCP의 입력 스키마 한 겹이다. `create_issue`는 이미 `repoIds`를 받는다. 이슈를 지우는 MCP 도구는 없다.
- MCP의 쓰기는 낙관적 잠금을 타지 않는다(`update`이지 `updateIfUnchanged`가 아니다). 열린 상세는 다음 저장 때 충돌 배너로 받는다 —
  본문·상태는 지금도 그렇다. 파생 필드(`closedAt`·`triagedAt`·`startedAt`)는 저장소가 정하고, `seenAt`은 agent가 못 올리게 따로 있다.
- **읽기 전용 run에는 MCP 쓰기 도구가 아예 등록되지 않는다**(`tools.ts` 227 — "파일은 못 고치는데 이슈 상태는 바꿀 수 있다면
  '읽기 전용'을 신뢰할 수 없다", 설계 §8). 읽기 도구(`list_issues`·`get_issue` 등)는 남는다.
- MCP 쓰기는 고치는 즉시 저장된다. "제안"이라는 중간 상태가 없다.
- 이슈의 첫 줄이 제목이다(first-line-title, `splitTitleBody`).

## 원하는 결과

**(1) 대화는 그 이슈의 repo에서 시작한다.**
- 이슈에서 `대화 시작`을 누르면 작업 디렉토리가 **그 이슈의 repo**다 — 사이드바에서 무엇을 골랐든. 이슈에 repo가 둘 이상이면
  처음 한 번 고르게 하고, 하나도 없으면 지금 규칙(사이드바)을 따른다.
- 새 대화 칸에 이슈를 담거나 할당하면 작업 디렉토리가 그 repo로 따라간다. **사람이 알약으로 직접 고른 값은 이긴다** — 다만
  이슈의 repo와 다르면 보내기 전에 그 사실이 보인다.
- 이미 보낸 뒤에 알았으면 **대화를 지우지 않고** 같은 지시·맥락·조건으로 다른 repo에서 새 대화를 시작할 수 있다. 옛 대화는
  끝낸 대화로 남고, 이슈 할당은 새 대화로 옮겨 간다.

**(2) 끝낸 대화는 이슈를 닫을 기회를 준다.**
- 할당된 이슈가 열린 대화를 끝낼 때 **"이슈도 완료할까요?"를 묻는다.** 답은 사람이 한다 — 자동으로 닫지 않는다.
- 그 자리에서 답하지 않았거나 놓친 것은 **홈의 할 일 다섯째 줄**("끝났는데 열린 이슈")로 남고, 거기서 `완료 처리` 한 번으로 닫는다.
  홈 배지에도 센다. 이슈 목록에서도 그 이슈가 그런 상태임이 보인다.

**(3) 흐릿한 이슈를 agent가 다듬어 제안하고, 사람이 고른다.**
- 훑기에서 정리 안 된 이슈를 agent에게 넘기면, 이슈마다 **다시 쓴 제목·본문, 분류 축, 완료 조건**을 제안받는다. 같은 말을 하는
  이슈는 **합칠 후보**로, 할 일이 아닌 것은 **메모로 옮길 후보**로 짚는다.
- **사람이 수락하기 전에는 아무것도 바뀌지 않는다.** 원문은 지우지 않는다.
- 다듬어진 이슈의 완료 조건은 (2)에서 "정말 끝났나"를 판단하는 근거가 된다.

**(4) agent는 MCP로 이슈의 사람이 고칠 수 있는 것을 전부 고칠 수 있다.**
- `update_issue`가 **제목·본문·상태·분류 셋·repo 태그**를 받는다 — 상세 화면에서 사람이 고칠 수 있는 것과 같은 목록이다.
- 파생 필드(`closedAt`·`triagedAt`·`startedAt`·`seenAt`·`updatedAt`)는 여전히 저장소가 정한다. agent가 넘길 수 없다.
- **삭제는 들지 않는다**(2026-10-22, 사용자 결정). MCP에 이슈를 지우는 도구를 두지 않는다.
- 규칙은 사람이 쓸 때와 같다 — repo 태그는 같은 workspace 소속만, 제목은 비울 수 없다, 상태가 바뀔 때만 시각을 찍는다.
- 그래서 (3)을 기다리지 않아도 대화에서 "이 이슈 제목이랑 repo까지 정리해 줘"가 된다. (3)은 그것을 **훑기에서 여러 개를, 수락을 받고**
  하는 길이다.

## 뒤집는 결정

- **conversation-issue FR-16 "작업 디렉토리는 사이드바 규칙 그대로"** → 이슈의 repo가 사이드바보다 먼저다. 근거: 그 결정은 repo가
  하나뿐인 workspace에서 내려졌고, 둘 이상이 되자 실제로 대화를 지우는 사고가 났다. 사이드바 거름이 "보기만 바꾼다"
  (dock-repo-sections FR-9)는 그대로다 — 바뀌는 것은 새 대화 칸의 **기본값**뿐이다.
- **conversation-issue "대화 쪽에서 이슈 상태를 쓰지 않는다"** → **사람이 누른 버튼으로는 쓴다.** 그 결정이 막으려던 둘 중
  "자동 완료는 틀린다"는 그대로 지킨다(묻기만 한다). "충돌 배너"는 인박스의 `관련 이슈 닫기`가 이미 같은 쓰기를 하고 있고,
  열린 상세는 낙관적 잠금으로 받는다. **대화를 시작할 때 자동으로 `진행 중`으로 바꾸는 것은 여전히 하지 않는다.**

## 영향 범위

- **사용자**: 이 앱을 쓰는 모든 사람(현재 한 명, 작성자).
- **시스템** (추정 — spec에서 확정):
  - (1) `RunPanel`의 cwd 결정 순서, 이슈 상세 → 도크로 가는 `대화 시작` 배선(`App`·`Dock`), 대화 헤더 `⋯`의 새 동작, core의 "다른
    cwd로 새 대화"(재료는 `runs.resume`과 같다).
  - (2) 대화 끝내기 경로(`Dock`의 줄 끝·헤더 메뉴), `core/home/summary.ts`의 할 일 종류 하나, 홈 화면, 이슈 목록의 표식.
  - (3) 훑기 화면, agent에게 넘기는 지시와 돌아온 제안을 읽는 길, 제안 화면, 수락한 제안의 이슈 쓰기(화면의 `updateIfUnchanged`).
  - (4) `core/mcp/tools.ts`의 `update_issue` 입력 스키마와 그 테스트. 저장소·IPC·렌더러는 바뀌지 않는다(이미 받는다). MCP 도구 설명이
    바뀌므로 `e2e/mcp.e2e.ts`의 기대도 본다.
- **건드리지 않는 것**: 이슈·메모의 데이터 모델(다대다 repo 태그, 공통 이슈), 대화의 저장 모양(뿌리의 `issue_id`), 인박스·배지 판정
  표(`INBOX_RULES`), 어댑터·권한·큐, MCP 도구의 권한 경계.

## 제약

- `core/`는 `electron`을 모르고, `renderer/`는 `core/`를 모르며, IPC 핸들러는 얇다.
- **이슈 상태는 사람이 누른 버튼으로만 바뀐다** — 대화가 끝나는 것만으로, agent의 제안만으로 바뀌지 않는다.
- **agent의 제안은 저장되기 전까지 이슈를 고치지 않는다.** 제안을 받는 run은 **읽기 전용**이다 — 읽기 전용에는 MCP 쓰기 도구가
  등록되지 않으므로(현황) "고치지 않는다"가 지시문이 아니라 구조로 지켜진다. (4)가 쓰기 도구를 넓혀도 이 경계는 그대로다.
- **(4)는 권한 경계를 넓히지 않는다.** 쓰기 도구가 받는 필드가 늘 뿐, 쓰기 도구가 서는 권한 단계(편집 허용·전체 허용)와 workspace 소속
  확인은 그대로다.
- **대화 기록을 지우지 않는다.** repo를 바꿔 다시 시작해도 옛 대화는 남는다.
- **issue/memo 대칭은 공통 필드에서 끝난다** — 다듬기·완료 조건·합치기는 이슈 전용이다. 메모로 옮기는 것은 이슈를 지우고 메모를
  만드는 것이지 메모에 이슈 기능을 더하는 것이 아니다.
- 짧은 라벨을 새로 붙이면 기존 e2e의 부분 일치가 깨진다(`완료`·`다시 시작`·`다듬기`) — 새 라벨은 e2e를 먼저 돌려 본다.
- 홈 배지와 인박스 배지는 다른 수다 — 새 할 일은 **홈 배지에만** 센다.

## 성공 기준

- 사이드바에서 web을 고른 채 api 이슈의 `대화 시작`을 누르면 입력부의 작업 디렉토리가 api이고, 그대로 보낸 첫 턴의 cwd가 api다.
- 새 대화 칸에서 알약으로 web을 고르고 api 이슈를 담으면, 보내기 전에 어긋남이 보이고 한 번에 api로 바꿀 수 있다.
- web에서 시작해 버린 대화에서 "다른 repo에서 다시 시작"을 누르면 api에서 같은 지시로 새 대화가 시작되고, 옛 대화는 끝낸 대화로
  남으며, 이슈 상세의 대화 버튼이 새 대화를 연다.
- 할당된 이슈가 열린 대화를 끝내면 "이슈도 완료할까요?"가 뜨고, 수락하면 이슈가 `완료`, 거절하면 이슈는 그대로이고 홈의 할 일에 그
  이슈가 선다. 홈에서 `완료 처리`를 누르면 그 줄이 빠진다.
- 대화를 시작하거나 끝내는 것만으로 이슈 상태가 바뀌는 경로가 없다.
- 훑기에서 이슈 셋을 agent에게 넘기면 셋의 제안이 원문과 나란히 보이고, 수락한 것만 바뀌고 나머지는 원문 그대로다. 제안을 받는 run이
  이슈를 직접 고치지 못한다.
- 편집 허용 대화에서 agent가 MCP로 이슈의 제목과 repo 태그를 바꾸면 화면의 이슈 목록·상세에 그대로 보인다. 다른 workspace의 repo를
  태그하려 하면 거부된다. 읽기 전용 대화에서는 여전히 어떤 이슈도 고치지 못한다.
- `pnpm test` · `pnpm typecheck` · `pnpm lint` · `pnpm test:e2e` 전부 통과.

## 진행 방식

intent 하나에 spec → plan → 구현을 **둘로** 돈다(code-editor와 같은 방식).

- **첫째 사이클 — (1) + (2) + (4).** 셋 다 작다. (1)이 사용자가 꼽은 가장 큰 문제라 먼저다. (4)는 입력 스키마 한 겹이라 가장 싸고,
  (1)이 기대는 이슈의 repo 태그를 agent가 바로잡게 해 준다.
- **둘째 사이클 — (3).** 제안을 어디에 두고 어떻게 받는지가 새 결정이라 크다. 첫째를 몇 주 써 본 뒤에 착수해도 된다.

## 범위 밖

- **이슈 보드 화면**(시안 ①). 볼 곳이 여섯이 되기 때문이다 — 홈·인박스·리포트·도크·이슈 패널. 보드를 들이려면 홈과 합칠 방법부터
  정해야 한다. (2)의 홈 할 일과 이슈 목록 표식이 그 자리를 먼저 채운다.
- **이슈 조사 버튼**(시안 ③) — 사용자가 "자동 조사는 위험하다"고 했고, 버튼 방식은 (3) 뒤에 따로 본다.
- **MCP로 이슈를 지우는 것**(2026-10-22, 사용자 결정).
- **이슈를 자동으로 처리하는 것** — 사용량과 검토 부담이 이슈 더미를 인박스 더미로 옮길 뿐이다.
- **대화를 시작할 때 이슈를 자동으로 `진행 중`으로 바꾸는 것.**
- 인박스 `관련 이슈 닫기`가 할당 기준으로 바뀌는 것(conversation-issue §6 우려 4) — (2)의 spec에서 같이 볼 수는 있지만 이 intent의 약속은 아니다.
