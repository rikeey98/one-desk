# Intent: 대화에 이슈를 할당한다

- 작성자: 권용현
- 상태: 승인됨 (2026-10-02)
- 작성일: 2026-10-02

## 문제

**"이 이슈를 푸는 대화"가 앱 어디에도 없다.** 2026-10-02 사용자(요약): "하나의 대화에서 하나의
이슈를 해결하려고 그렇게 쓰고 있다." 쓰는 방식은 앱과 잘 맞는다 — 제목 폴백이 담은 이슈 이름을
고르고, 대화끼리는 병렬로 돈다. 그러나 그 약속을 앱이 모른다. 이슈와 대화를 잇는 것은 "그 턴에
맥락으로 담았다"는 기록뿐이다.

1. **이슈에서 그 이슈의 대화로 가는 길이 없다.** 이슈 상세에는 대화 표시가 없고, 도크 목록에서
   제목으로 찾아야 한다.
2. **무엇이 이 대화의 이슈인지가 추론이다.** "담은 적 있다"로 이으면 참고로 담은 대화도 그 이슈의
   대화가 되고, 첫 턴에 담는 것을 잊으면 제목이 repo 이름이나 첫 지시로 떨어진다.

같은 날 처음에는 이슈를 repo 아래로 옮기는 구조 변경을 검토했다(`docs/sdlc/repo-issues/`, 보류).
연결은 명확해지지만 마이그레이션·보관함·MCP·훑기·메모 대칭까지 바뀌고, 사용자가 "이런 규칙들이
어렵다"고 했다. 그리고 **이 장비의 workspace는 셋 다 repo가 하나뿐이라** "repo 아래 이슈"와
"workspace 아래 이슈"가 지금은 같은 말이다. 틈 둘은 구조가 아니라 **대화에 칸 하나**로 풀린다.

## 현황 (읽고 확인한 것)

- **이슈와 대화를 잇는 것은 `run_context_item`뿐이다.** `item_id`에 외래키가 없는 것은 의도다
  (`core/db/schema.ts:170` — 이슈를 지워도 과거 run의 첨부 기록이 사라지지 않게).
- **제목은 폴백 사다리다** — 사용자가 붙인 이름 > 담긴 이슈·메모 > repo > 첫 지시
  (`renderer/conversation.ts:126`, lifecycle FR-11). 이슈를 첫 턴에 담아야 제목이 이슈 이름이 된다.
- **대화의 저장 속성은 뿌리 행에만 있다** — `title`·`closed_at`. 이어지는 턴에도 칸은 있고 null일
  뿐이라 저장소의 `assertRoot`(`core/db/repositories/run.ts:227`)가 유일한 방어선이다.
- **run을 잇는 칸은 외래키 없는 text로 더해 왔다** — `root_run_id`가 `ALTER TABLE ADD COLUMN`
  한 줄이었다(`drizzle/0002`). `run` 테이블을 다시 만들면 `run_context_item`의 cascade가 탄다.
- **새 대화의 작업 디렉토리는 사이드바에서 고른 repo를 따라간다**(`RunPanel.tsx:86`, v0.19.2).
- **상태 편집은 상세에서만 한다**(`2026-08-14-issue-memo-body-design.md:137`). 상세 밖의 쓰기는 열린
  상세의 기대값을 낡게 만들어 사용자 자신의 클릭에 충돌 배너를 띄운다.
- **이슈 상세의 메타는 한 줄이다** — 본문을 밀지 않으려는 결정이다. 오른쪽 끝에 시각과 id 알약이 있다.
- **패널 창(별도 창)에는 도크가 없다.** 그래서 창에는 맥락 담기도 없다(패널의 `context` prop이 선택이고
  App만 넘긴다, item-windows FR-8).
- **인박스의 "관련 이슈 닫기"는 그 대화에 담긴 이슈를 본다.** 인박스의 "대화 열기" 버튼 이름이 이미 있다.
- **이 장비의 실제 데이터**(2026-10-02, 읽기 전용으로 셈): workspace 3개에 repo가 하나씩, 이슈 1개,
  대화 5개, 이슈를 담은 대화 0개.
- 마이그레이션은 지금 `0009`까지다.

## 원하는 결과

- **대화에 "이슈" 칸이 하나 있다.** 비어 있어도 된다 — 이슈가 없는 대화가 "공통"이다. 대화 하나에
  이슈는 많아야 하나, 이슈 하나에 대화는 여럿일 수 있다(인수인계·agent 바꾸기·다시 시도).
- **이슈에서 그 이슈의 대화로 한 번에 간다.** 대화가 없으면 `대화 시작`, 하나면 `대화 열기`(상태 점과
  함께), 여럿이면 `대화 N`을 눌러 고른다. 평소처럼 하나뿐이면 화면도 하나만 보인다.
- **이슈에서 시작한 대화는 처음부터 그 이슈가 할당돼 있다.** 제목이 이슈 이름이 되고, 첫 턴에
  담기를 잊을 일이 없다.
- **대화에서 그 이슈로 한 번에 간다.** 대화 헤더에 할당된 이슈가 보이고, 누르면 이슈 상세가 열린다.
  상태는 거기서 바꾼다. 할당·해제도 헤더에서 한다.
- **컨텍스트가 차면 같은 이슈로 새 대화를 이어 간다.** 이슈 본문에 진행 상황을 정리하고 → 대화를
  끝내고 → 이슈에서 대화를 다시 시작한다. 따로 기능이 없어도 된다.

## 영향 범위

- **사용자**: 이 앱을 쓰는 모든 사람(현재 한 명, 작성자).
- **시스템**:
  - `core/db/schema.ts` + `drizzle/0010` — run(뿌리)에 칸 하나. **컬럼 추가만.**
  - `core/db/repositories/run.ts` — 할당·해제, `assertRoot`.
  - `core/execution.ts` — 이슈를 할당한 채로 새 대화를 시작하는 길.
  - `core/index.ts` + IPC + preload + `shared/client.ts` — 할당 통로.
  - `renderer/conversation.ts` — 제목 사다리에 할당된 이슈, 이슈별 대화 찾기.
  - `renderer/components/ConversationHeader.tsx`·`Dock.tsx`·`RunPanel.tsx` — 할당된 이슈 표시·할당·해제,
    이슈가 정해진 새 대화 칸.
  - `renderer/components/IssueDetail.tsx`·`renderer/App.tsx` — 이슈 상세의 대화 버튼과 그 배선.
  - e2e — 이슈에서 대화 시작·열기, 헤더에서 이슈 열기.
- **건드리지 않는 것**: 이슈·메모·repo의 모델(태그 다대다 그대로, 공통 이슈 그대로), 훑기, MCP의
  이슈·메모 도구, repo 삭제, 맥락 담기 칩, 인박스·배지 판정, 어댑터·권한·큐.

## 제약

- `core/`는 `electron`을 모르고, `renderer/`는 `core/`를 모르며, IPC 핸들러는 얇다.
- **`run` 테이블을 다시 만들지 않는다.** `ALTER TABLE ADD COLUMN`만. 외래키를 붙이면 drizzle이
  테이블 재생성 SQL을 낼 수 있으니 생성된 SQL을 반드시 읽는다 — 선례(`root_run_id`)는 외래키 없는 text다.
- **할당은 뿌리에서만 의미가 있다.** `title`·`closed_at`과 같은 방어(`assertRoot`)를 받는다.
- **이슈의 상태를 대화 쪽에서 쓰지 않는다** — 헤더에서 바꾸지도, 대화를 시작·끝낼 때 자동으로
  바꾸지도 않는다. 이슈 상세를 열어 둔 채 도크에서 대화를 보는 것이 바로 이 흐름이라, 상세 밖의
  쓰기가 충돌 배너를 가장 잘 터뜨린다(본문 설계 §137).
- **규칙을 늘리지 않는다.** 할당할 수 있는 이슈를 repo로 거르지 않는다 — 같은 workspace의 이슈면 된다.
- **기록을 지우지 않는다.** 이슈를 지우면 그 대화는 공통 대화가 될 뿐 대화는 남는다.
- 짧은 라벨을 새로 붙이면 기존 e2e의 부분 일치가 깨진다 — 새 라벨은 e2e를 먼저 돌려 본다.
  `대화 열기`는 인박스 버튼 이름과 같다.

## 성공 기준

- 이슈 상세에서 `대화 시작`을 누르면 그 이슈가 할당된 새 대화 칸이 열리고, 첫 턴을 보내면 대화 제목이
  이슈 이름이다.
- 그 뒤 이슈 상세의 버튼이 `대화 열기`가 되고, 누르면 도크에서 그 대화가 열린다.
- 같은 이슈로 대화를 하나 더 시작할 수 있고, 이슈 상세에서 둘 다 찾아 열 수 있다.
- 대화 헤더에 할당된 이슈가 보이고, 누르면 그 이슈 상세가 열린다. 헤더에서 해제하면 공통 대화가 된다.
- 이슈를 지워도 대화는 남고 공통 대화가 된다.
- 이슈·메모·repo·훑기·MCP 이슈 도구의 동작은 바뀌지 않는다.
- 기존 DB를 열면 마이그레이션 `0010`이 한 번 돌고, 기존 대화가 그대로 보인다.
- `pnpm test` · `pnpm typecheck` · `pnpm lint` · `pnpm test:e2e` 전부 통과.

## 결정 (2026-10-02, 사용자)

- **구조는 느슨한 그대로, 연결만 명시한다.** 이슈를 repo 아래로 옮기는 안(`docs/sdlc/repo-issues/`)은
  보류한다. 다시 꺼낼 신호: workspace 하나에 repo가 여럿 붙고 repo마다 이슈가 쌓여 "이 이슈는 어느
  repo 일이지?"가 헷갈리기 시작할 때.
- **대화에 이슈는 0~1개, 이슈에 대화는 여럿.** 막으면 할당을 풀고 다시 거는 단계와 오류가 하나씩 는다.
- **"공통"은 이슈가 할당되지 않은 대화를 부르는 말이다.**
- **규칙은 적을수록 좋다.** 사용자가 고르게 하지 말고 합리적인 기본값으로 정한다.

## 이번 범위에서 뺀 것

- **대화 헤더에서 이슈 상태 바꾸기, 대화 시작 때 자동으로 "진행 중", 대화를 끝낼 때 자동 완료.**
  셋 다 상세 밖의 상태 쓰기다(위 제약). 자동 완료는 게다가 틀린다 — 컨텍스트가 차서 새로 시작하거나
  접근을 접을 때도 대화를 끝낸다.
- **이슈 본문이 바뀌었다는 `수정됨` 표시.** `updatedAt`은 상태·축·agent의 MCP 편집에도 오르므로
  오탐이 많고, 본문만의 시각을 두려면 칸이 하나 더 든다. 당분간 "고쳤으면 다시 담는다".
- **사이드바 표시, repo 보관함, 이슈의 repo 하나 제한** — 보류한 구조 변경의 몫이다.

- [ ] **제목 사다리에서 할당된 이슈의 자리.** (추정: 사용자가 붙인 이름 다음, 담긴 이슈·메모 앞.)

      — 이 장비에는 해당 대화가 0개이고, 규칙이 하나 준다.)

      "없는 이슈 = 공통"으로 볼지(`run_context_item`의 방식).
- [ ] **이슈에서 시작할 때 작업 디렉토리.** (추정: 지금 규칙 그대로 — 사이드바에서 고른 repo. 입력부의
      알약에서 바꾼다.)
- [ ] **`대화 N`의 목록 모양.** 메타 줄을 두 줄로 만들지 않는 선에서. 끝낸 대화를 포함하는지, 순서.
- [ ] **패널 창의 이슈 상세.** (추정: 버튼을 숨긴다 — 창에 도크가 없고, 맥락 담기도 같은 이유로 없다.)
- [ ] **"다시 실행"(새 대화)은 할당을 따라가는가?**
- [ ] **인박스의 "관련 이슈 닫기"는 담긴 이슈와 할당된 이슈 중 무엇을 보는가.**
- [ ] **MCP `list_conversations`·`get_conversation`에 할당된 이슈를 싣는가.** 기간 정리("이번 주에 한 일")가
      대화와 이슈를 묶어 말할 수 있게 된다.
