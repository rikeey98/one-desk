# Intent: 지시를 등록해 두면 정해진 주기마다 agent가 저절로 돈다 — 정기 실행

- 출처: 대화 (2026-11-02) — "리포트 밑에 새로운 기능을 추가하고 싶어. 주기적으로 … 실행시킬수 있는거야. 주기적으로 llm 응답을
  실행시키는거지"
- 작성자: 권용현 (초안: Claude)
- 상태: **승인됨** (2026-11-02, 사용자 "승인, spec 작성해줘") — spec은 `spec.md`
- 관계: 전체 설계 §3("이번 스펙에서 제외 — 자율 실행 / 스케줄링 … 별도 스펙으로 다룬다")·§14("자율 실행")가 미뤄 둔 자리다.
  그 둘이 그린 것은 "이슈를 등록하면 스케줄러가 가져가 처리"와 "앱이 닫혀 있어도 도는 데몬"인데, **이 intent는 둘 다 아니다** —
  사람이 쓴 지시를 시각에 맞춰 보내는 것이고, 앱이 떠 있을 때만 돈다(아래 "정해진 것").

## 정해진 것 (2026-11-02, 사용자)

- **진입점은 사이드바의 리포트 아래다.**
- **대화 방식은 등록마다 고른다** — `매번 새 대화` 또는 `한 대화를 이어 감`.
- **앱이 꺼져 있던 동안 놓친 실행은 다음에 켤 때 한 번만 돈다** — 놓친 횟수와 상관없이 한 번. 백그라운드 데몬·트레이는 만들지 않는다.
- **주기는 프리셋과 cron 둘 다** — 기본은 프리셋(매일 · 평일 · 매주 ○요일 · N시간마다, 시각 HH:MM), 고급으로 cron 식.
- **권한은 셋 다 고를 수 있되, 전체 허용은 확인을 거친다** — workspace 기본값 절과 같은 모양(경고 문장 + `ConfirmButton`, 전체 허용으로
  "올릴 때"만 묻는다).

## 문제

같은 지시를 주기마다 손으로 보내고 있다 — "어젯밤 실패한 CI를 훑어 줘", "열린 이슈를 요약해 메모로 남겨 줘", "의존성 업데이트가
나왔나 봐 줘" 같은 것. 지금 one-desk의 모든 run은 사람이 실행 버튼을 눌러야 시작한다(`runs.start`·`runs.resume`, 홈의 새 대화 카드도
App이 사람의 클릭으로 부른다). 시각이 되면 앱이 대신 보내 주는 길이 없다.

## 현황 (읽고 확인한 것)

- **실행 입력은 이미 직렬화할 수 있는 값 하나다** — `StartRunInput`(`shared/models.ts` 494: workspace · agent · 모델 · effort · cwd ·
  권한 · 지시 · 맥락 ref · 이슈)과 `ResumeRunInput`(대화 id + 같은 것). 등록해 둔 값을 시각에 그대로 넘기면 run이 된다.
- **실행은 core 한 자리다** — `core/execution.ts`의 `start`(582)·`resume`(624). 그 뒤의 큐(동시 실행 상한 `settings.concurrencyLimit()`)·
  MCP 토큰·로그·인박스·배지는 사람이 누른 run과 같은 길을 탄다. 새 실행 경로를 만들 필요가 없다.
- **core에 시계로 움직이는 것이 없다** — 타이머는 터미널 출력 모으기·취소 유예·타임아웃 같은 짧은 것뿐이다. 주기 판정은 새로 생긴다.
- **부팅 때 `runs.reapStale()`**(`core/index.ts` 342)이 지난 실행의 running 행을 interrupted로 내린다. 놓친 실행을 켤 때 돌리려면 그 뒤여야
  한다.
- **앱은 창을 닫으면 끝난다** — 트레이가 없고, 종료 정리는 `will-quit`의 `core.shutdown()`이다(`electron/main.ts` 138).
- **"예약"이라는 말은 이미 쓰였다** — 대화에서 앞 턴이 도는 동안 이어 보낸 지시(입력칸 위 `예약` 칩, `예약 취소`). 이 기능을 "예약"이라고
  부르면 같은 화면에서 두 뜻이 부딪힌다. 이 문서는 **정기 실행**이라고 부른다(이름은 spec에서 e2e 부분 일치와 함께 확정).
- **"마지막으로 보낸 곳"(`home.lastTarget`)은 사람이 보낸 것만 찍는다** — 자동 재시도·MCP가 만든 run은 찍지 않는다(home spec FR-7).
  정기 실행도 찍지 않아야 한다.
- **core는 시간대를 모른다**는 것이 지금까지의 규칙이다 — 홈의 "오늘" 경계는 렌더러가 넘긴다(home spec FR-5). 정기 실행은 사람이 없을 때
  시각을 계산해야 하므로 이 규칙과 부딪힌다(아래 미해결).

## 원하는 결과

- 사이드바의 리포트 아래 `정기 실행`이 등록 목록을 보인다 — 줄마다 이름 · workspace/repo · 주기(사람 말로 — "평일 09:00") · 다음 실행
  시각 · 마지막 결과(상태 점 + 그 대화 열기) · 켜고 끄기.
- 등록은 실행 패널이 받는 것과 같은 것 — workspace · 작업 디렉토리(repo) · agent · 모델 · effort/variant · 권한 · 지시 · 맥락(이슈·메모·asset) —
  에 **주기**와 **대화 방식**을 더한 것이다.
- 시각이 되면 앱이 그 지시를 보낸다. 결과는 평소와 같이 도크의 대화·인박스에 쌓이고, 등록 줄에서 그 대화로 간다. `매번 새 대화`면
  그 등록이 만든 대화들이 등록 아래 모여 보인다.
- `지금 실행`으로 시각을 기다리지 않고 한 번 돌릴 수 있다(시험용).
- 앱을 켜면 꺼져 있던 동안 놓친 등록마다 한 번 돈다. 무엇이 왜 돌았는지(놓쳐서 돈 것인지) 등록 줄에 남는다.

## 영향 범위 (추정 — spec에서 확정)

- **DB**: 등록을 담는 테이블 하나와, 어떤 대화가 어느 등록에서 나왔는지(`run`의 뿌리 행에 등록 id, 또는 등록 쪽 기록) — **마이그레이션
  하나**.
- **core**: 주기 계산(프리셋·cron → 다음 시각), 깨어나 확인하는 타이머, 부팅 시 놓친 것 판정, `execution.start`/`resume` 호출. 앱 종료 때
  타이머 정리.
- **IPC·preload·`OneDeskClient`**: 등록 CRUD, 켜고 끄기, 지금 실행, 다음 시각 미리보기(입력한 cron이 언제 도는지).
- **renderer**: 사이드바 진입점, 목록·편집 화면(실행 패널의 알약·`ModelField`·권한 표를 재사용), App 배선.
- **건드리지 않는 것**: 실행 파이프라인(큐·어댑터·MCP·판정), 인박스·배지 표(`INBOX_RULES`), 권한 정책 생성, 대화 데이터 모델.

## 제약

- **앱이 떠 있을 때만 돈다.** 데몬 분리(전체 설계 §14)는 이 작업의 범위가 아니다. 앱을 켠 순간의 한 번이 그 대가를 메운다.
- **정기 실행은 사람의 실행과 같은 길을 탄다** — 같은 큐 상한, 같은 권한 정책, 같은 MCP 경계(그 workspace만). 정기 실행 전용의 우회로를
  만들지 않는다.
- **생성하는 권한 설정에 `ask`가 없다는 규칙은 더 무겁다** — 사람이 없는 시각에 돈다.
- **같은 등록이 겹쳐 돌지 않는다.** 앞 실행이 아직 끝나지 않았으면 이번 것은 건너뛴다(쌓지 않는다). `한 대화를 이어 감`은 어차피
  "대화당 예약 하나"(`RunQueue`의 `groupKey`)에 막힌다.
- **놓친 것을 몰아서 돌리지 않는다** — 일주일 꺼 두었다 켜도 등록마다 한 번.
- 세 경계(`core/`는 electron 없음 · renderer는 core 없음 · IPC는 얇다). 전원 이벤트(`powerMonitor`)가 필요하면 main이 core에 알린다.
- App이 내리는 prop은 필수, 짧은 새 이름은 기존 e2e와 부분 일치를 본다(`실행`·`예약`·`취소`·`대화`는 이미 많이 걸린다).
- 사용량이 든다 — 저절로 도는 것이므로 화면이 다음 실행 시각과 켜짐 여부를 늘 보인다.

## 범위 밖

- 앱이 닫혀 있어도 도는 데몬, 트레이 상주, OS 작업 스케줄러 등록, 로그인 시 자동 시작.
- 이슈를 등록하면 agent가 알아서 가져가 처리하는 자율 큐(전체 설계 §3의 그것) — 별도.
- agent가 MCP로 정기 실행을 만들거나 고치는 것.
- 결과에 따라 분기하는 흐름(성공하면 B를 돌린다 등), 여러 단계 파이프라인.
- OS 알림(전체 설계 §3이 뺀 것 그대로).

## 미해결 질문 (spec에서 다룬다)

- [ ] **이름.** `정기 실행`은 `실행`을 품는다 — 기존 e2e의 버튼 `{ name: '실행' }`은 전부 exact이고 exact가 아닌 넷은 설정의 `tab`이라
  사이드바 버튼과 부딪히지 않는다(2026-11-02 grep). spec에서 새로 붙일 이름까지 다시 훑는다.
  (가정: 사이드바 `정기 실행`, 등록 하나는 "정기 실행 하나")
- [ ] **시간대.** core가 다음 시각을 계산해야 한다. (가정: 등록에 IANA 시간대를 함께 저장하고 — 렌더러가 만들 때의 시간대 — core는
  그 값으로 계산한다. "core는 시간대를 모른다"를 "core는 **장비의** 시간대를 묻지 않는다"로 좁힌다.)
- [ ] **cron 해석.** 의존성을 들일지 직접 쓸지. (가정: 5필드 표준 cron만, 직접 쓴 순수 함수 — 프리셋도 같은 함수로 바꿔 한 길로 계산한다.)
- [ ] **깨어나는 방식.** (가정: 1분마다 확인하는 타이머 하나 + 절전에서 깨면(`powerMonitor` `resume`) 즉시 확인. 절전 중 놓친 것도 "켤 때
  한 번"과 같은 규칙.)
- [ ] **맥락은 언제 읽나.** (가정: 실행하는 그 시각에 다시 읽는다 — 이슈 본문이 바뀌었으면 바뀐 것이 실린다. 지워진 항목은 빼고 등록
  줄에 표시.)
- [ ] **`한 대화를 이어 감`에서 앞 턴이 답변 필요로 멈춰 있으면.** (가정: 이어 보내지 않고 건너뛴다 — 사람의 답을 기다리는 대화에 기계가
  끼어들지 않는다. 세션이 없어 이을 수 없으면 실패로 남긴다.)
- [ ] **연속 실패.** (가정: N번 연속 실패하면 저절로 끈다 — 고장 난 등록이 매시간 사용량을 쓰지 않게. N은 spec에서.)
- [ ] **인박스.** 매시간 도는 등록이 인박스를 채운다. (가정: 평소와 같은 규칙 — 성공은 배지에 세지 않고 목록에만. 넘치면 spec에서 다시
  본다.)
- [ ] **workspace·repo를 지우면.** (가정: 그 등록도 지운다 — cascade. repo만 지워졌으면 등록을 끄고 표시.)
- [ ] **홈에 무엇을 보이나.** (가정: 도는 정기 실행은 이미 "지금 돌고 있는 것"에 보인다. "오늘 예정"은 1차에 넣지 않는다.)

## 성공 기준

- `평일 09:00`, 읽기 전용, "열린 이슈를 요약해 줘"를 등록하고 앱을 켜 두면 다음 평일 09:00에 새 대화가 생기고 인박스에 결과가 뜬다.
  등록 줄의 마지막 결과가 그 대화를 연다.
- 같은 등록을 켜 둔 채 앱을 끄고 이틀 뒤 켜면 정확히 한 번 돌고, 등록 줄이 "놓쳐서 실행"을 말한다.
- 전체 허용으로 바꾸려 하면 경고와 두 번 누르기를 거쳐야 저장된다.
- cron `*/30 * * * *`를 넣으면 저장 전에 다음 세 번의 실행 시각이 보인다.
