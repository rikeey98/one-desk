# Intent: 탭 기반 설정 화면

- 작성자: 권용현
- 상태: 승인됨 (2026-09-19)
- 작성일: 2026-09-19

## 문제

**설정값은 이미 여덟 개인데 화면에서 바꿀 수 있는 것은 셋뿐이고, 그 셋조차 두 군데로
흩어져 있다.** 나머지는 앱을 끄고 SQLite를 직접 열어야 바뀐다.

| 설정 | 저장 위치 | 읽는 코드 | 지금 바꾸는 법 |
|---|---|---|---|
| 글로벌 asset 경로 (claude) | `app_setting` | asset 스캔 | 설정 화면 |
| 글로벌 asset 경로 (opencode) | `app_setting` | asset 스캔 | 설정 화면 |
| 동시 실행 상한 | `app_setting` | `core/runner/queue.ts` | 도크의 슬롯 표시기 — 설정 화면이 아니다 |
| workspace 기본 agent | `workspace.default_agent_kind` | `RunPanel.tsx:45` | SQL |
| workspace 기본 권한 | `workspace.default_permission` | `RunPanel.tsx:110` | SQL |
| workspace 기본 모델 (claude·opencode) | `workspace.default_model_*` | **아무도 읽지 않는다** | 없음 |
| claude·opencode 실행 파일 경로 | `workspace.claude_path`·`opencode_path` | `core/runner/agentPath.ts` | SQL |
| repo 경로 | `repo.path` | 실행 cwd, asset 스캔 | SQL 또는 삭제 후 재등록 |

### 이것이 문제라는 증거

**2026-09-19, 기본 agent를 OpenCode로 바꾸는 데 SQL이 필요했다.** 실행 패널의 agent
드롭다운은 `workspace.defaultAgentKind`를 읽는데 그 값을 쓰는 화면이 없다. 설정 하나를
바꾸려고 DB 파일을 여는 것은 정상이 아니다.

**문서가 그 우회로를 정식 절차로 적어 두고 있다.** `docs/windows-setup.md` §4는 repo
경로에 대해 "앱에서 바꿀 수 없다"고 못 박고 `UPDATE repo SET path = ...`를 안내한다.
같은 문서가 `claude_path`·`opencode_path`도 "편집 UI가 없으니 SQL로 비워 두라"고 적는다.
**새 장비로 옮기는 절차가 문서 속 SQL 스니펫으로만 존재한다.**

**무엇이 설정이고 무엇이 실행마다 고르는 값인지 구분되지 않는다.** 바꿀 수 있는 값이
사이드바·실행 패널·DB에 흩어져 있어서, 이번 한 번만 적용되는 값(실행 패널의 권한·모델)과
기본값으로 남는 값(workspace 컬럼)이 화면상 구별되지 않는다.

**두 컬럼은 아예 죽어 있다.** `default_model_claude`·`default_model_opencode`는 스키마와
`shared/models.ts`에만 있고 읽는 코드가 없다. 같은 `RunPanel`이 `defaultAgentKind`는
읽으면서 모델만 읽지 않아 대칭이 깨져 있다.

**이 자리는 예고돼 있었다.** `SettingsPanel.tsx`의 주석이 "전체 설계 §403이 전제한
workspace 기본값도 앞으로 여기로 모을 자리다"라고 적었고, `docs/sdlc/asset-scope/intent.md`의
미해결 질문도 "이 값들만 위한 최소 화면인가, 기존에 화면이 없던 다른 설정까지 담는 자리를
만드는가"를 남겼다. **그때 최소 화면을 골랐고, 지금 그 미룬 값을 치르고 있다.**

## 원하는 결과

**앱 안에서 설정을 전부 보고 바꿀 수 있다.** SQLite를 여는 절차가 문서에서 사라진다.
장비를 옮긴 뒤 해야 할 일이 "설정 화면에서 경로 몇 개 고치기"로 끝난다.

**무엇이 어느 범위의 값인지 화면이 알려준다.** 장비 전체에 걸리는 값, workspace마다 다른
값, 실행할 때마다 고르는 값이 서로 다른 자리에 있다는 것이 보인다.

**설정이 늘어날 자리가 생긴다.** 값이 하나 늘 때마다 화면을 다시 설계하지 않아도 되도록
탭으로 갈라 둔다. 네 갈래를 예상한다 — 실행 기본값, 앱 전체, repo 관리, 진단·정보.

**위험한 값은 실수로 바뀌지 않는다.** 특히 기본 권한을 전체 허용으로 올리는 것은 전체 설계
§403이 별도 확인 절차를 요구한 자리다.

**진단 정보를 물어볼 곳이 생긴다.** MCP 서버 상태와 포트, DB 파일 위치, 앱 버전, 로그
폴더처럼 문제가 생겼을 때 필요한 것들을 한 화면에서 확인한다.

## 영향 범위

- **사용자**: one-desk 사용자 전부. 장비를 옮기는 사람과 글로벌 경로가 기본값과 다른
  사람이 가장 크게 체감한다.
- **시스템**:
  - `renderer/components/SettingsPanel.tsx` — 지금은 단일 화면이다. 탭을 갖는다.
  - `App.tsx`의 화면 전환 배선 — 설정은 모달이 아니라 본문 영역을 대신 차지한다.
  - `shared/channels.ts`·`shared/client.ts`·`electron/ipc/` — workspace는 지금
    list·create·rename·remove만 있고 **기본값을 고치는 통로가 없다.** repo도 마찬가지다.
  - `core/db/repositories/workspace.ts`·`repo.ts` — 갱신 메서드가 필요하다.
  - `renderer/components/SlotIndicator.tsx` — 동시 실행 상한을 이미 여기서 바꾼다.
    설정 화면에도 둔다면 **같은 값을 고치는 자리가 둘이 된다.**
  - asset 스캔 — repo 경로가 바뀌면 그 아래 asset의 `file_path`가 전부 달라진다.
    동일성 키가 `(workspace_id, file_path)`이므로 **옛 행이 "없음"으로 남고 새 행이 쌓인다.**
  - `docs/windows-setup.md` §4 — SQL 안내가 화면 안내로 바뀐다.

## 제약

- **전체 설계 §403을 지킨다.** 기본 권한을 전체 허용으로 바꾸려면 별도 확인 절차를 거친다.
- **경계 세 가지를 우회하지 않는다.** `core/`는 `electron`을 import하지 않고(진단 탭의
  "로그 폴더 열기" 같은 것은 메인 프로세스 몫이다), `renderer/`는 `core/`를 import하지
  않으며, IPC 핸들러는 얇게 유지한다.
- **스키마 변경은 최소로.** 필요한 컬럼은 이미 전부 있다. 마이그레이션 `0006`이 필요하다면
  그 근거가 분명해야 한다.
- **사라진 데이터를 만들지 않는다.** repo 경로 편집이 asset 행이나 과거 run의 맥락 기록을
  끊으면 안 된다 — 전체 설계 §232의 "사라진 asset을 지우지 않는다"와 같은 이유다.
- **배선도 검증 대상이다.** `App.tsx`가 자식에게 내려보내는 prop 한 줄이 3a·3b 리뷰에서
  반복해 새어나간 자리다. 탭 전환과 저장 경로가 테스트로 고정돼야 한다.

## 성공 기준

1. 위 표의 여덟 값을 **SQL 없이** 앱에서 바꿀 수 있다.
2. 장비를 옮긴 뒤 필요한 재지정(글로벌 경로·repo 경로·CLI 경로)이 설정 화면만으로 끝난다.
   `docs/windows-setup.md` §4에서 SQL 스니펫을 지울 수 있다.
3. 기본 권한을 전체 허용으로 올릴 때 확인 절차가 한 번 더 개입한다.
4. 탭을 옮겨도 저장하지 않은 입력이 조용히 사라지지 않는다.
5. 값을 바꾼 뒤 **언제 적용되는지가 화면에 드러난다** — 특히 다음 실행부터인지, 앱을 다시
   켜야 하는지.
6. `e2e`가 실제로 설정 화면을 클릭해 값을 바꾸고, 그 값이 실행 패널의 기본값으로 나타나는
   것까지 확인한다.

## 미해결 질문

- [ ] 탭을 정확히 어떻게 가르는가. 네 갈래(실행 기본값·앱 전체·repo 관리·진단)를
      가정했으나 이름과 경계는 spec에서 확정한다.
- [ ] workspace가 여럿일 때 설정 화면은 어느 workspace를 다루는가. 사이드바에서 고른 것
      하나인가, 화면 안에서 고르는가.
- [ ] `default_model_claude`·`default_model_opencode`를 배선하는가, 아니면 지우는가.
      **전체 설계가 이 값을 어떻게 정해 두었는지 먼저 확인할 것** — 설계에 있는데 구현이
      빠진 것인지, 설계가 버린 것인지에 따라 답이 갈린다. 지금은 빈 칸이면 각 CLI의 설정
      기본값이 쓰인다(`core/runner/adapters/opencode.ts:98`).
- [ ] repo 경로를 바꿀 때 그 아래 asset 행을 어떻게 하는가. 새 경로로 옮겨 주는가, 옛 행을
      "없음"으로 두는가. 후자면 목록이 조용히 두 배가 된다.
- [ ] 동시 실행 상한을 설정 화면으로 옮기는가, 도크에 남기는가, 양쪽에 두는가. 지금은
      도크의 슬롯 표시기에서 바꾸며 `queue.setLimit`이 곧바로 반영한다 — **옮기면 run이
      대기하는 맥락 바로 옆에서 상한을 조절하던 이점을 잃는다.**
- [ ] 저장 방식 — 지금 화면처럼 저장 버튼인가, 즉시 저장인가. 이슈·메모 본문은 디바운스
      자동 저장에 낙관적 잠금을 쓴다. 설정도 같은 규칙을 따를 이유가 있는가.
- [ ] 위험한 값의 확인 절차는 어떤 모양인가 — 한 번 더 누르기(`ConfirmButton`)인가, 이름을
      타이핑하기(`DeleteByName`)인가. 앱에 이미 두 패턴이 있다.
- [ ] 진단 탭이 보여줄 것의 범위. 읽기 전용으로 끝나는가, "로그 폴더 열기"처럼 동작하는
      버튼이 붙는가. 후자는 메인 프로세스 통로가 필요하다.
