# 이슈·메모 본문 편집 설계

**날짜:** 2026-08-14
**상태:** 승인됨
**근거 문서:** 전체 설계 §5(데이터 모델) · §9(UI 구조), 4단계 설계 `2026-08-12-stage4-mcp-design.md` §5

---

## 1. 문제

이슈와 메모가 **제목만 있는 상태**로 쓰이고 있다. `IssuePanel`은 제목과 상태 버튼만, `MemoPanel`은 제목만 그린다. 본문을 입력할 자리도, 고칠 자리도, 지울 자리도 없다.

그런데 아래층은 전부 준비돼 있다.

- `Issue`·`Memo` 모델과 스키마에 `body`가 있다
- 저장소의 `create`·`update`·`remove`가 `body`를 다룬다
- `OneDeskClient`에 `update`·`remove`가 노출돼 있다
- `assemblePrompt`가 `<body>`를 **이미 agent에게 보낸다**
- 4단계 MCP의 `create_issue`·`update_issue`로 **agent는 본문을 쓸 수 있다**

즉 지금 `body`는 **사람은 볼 수 없고 agent만 쓸 수 있는 필드**다. agent가 이슈에 조사 결과를 적어도 사용자는 그것을 앱에서 읽을 방법이 없다.

막힌 곳은 렌더러 하나뿐이다.

---

## 2. 범위

이 스펙은 "메모와 이슈를 실제로 쓸 만하게" 중 **본문 계층**만 다룬다. 넷으로 쪼갠 것 중 첫 번째다.

### 들어가는 것

- 본문 보기·편집, 제목 편집, 삭제
- 3컬럼 동적 확장 — 선택한 패널이 커지고 나머지가 줄어든다
- 맥락 담기를 항목 클릭에서 **별도 토글 버튼으로 분리**
- 낙관적 잠금 — agent와 사람이 같은 본문을 동시에 고치는 상황

### 빠지는 것

**마크다운 렌더링.** 본문을 평문으로 먼저 굳힌다. 렌더링을 넣는 순간 "편집 중엔 원문, 볼 땐 렌더링"이라는 모드 전환 결정이 따라오는데, 그게 본문 UI에서 가장 성가신 자리다. 별도 스펙으로 다룬다.

**검색·필터·정렬.** 이슈가 수십 개 쌓인 뒤에 필요해진다. 지금 정하면 안 쓸 기준을 짓게 된다.

**run 완료 구독.** agent가 MCP로 만든 이슈가 화면에 즉시 뜨게 하는 것. 4단계가 5단계로 이월한 항목과 같은 자리이고, 이 스펙과 독립적으로 붙일 수 있다. **다만 이 스펙의 낙관적 잠금이 그 부재를 견디게 만든다** — 화면이 낡았어도 저장이 조용히 덮어쓰지는 않는다.

**되돌리기·편집 이력.** 이 앱에 없고, 이번에도 만들지 않는다. 실수로 본문을 지우고 나가면 그대로다. 한계로 명시한다.

**삭제의 버전 검사.** 낙관적 잠금(§6)은 **갱신에만** 건다. `remove`에는 아무 검사가 없어, 화면이 낡았어도 삭제는 그대로 통과한다 — agent가 방금 본문을 채운 이슈를 그 사실을 모르는 사용자가 지울 수 있다. 덮으려면 `remove`도 `expectedUpdatedAt`을 받아야 하고 충돌 화면도 "지우려던 항목이 그 사이 바뀌었습니다"로 갈라지는데, 삭제 쪽은 인라인 2단계 확인(§5)이 이미 실수를 한 번 막고 있어 지금은 균형이 맞지 않는다. **알려진 구멍으로 남긴다.**

## 3. 상태는 `App.tsx`가 하나만 갖는다

```ts
const [openItem, setOpenItem] = useState<{ panel: 'issue' | 'memo'; id: string } | null>(null)
```

**한 번에 한 패널만 확장되므로 상태도 하나다.** `IssuePanel`과 `MemoPanel`이 각자 갖게 하면 둘 다 열린 상태를 만들 수 있고, 컬럼 비율을 누가 정하는지도 흐려진다.

이 프로젝트는 훅을 자식이 각자 부르다 두 번 사고를 냈다 — `useRepos`를 `RepoStrip`과 `RunPanel`이 각자 불러 repo 등록이 한쪽에만 반영됐고(`fbcd0e6`), `useWorkspaces`를 셋이 각자 불러 인박스가 방금 만든 workspace를 "(사라진 workspace)"로 그렸다. 같은 모양을 만들지 않는다.

두 패널은 같은 모양의 prop을 받는다.

```ts
expanded: boolean          // 이 패널이 확장돼 있는가
openId: string | null      // 그중 어느 항목이 열려 있는가
onOpen: (id: string) => void
```

**`IssuePanel`과 `MemoPanel`은 합치지 않는다.** `issue.ts`↔`memo.ts` 규칙 그대로다 — 이슈에는 앞으로 상태 전이와 run 연결이 붙고 메모에는 붙지 않는다. 대칭으로만 유지한다.

## 4. 레이아웃

`.columns`의 자식에 flex 비율만 준다. JS로 픽셀을 계산하지 않는다.

| 상태 | Issues | Memos | Assets |
|---|---|---|---|
| 평소 | `flex: 1` | `flex: 1` | `flex: 1` |
| 이슈 열림 | `flex: 3` | `flex: 1` | `flex: 1` |
| 메모 열림 | `flex: 1` | `flex: 3` | `flex: 1` |

1400px 창 기준으로 확장된 패널이 약 715px, 나머지가 각 238px이다. 238px면 제목이 잘리지만(`item-title`이 이미 `text-overflow: ellipsis`) 목록으로는 충분하다.

확장된 패널 안은 **좌우로 나눈다** — 목록이 왼쪽 고정 200px, 상세가 오른쪽 나머지. 위아래로 나누면 715px 폭이 놀고 세로만 잡아먹는다. 도크를 열면 세로가 34% 깎이므로 세로가 더 아쉽다.

```
평소                     이슈 클릭
┌ISSUES┐┌MEMOS┐┌ASSETS┐  ┌─ISSUES──────────────┐┌MEMOS┐┌ASSET┐
│이슈 A││메모1 ││      │  │이슈 A  │ 토큰 만료  ││메모1││     │
│이슈 B││메모2 ││      │  │이슈 B ◀│ [open]     ││메모2││     │
│이슈 C││      ││      │  │이슈 C  │ ┌────────┐ ││     ││     │
│      ││      ││      │  │        │ │본문…   │ ││     ││     │
└──────┘└──────┘└──────┘  │        │ └────────┘ │└─────┘└─────┘
                          └─────────────────────┘
```

`AssetPanel`은 5단계 스텁이라 열 항목이 없다. 확장 대상이 아니고 항상 `flex: 1`이다.

**도크는 자동으로 접지 않는다.** 도크는 사용자가 여닫는 것이고, 로그를 보면서 이슈를 고치는 상황이 오히려 자연스럽다.

## 5. 상호작용

| 동작 | 결과 |
|---|---|
| 항목 클릭 | 그 패널이 확장되고 그 항목이 열린다 |
| 같은 항목 다시 클릭 | 접힌다 |
| Esc | 접힌다 |
| 다른 패널 항목 클릭 | 그쪽이 확장되고 이쪽은 접힌다 |
| 확장된 패널의 다른 항목 클릭 | 열린 항목만 바뀐다 (확장 유지) |

접기와 항목 전환은 **대기 중인 저장을 먼저 flush한다.**

Esc는 본문을 치는 도중에 눌러도 접는다. 자동 저장이라 취소 의미가 없고, flush가 먼저 돌아 내용이 남는다. 상세 안에 닫기 버튼은 두지 않는다 — 위 셋으로 충분하고 좁은 헤더에 버튼을 더 얹을 이유가 없다.

### 맥락 담기가 클릭에서 분리된다

**지금은 제목 클릭이 곧 "맥락에 담기"다.** 본문이 생기면 "열어본다"가 주된 행동이 되므로, 잦은 쪽이 기본 클릭을 갖는다.

항목마다 작은 담기 토글 버튼을 따로 둔다. 담긴 항목은 지금처럼 파랗게 표시된다(`item-picked`) — 상태 표현은 그대로 유지한다.

이것은 **되돌릴 수 있는 변경**이다. 배선이 끊기면 항목을 클릭했을 때 칩이 생기거나, 토글을 눌러도 칩이 안 생긴다. 둘 다 변이표에 있다.

### 편집과 저장

제목과 본문 모두 상세에서 편집한다. 저장은 **자동**이다.

- 입력이 멎으면 600ms 뒤 저장 (디바운스)
- 입력란에서 포커스가 빠지면 저장
- 접기·항목 전환 시 대기 중인 저장을 flush

저장 버튼은 두지 않는다. 이 앱은 이미 그렇게 굴러간다 — 상태는 고르는 즉시 쓰고 추가 폼은 Enter로 바로 만든다. 본문만 "저장 누르세요"가 되면 결이 어긋나고, 안 누르고 나가서 날리는 사고가 생긴다.

**상태도 상세에서만 고친다**(§9). 목록의 상태 칩은 읽기 전용 배지다 — 항목을 열어야 상태를 바꿀 수 있다. 목록에 쓰기 버튼을 두면 그 쓰기가 잠기지 않은 `update`를 타고 `updatedAt`을 올려 **열려 있는 상세의 기대값만 낡게 만들고**, 그다음 자동 저장이 사용자 자신의 클릭을 agent의 편집으로 착각해 충돌 배너를 띄운다(§6의 "성공한 저장은 기대값을 갱신해야 한다"가 목록 쪽 쓰기까지 덮지 못하는 자리다). 클릭 한 번이 늘어나는 대신 잠기지 않은 쓰기 경로가 화면에서 사라진다.

### 삭제

상세 안에 삭제 버튼. 되돌리기가 없으므로 **인라인 2단계 확인**을 거친다 — 한 번 누르면 버튼이 "정말 삭제?"로 바뀌고, 다시 눌러야 지워진다. 다른 곳을 누르면 원래대로 돌아간다.

**Esc는 안쪽부터 푼다.** 확인이 켜져 있으면 Esc가 확인만 끄고 패널은 그대로 둔다. 확인이 꺼져 있을 때만 Esc가 패널을 접는다. 삭제를 취소하려다 편집 화면까지 닫히면 안 된다.

모달을 만들지 않는 이유는 이 앱에 모달 인프라가 없고, `SlotIndicator`가 이미 인라인 확인 패턴을 쓰고 있기 때문이다.

삭제되면 패널이 접힌다.

## 6. 낙관적 잠금

4단계가 만든 새 상황이다. 이슈 본문을 열어 편집하는 동안 **돌고 있는 agent가 `update_issue`로 같은 본문을 바꿀 수 있다.** 패널은 run 완료를 구독하지 않으므로 화면은 그 사실을 모르고, 자동 저장이 도는 순간 agent가 쓴 내용을 낡은 버퍼가 조용히 덮어쓴다. 반대 방향도 같다.

### 충돌은 예외가 아니라 값으로 돌려준다

`electron/preload.ts`가 IPC 오류를 받아 **메시지만 남기고 평범한 `Error`로 다시 던진다.** 클래스가 사라지므로 렌더러에서 `instanceof`로 충돌을 가려낼 수 없고, 남는 것은 메시지 문자열 매칭뿐이다 — 4단계에서 `resume`의 catch를 좁히며 없앤 바로 그 취약함이다.

그래서 충돌을 값으로 돌려준다. 어차피 UI가 "다시 불러오기"를 제안하려면 최신 행이 필요하므로, 값으로 받는 편이 실제로 더 쓸모 있다.

```ts
// shared/models.ts — 의도된 중복. issue와 memo를 따로 둔다.
export type IssueUpdateResult =
  | { ok: true; issue: Issue }
  | { ok: false; current: Issue }

export type MemoUpdateResult =
  | { ok: true; memo: Memo }
  | { ok: false; current: Memo }
```

```ts
// shared/client.ts
issues: {
  // 기존 그대로 — cycleStatus, 인박스의 이슈 닫기, MCP가 쓴다
  update(input: UpdateIssueInput): Promise<Issue>
  // 사람이 편집 화면에서 저장할 때만 쓴다
  updateIfUnchanged(
    input: UpdateIssueInput & { expectedUpdatedAt: number }
  ): Promise<IssueUpdateResult>
}
```

memo도 대칭으로 같다.

### 저장소

트랜잭션 안에서 현재 `updatedAt`을 읽어 기대값과 비교하고, 다르면 던져서 롤백시킨 뒤 최신 행을 `{ ok: false, current }`로 돌려준다.

읽고 나서 쓰는데도 경합이 없다 — **better-sqlite3는 동기이고 커넥션이 하나뿐이라 `db.transaction` 안에서는 다른 JS가 끼어들 수 없다.** 조건부 `UPDATE`의 영향 행 수를 세는 방법도 되지만, 읽는 쪽이 분명하고 충돌 시 돌려줄 최신 행이 이미 손에 있다.

`updatedAt`은 지금도 모든 쓰기에 찍히므로 새 컬럼이 없다. 마이그레이션이 생기지 않는다.

### `updatedAt`은 단조 증가해야 한다

지금 `update`는 `Date.now()`를 그대로 넣는다. **같은 밀리초에 두 번 쓰면 값이 같아져 "그 사이 바뀌었다"를 놓친다.** agent가 쓰고 사용자가 저장하는 간격이 1ms 미만이면 잠금이 조용히 통과하고, 이 기능이 막으려던 덮어쓰기가 그대로 일어난다. 테스트도 같은 이유로 간헐적으로 초록이 된다.

`updatedAt`이 잠금의 버전 노릇을 하므로 **이전 값보다 반드시 크게 만든다.**

```ts
updatedAt: Math.max(Date.now(), previousUpdatedAt + 1)
```

`update`와 `updateIfUnchanged`가 같은 규칙을 쓴다. 이 프로젝트는 이미 같은 종류의 문제를 겪었다 — 스키마의 `unixepoch() * 1000` 기본값이 초 해상도라 같은 초에 만든 항목들의 정렬이 무너졌고, 그래서 시각을 `Date.now()`로 명시 삽입하는 규칙이 생겼다. 여기서는 한 걸음 더 나아가 단조성까지 보장한다.

### agent는 잠기지 않는다

**MCP의 `update_issue`·`update_memo`는 잠금 없는 `update`를 그대로 쓴다.** agent가 사람의 편집 상태 때문에 막히면 안 된다 — 헤드리스에서 도구가 거부되면 agent가 그 지점에서 작업을 접는다.

비대칭이 의도다. 사람은 충돌을 보고 판단할 수 있고 agent는 못 한다. 그래서 판단할 수 있는 쪽이 거부당한다.

### 함정 — 성공한 저장은 기대값을 갱신해야 한다

자동 저장이 디바운스로 연달아 돈다. 첫 저장이 `updatedAt`을 새로 찍었는데 렌더러가 옛 값을 계속 들고 있으면 **두 번째 저장이 자기 자신과 충돌한다.** 상태를 바꿔도 같은 일이 벌어진다 — 그래서 상태 변경도 본문·제목과 같은 저장 경로(`updateIfUnchanged` → 기대값 갱신)를 지난다.

규칙 하나로 덮는다.

> **열려 있는 항목에 대한 성공한 모든 쓰기는, 돌려받은 행의 `updatedAt`으로 기대값을 갱신한다.**

`update`도 `updateIfUnchanged`도 갱신된 행을 돌려주므로 추가 호출이 없다.

## 7. 충돌했을 때 화면

본문 위에 줄 하나가 뜬다 — "이 항목이 그 사이 바뀌었습니다" 옆에 버튼 둘.

- **다시 불러오기** — 내 편집을 버리고 최신을 띄운다. 충돌 응답이 이미 최신 행을 들고 왔으므로 추가 호출이 없다
- **덮어쓰기** — 잠금 없는 `update`로 내 내용을 밀어 넣는다

**배너가 떠 있는 동안 자동 저장은 멈춘다.** 계속 재시도하면 결국 덮어쓰기가 되어 잠금이 무의미해진다. 사용자가 둘 중 하나를 고를 때까지 기다린다.

### Esc는 상세가 직접 받는다

접기를 App의 document 리스너에 맡기면 상세가 그 자리에서 언마운트되고, 대기 중이던 저장은 언마운트 flush로 흘러나간다. 그 flush가 충돌로 거부되면 `setConflict`가 이미 사라진 컴포넌트에 떨어져 React가 조용히 버린다 — **배너도 오류도 없이, flush가 이미 소비한 텍스트만 사라진다.**

그래서 Esc는 상세가 살아 있는 동안 자기가 먼저 받는다. flush를 끝까지 기다리고, 충돌이 났으면 **접지 않고** 배너를 남겨 판단할 자리를 지킨다. 이벤트가 App까지 올라가지 않게 `stopPropagation`으로 멈춘다 — `ConfirmButton`이 삭제 확인에 쓰는 것과 같은 방법이다.

### 남는 한계 — 상세가 언마운트되며 나가는 충돌

**Esc가 아닌 경로로 상세가 사라질 때는 그렇게 할 수 없다.** 목록에서 다른 항목을 누르거나(패널의 `key`가 새 항목으로 바뀐다), 사이드바에서 인박스로 넘어가거나, workspace를 바꾸면 상세가 그 자리에서 언마운트되고 대기 중이던 저장은 언마운트 flush로 나간다. 물어볼 화면이 이미 없다.

그래서 **항목 전환·화면 전환·workspace 전환 중에 일어난 충돌은 판단을 물을 자리가 없어 서버 쪽이 이기고 그때까지 친 내용이 사라진다.** 알려진 한계로 남긴다. 전환을 비동기로 붙잡아 두거나 충돌을 패널 위로 끌어올리는(전역 충돌 큐) 방법이 있지만 둘 다 이 스펙이 감당할 크기가 아니고, Esc가 훨씬 흔한 경로라 그쪽만 막았다.

포커스가 상세 바깥(예: 목록의 제목 버튼)에 있을 때 누른 Esc도 같은 이유로 App의 리스너가 받는다. 다만 그때는 방금 친 내용이 없으므로 — 타이핑은 포커스를 상세 안에 둔다 — 잃을 것도 없다.

## 8. 오류 처리

저장 실패(충돌이 아닌 진짜 오류)는 상세 안에 그대로 띄운다. 조용히 삼키지 않는다 — 자동 저장은 사용자가 결과를 안 보므로, 실패를 숨기면 안 썼는데 썼다고 믿게 된다.

삭제 실패도 같은 자리에 띄우고 패널은 접지 않는다.

**열려 있는 항목이 목록에서 사라지면**(다른 경로로 지워졌거나 workspace가 바뀌었으면) 패널을 접는다. 존재하지 않는 항목의 상세를 그리지 않는다.

## 9. 컴포넌트 구성

```
renderer/components/
├─ IssuePanel.tsx     목록 + 확장 모드. IssueDetail을 품는다
├─ IssueDetail.tsx    제목·본문·상태·삭제. 낙관적 잠금 보유
├─ MemoPanel.tsx      위와 대칭
├─ MemoDetail.tsx     위와 대칭 (상태 없음)
├─ ConflictBanner.tsx 공용 — 도메인이 없다
└─ ConfirmButton.tsx  공용 — 2단계 확인. 도메인이 없다
```

`renderer/hooks/useDebouncedSave.ts` — 타이머와 flush만 담는다. `save(value)` 콜백을 받는다.

**`IssueDetail`과 `MemoDetail`은 의도적으로 중복한다.** 이슈에는 상태 전이가 있고 앞으로 run 연결이 붙는다. 지금 합치면 다음 단계에서 되돌려야 한다.

**`ConflictBanner`·`ConfirmButton`·`useDebouncedSave`는 공용으로 둔다.** 셋 다 도메인이 없다 — 배너는 문자열 하나와 콜백 둘, 확인 버튼은 두 번 눌러야 부르는 버튼, 훅은 타이머다. 이슈와 메모가 갈라지더라도 이 셋은 갈라질 이유가 없다. 낙관적 잠금의 기대값 관리는 **각 Detail이 직접 들고 있는다** — 그쪽은 도메인이다.

## 10. 테스트와 변이표

렌더러 테스트가 대부분이고 core는 저장소 두 개에 잠금 경로가 붙는다.

CLAUDE.md가 3a·3b에서 두 번 다 새어나간 자리로 기록한 것이 **`App.tsx`가 자식에게 내려보내는 prop 한 줄**이라, 이번에는 그 줄들을 변이표 맨 앞에 놓는다.

각 줄은 "이 줄을 되돌리면 이 테스트가 빨개진다"는 짝이다. 회귀 테스트를 넣을 때는 **대상 코드를 잠시 망가뜨려 실제로 실패하는지 확인한다.**

| # | 약속 | 되돌릴 줄 | 실패해야 하는 테스트 |
|---|---|---|---|
| 1 | **배선** `App.tsx` → `IssuePanel`의 `openId` | 전달 한 줄 | 이슈를 클릭하면 상세가 뜬다 |
| 2 | **배선** `App.tsx` → `MemoPanel`의 `openId` | 전달 한 줄 | 메모를 클릭하면 상세가 뜬다 |
| 3 | **배선** `App.tsx` → `.columns`의 확장 클래스 | 전달 한 줄 | 열린 패널이 `flex: 3`이 된다 |
| 4 | 한 번에 한 패널만 확장 | `setOpenItem`이 이전 것을 덮는 줄 | 메모를 열면 이슈 상세가 사라진다 |
| 5 | 같은 항목 재클릭이 접는다 | 토글 분기 | 두 번 클릭하면 상세가 사라진다 |
| 6 | Esc가 접는다 | keydown 핸들러 | Esc 후 상세가 사라진다 |
| 7 | 확인이 켜져 있으면 Esc가 확인만 끈다 | Esc의 중첩 분기 | 삭제 확인 중 Esc를 눌러도 상세가 남는다 |
| 8 | 항목 클릭이 맥락 칩을 만들지 않는다 | 분리한 배선 | 클릭 후 도크에 칩이 없다 |
| 9 | 담기 토글이 칩을 만든다 | 토글 버튼의 `onToggleContext` | 토글 후 도크에 칩이 생긴다 |
| 10 | 담긴 항목 표시가 유지된다 | `item-picked` 조건 | 담은 항목에 표시가 붙는다 |
| 11 | 본문 편집이 디바운스로 저장된다 | 타이머 호출 | 타이머를 진행시키면 저장된다 |
| 12 | 접기·항목 전환이 대기 중 저장을 flush한다 | flush 호출 | 디바운스 도중 접어도 저장돼 있다 |
| 13 | 그 사이 바뀌면 저장이 거부된다 | 저장소의 `updated_at` 조건 | `{ ok: false }`가 온다 |
| 14 | 거부된 저장은 DB를 바꾸지 않는다 | 트랜잭션 롤백 | 원본 본문이 그대로다 |
| 15 | **성공한 저장이 기대값을 갱신한다** | 갱신 한 줄 | 연속 두 번 저장이 충돌하지 않는다 |
| 15b | **`updatedAt`이 단조 증가한다** | `Math.max(…, previous + 1)` | 같은 밀리초에 두 번 써도 값이 달라진다 |
| 16 | 충돌 후 다시 불러오기가 최신을 띄운다 | `current`로 편집 버퍼를 덮는 줄 | 버튼을 누르면 agent가 쓴 본문이 보인다 |
| 17 | 충돌 후 덮어쓰기가 실제로 덮는다 | 잠금 없는 `update` 호출 | DB에 내 본문이 남는다 |
| 18 | 배너가 떠 있으면 자동 저장이 멈춘다 | 가드 | 배너 상태에서 타이머를 진행시켜도 저장이 안 불린다 |
| 19 | 저장 실패가 화면에 뜬다 | 오류 표시 | 저장이 던지면 메시지가 보인다 |
| 20 | 삭제가 2단계 확인을 거친다 | 확인 상태 | 한 번 눌러서는 안 지워진다 |
| 21 | 삭제 후 패널이 접힌다 | `setOpenItem(null)` | |
| 22 | 열린 항목이 목록에서 사라지면 접힌다 | 정리 effect | 목록에서 빠지면 상세가 사라진다 |
| 23 | MCP `update_issue`는 잠금을 쓰지 않는다 | MCP 도구가 `updateIfUnchanged`를 쓰게 바꾸기 | 사람이 편집 중이어도 agent 쓰기가 통과한다 |
| 24 | **memo 대칭** | 11–22 전부 | memo 쪽에도 같은 테스트 |

**e2e 하나를 추가한다.** 이슈를 열어 본문을 쓰고, 접었다 다시 열어 본문이 남아 있는 것을 확인한다. 같은 테스트에서 담기 토글이 클릭과 분리된 것도 확인한다 — 항목을 클릭해도 도크에 칩이 안 생기고, 토글을 눌러야 생긴다.

## 11. 구현 순서

1. **저장소** — `issue.updateIfUnchanged`, `memo.updateIfUnchanged` (마이그레이션 없음)
2. **전송 계층** — `shared/models.ts`의 결과 타입, `shared/channels.ts`의 채널 둘, `shared/client.ts`, `electron/ipc/`의 얇은 핸들러 둘
3. **확장 배선** — `App.tsx`의 `openItem`, 컬럼 flex, 두 패널의 확장 모드 (상세는 아직 빈 껍데기). **여기서 배선 셋을 테스트로 못박는다**
4. **맥락 담기 토글 분리** — 클릭과 담기를 가른다
5. **`IssueDetail`** — 제목·본문 편집, 자동 저장, 낙관적 잠금, 충돌 배너, 삭제
6. **`MemoDetail`** — 대칭
7. **e2e**

1과 2는 서로 독립이고 3이 가장 조용히 깨지는 자리다. 5를 만들기 전에 3의 배선 테스트를 먼저 초록으로 만들어 둔다.
