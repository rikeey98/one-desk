# MCP 서버 상시 기동과 상태 표시 설계

**날짜:** 2026-08-14
**상태:** 승인됨
**근거:** `core/mcp/host.ts`, 4단계 설계 §3, 전체 설계 §14

---

## 1. 범위

MCP 서버를 앱 시작과 동시에 띄우고, 사이드바 하단에 상태를 보여준다.

**계기.** 대상 Windows 환경에서 agent가 MCP에 붙지 못하는데 화면에 아무 단서가 없었다. 실행 로그를 파야만 알 수 있었고, 그 사이 run은 "성공"으로 끝났다. 서버가 떠 있는지조차 눈으로 확인할 방법이 없다.

### 들어가는 것

- 부팅 시 기동 — 실패해도 앱은 뜬다
- `McpStatus` 타입과 core의 상태 이벤트
- IPC 배선 (조회 + 구독)
- 사이드바 하단의 상태 줄

### 빠지는 것

**동적 포트 할당.** **이미 구현돼 있다.** `host.ts`의 `s.listen(0, '127.0.0.1')`에서 `0`은 "빈 포트를 OS가 고르라"는 뜻이다. 고정 포트를 쓰지 않으므로 다른 프로세스와의 충돌이 구조적으로 불가능하다. 이 항목은 새로 할 일이 없다.

**장기 토큰.** 토큰은 run 시작 때 발급되고 끝나면 폐기된다. 서버를 상시 띄워도 **run이 없는 동안에는 유효한 토큰이 하나도 없어** 모든 요청이 401이다. 터미널에서 띄운 claude나 외부 도구가 붙게 하려면 run에 매이지 않는 토큰이라는 개념이 필요하고, 그건 권한 모델을 다시 그리는 일이라 별도 설계로 뺀다.

**연결 실패의 해결.** 상시 기동은 그 문제를 고치지 않는다. 지금도 `prepare()`가 listening을 끝낸 **뒤에** agent를 spawn하므로 순서 문제가 아니었다. 이 작업이 주는 것은 가시성이다.

## 2. 뒤집는 결정 — 부팅 시 포트를 연다

전체 설계 §14와 `core/index.test.ts`의 "부팅만으로는 MCP 포트를 열지 않는다"가 **정반대를 못박고 있었다.** 그 근거는 "앱을 여는 행위가 아무것도 시작하면 안 된다"였고, agent를 한 번도 안 돌리는 사용자에게는 listening 소켓이 아예 없다는 성질을 지키기 위한 것이었다.

**사용자가 상시 기동을 명시적으로 선택해 이 결정을 뒤집는다.** 바뀌는 것과 바뀌지 않는 것을 분명히 해 둔다.

| | 전 | 후 |
|---|---|---|
| 앱을 켜둔 동안 listening 소켓 | 첫 run 전까지 없음 | **항상 하나** |
| 바인딩 주소 | `127.0.0.1` | `127.0.0.1` (그대로) |
| 토큰 없는 요청 | 401 | 401 (그대로) |
| run이 없을 때 유효한 토큰 | 없음 | 없음 (그대로) |

**노출이 넓어지는 것은 사실이다.** 완화는 그대로 남는다 — 외부 인터페이스에 바인딩하지 않고, 토큰 없이는 아무것도 못 한다. 첫 run 전까지는 토큰이 하나도 없으므로 그 구간의 서버는 401만 돌려주는 껍데기다.

**기존 테스트는 지우지 않고 뒤집는다.** "부팅하면 MCP 포트가 열린다"로 바꿔, 이 성질이 여전히 실행 가능한 단언으로 남게 한다.

## 3. 상태 모델

```ts
export type McpStatus =
  | { state: 'starting' }
  | { state: 'listening'; port: number }
  | { state: 'failed'; message: string }
```

`shared/models.ts`에 둔다. 렌더러와 core가 모두 봐야 하고, `core/`는 `electron`을 import하지 않으므로 공용 자리가 필요하다.

**`stopped`를 두지 않는다.** 부팅이 곧 기동이므로 core가 살아 있는 동안 이 셋 중 하나다. `close()` 이후의 상태는 앱이 종료되는 중이라 아무도 보지 않는다.

**실패를 상태로 남긴다.** 던지지 않는다 — MCP가 없어도 이슈·메모 편집은 멀쩡히 되어야 하고, 포트 하나 때문에 앱이 안 뜨면 그게 더 나쁘다.

## 4. 흐름

```
createCore()
   │
   ├─ mcp.start()        ← await하지 않는다. 창이 이것 때문에 늦어지면 안 된다.
   │    ├─ 성공 → status = { listening, port } → emit
   │    └─ 실패 → status = { failed, message } → emit + onError
   │
   └─ 창이 뜬다
        └─ Sidebar가 mount되며 core.mcpStatus()를 한 번 읽고, 이후 구독한다
```

**한 번 읽기와 구독이 둘 다 필요하다.** `start()`가 비동기라 창이 먼저 뜰 수 있는데, 그때 구독만 있으면 이미 지나간 전이를 놓쳐 영원히 `starting`으로 굳는다. 반대로 읽기만 있으면 창이 먼저 떴을 때 `starting`에서 멈춘다. **둘 다 있어야 어느 순서로 일어나도 맞는 값이 보인다.**

기존 인박스 배선과 같은 모양이다 — core가 emit, `electron/ipc/`가 중계, preload가 구독을 노출, 훅이 소비.

## 5. 배선

| 파일 | 더할 것 |
|---|---|
| `shared/models.ts` | `McpStatus` |
| `core/mcp/host.ts` | `start()`, `status()` |
| `core/index.ts` | 부팅 시 `start()`, `mcpStatus()`, `onMcpStatus()` |
| `shared/channels.ts` | `mcpStatus` (invoke), `mcpStatusUpdate` (event) |
| `electron/ipc/runs.ts` | 핸들러와 중계 |
| `electron/preload.ts` | `mcp.status()`, `mcp.onStatus()` |
| `shared/client.ts` | 같은 시그니처 |
| `renderer/hooks/useMcpStatus.ts` | 읽기 + 구독 |
| `renderer/components/Sidebar.tsx` | 하단 상태 줄 |

**`core.mcpPort()`는 남긴다.** 기존 테스트가 쓰고 있고, `status()`와 달리 "지금 이 순간 서버 핸들이 있는가"를 본다.

## 6. 화면

사이드바 맨 아래, 기존 항목들과 구분선으로 나눈 한 줄.

```
● MCP :53021        ← listening (초록 점)
○ MCP 시작 중        ← starting (회색 점)
● MCP 연결 실패      ← failed (빨간 점, title에 사유)
```

**포트를 보여주는 이유:** 지금 같은 진단 상황에서 "서버가 정말 떴는가"와 "몇 번 포트인가"를 눈으로 확인할 수 있어야 한다. 실패 사유는 길어질 수 있으므로 `title`에 넣어 hover로 본다.

`aria-live="polite"`를 준다 — 상태가 바뀌면 스크린 리더가 읽는다.

## 7. 검증

| 항목 | 방법 |
|---|---|
| 부팅이 포트를 연다 | `core/index.test.ts` — 기존 테스트를 뒤집는다 |
| 기동 실패가 앱을 죽이지 않는다 | 단위 — `start()`가 던지지 않고 `failed` 상태가 된다 |
| 상태 전이가 emit된다 | 단위 — `onMcpStatus` 리스너가 `listening`을 받는다 |
| 읽기와 구독이 둘 다 배선됐다 | 렌더러 — 훅이 초기값을 읽고, 이벤트로 갱신된다 |
| 사이드바가 포트를 보여준다 | 렌더러 — `listening`일 때 포트 문자열이 보인다 |

**배선 한 줄을 겨냥한다.** `App.tsx`가 `Sidebar`에 상태를 내려보내는 줄, `ipc/runs.ts`가 중계하는 줄은 각각 지웠을 때 빨개지는 테스트를 갖는다 — 3a·3b가 두 번 다 이 자리에서 새어나갔다.
