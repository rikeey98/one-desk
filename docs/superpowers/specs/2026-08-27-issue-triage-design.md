# 이슈 훑기 설계 — 던지기와 정리를 떼어놓기

**날짜:** 2026-08-27
**상태:** 승인됨
**근거 문서:** 전체 설계 §5(데이터 모델) · §9(UI 구조), 본문 편집 설계 `2026-08-14-issue-memo-body-design.md` §3(상태) · §6(낙관적 잠금), 4단계 설계 `2026-08-12-stage4-mcp-design.md` §8(권한)

---

## 1. 문제

사용자가 실측으로 말한 통증은 하나다. **이슈의 존재 자체를 잊는다.**

한 프로젝트에 살아있는 이슈가 50개쯤 되고, 그것들이 서로 다른 창구에서 온다 — 고객/현업 요청, 기획 요청, 회의에서 나온 말, 개발하다 발견한 것. 하나를 하다 우선순위가 튀고, 돌아왔을 때 무엇이 있었는지가 남아 있지 않다.

새는 곳이 **두 군데**라는 것이 확인됐다.

**적히기 전에 샌다.** 회의 중에, 코드를 보다가 발견한 것을 앱에 옮겨 적는 행위가 일어나지 않는다. 지금 이슈를 만들려면 제목만 치면 되므로(`AddForm`) 입력 자체는 이미 가볍다 — 문제는 **분류 축이 붙는 순간 이 가벼움이 사라진다**는 것이다.

**적힌 뒤에 묻힌다.** 여기엔 기계적 원인이 둘 있다.

1. **정렬이 `updatedAt DESC`다** (`core/db/repositories/issue.ts:103`). 최근 손댄 것이 위로 온다 — 즉 **안 본 것일수록 아래로 밀린다.** 잊고 싶지 않은 것을 정확히 반대 방향으로 보낸다.
2. **`list`에 status 필터가 없다** (`:89`). `done`이 살아있는 이슈 사이에 그대로 섞인다. 절반이 done이면 체감 밀도가 두 배다.

그리고 세 번째, 더 조용한 오염이 있다. **`updatedAt`은 agent도 올린다.** MCP `update_issue`가 이슈를 고치면 `updatedAt`이 갱신되고, 사람이 그 이슈를 본 적이 없는데도 목록 맨 위로 올라온다. 지금 정렬이 `updatedAt` 기준이므로 **이 오염은 이미 진행 중이다.**

## 2. 범위

### 들어가는 것

- `issue`에 분류 축 셋(`source`·`kind`·`priority`)과 `triagedAt`·`seenAt`
- **훑기(triage)** — 정리 안 된 이슈를 한 건씩 넘기며 축을 찍는 흐름. `IssuePanel`의 상세 자리에서 돈다
- 목록의 **그룹핑 · 접기 · 축 전환**, 그룹 안의 정렬 역전, `done` 분리
- **방치 배지** — 오래 안 본 이슈에 표식
- MCP `create_issue`·`update_issue`가 축을 받는다 — agent가 회의 메모를 이슈로 쪼개 넣을 때 축까지 찍게

### 빠지는 것

**전역 단축키.** 어느 앱에서든 한 줄을 던지는 입구다. `globalShortcut` + 별도 창 + 트레이 상주가 따라온다. 사용자가 명시적으로 뺐다 — 앱 안 입력으로 먼저 써보고, 창 전환이 실제로 걸리면 그때 붙인다.

**스누즈.** B안의 "미루기"인데 `priority`와 역할이 겹친다. 미루고 싶으면 `언젠가`로 내리면 된다. 상태 하나를 줄이는 쪽을 택했다. 필요해지면 그때 붙인다.

**축 값 커스터마이즈.** enum을 코드에 박는다. workspace별 설정으로 만들면 테이블과 설정 화면이 하나씩 늘고, **처음 쓸 때 빈 목록부터 채워야 한다** — 그 마찰이 이 스펙이 없애려는 마찰과 같은 종류다.

**검색·필터·정렬 UI.** CLAUDE.md에 이미 별도 후보로 잡혀 있다. 그룹핑이 들어가면 필요가 줄어들 수 있으니 **이것을 먼저 쓴 뒤에** 판단한다.

**이슈 ↔ run(대화) 연결.** "돌아왔을 때 어디까지 했는지"를 복원하는 기능이다. 사용자가 통증 1순위로 *존재 망각*을 골랐으므로 이번엔 뺀다. **다음 라운드 1순위 후보로 기록한다.**

**메모 쪽 대칭 적용.** §9에서 따로 다룬다 — 이건 그냥 빼는 것이 아니라 기존 규칙과 정면으로 부딪히는 자리다.

## 3. 데이터 모델

`issue`에 다섯 칸을 더한다. **`status`는 건드리지 않는다.**

```ts
source     text('source',   { enum: ['customer', 'plan', 'meeting', 'dev'] })
kind       text('kind',     { enum: ['bug', 'feature', 'refactor', 'docs', 'research'] })
priority   text('priority', { enum: ['urgent', 'week', 'someday'] })
triagedAt  integer('triaged_at')
seenAt     integer('seen_at')
```

다섯 칸 모두 nullable이다. **"아직 안 정해졌다"가 정상 상태**이기 때문이다 — 그것이 이 설계의 핵심이다.

표시 라벨은 렌더러가 갖는다. DB에는 영어 코드가 들어가고 화면에는 한국어가 나온다.

| 축 | 코드 → 라벨 |
|---|---|
| `source` | `customer` 고객 · `plan` 기획 · `meeting` 회의 · `dev` 개발중 |
| `kind` | `bug` 버그 · `feature` 기능 · `refactor` 리팩 · `docs` 문서 · `research` 조사 |
| `priority` | `urgent` 긴급 · `week` 이번주 · `someday` 언젠가 |

`priority`는 **순서가 있다.** 정렬에 쓰이므로 enum의 나열 순서가 곧 급한 순서다.

### `status`에 `inbox`를 넣지 않는 이유

넣으면 `status`가 *진행 상태*와 *정리 여부* 두 뜻을 겸한다. 던져놓고 바로 착수한 이슈는 **`doing`이면서 미분류**일 수 있는데 한 컬럼으로는 표현할 수 없다. `closedAt`이 `status`에서 파생된다는 기존 규칙(CLAUDE.md 데이터 규칙)도 같이 흔들린다 — `inbox → done`이 무슨 뜻인지 정해야 한다.

**정리 여부는 `triagedAt` 한 칸으로 분리한다.** null이면 훑기 대기열이다.

### `triagedAt`은 파생된다 — 호출자가 넘기지 않는다

```
triagedAt := (source ≠ null ∧ kind ≠ null ∧ priority ≠ null) 인 순간 Date.now()
             셋 중 하나라도 null로 되돌아가면 null
```

`closedAt`이 `status`에서 파생되는 것과 **같은 모양**이다. 호출자가 따로 관리하게 두면 "축은 다 찍혔는데 미분류로 남은 이슈" 같은, 화면에서 설명할 수 없는 상태가 생긴다.

이 규칙 덕분에 **"정리 안 됨"의 정의가 하나로 고정된다.** 훑기 화면의 `[다음 →]`이 세 축을 다 요구하는 것도, agent가 MCP로 축을 부분만 채웠을 때 그 이슈가 대기열에 남는 것도, 전부 이 한 줄에서 나온다.

### "정리 안 됨"과 "미지정"은 다른 말이다

화면에 나오는 두 표현이 서로 다른 것을 가리키므로 **단어를 갈라 쓴다.**

| 표현 | 뜻 | 판정 |
|---|---|---|
| **정리 안 됨** | 훑기 대기열. 배너와 훑기 흐름이 쓴다 | `triagedAt IS NULL` |
| **미지정** | 지금 묶은 축의 값이 비어 있음. 그룹 이름으로 쓴다 | 그 축이 null |

같은 단어를 두 뜻으로 쓰면 "정리 안 됨 0건인데 미분류 그룹에 3개가 있다"는 화면이 나온다 — 백필된 이슈(아래)에서 실제로 생기는 조합이다.

### `seenAt` — 방치 판정에 `updatedAt`을 쓰면 안 된다

⚠️ **`updatedAt`은 agent도 올린다.** MCP `update_issue`가 본문을 고치면 `updatedAt`이 갱신된다. 사람이 그 이슈를 본 적이 없어도 "방금 본 것"이 된다. 이 신호로 방치를 판정하면 **agent가 건드린 이슈일수록 조용해진다** — 정확히 거꾸로다.

그래서 `seenAt`을 따로 둔다. **사람이 상세를 열었을 때만** 찍힌다.

두 가지 제약이 붙는다.

**① `seenAt` 쓰기는 `updatedAt`을 건드리면 안 된다.** 건드리면 열려 있는 `IssueDetail`의 낙관적 잠금 기대값(`expected.current`)이 즉시 낡아, 다음 자동 저장이 **사용자 자신의 열람을 agent의 편집으로 착각해 유령 충돌 배너를 띄운다.** 이 프로젝트가 이미 한 번 겪은 함정이다(CLAUDE.md · 본문 편집 설계 §6). 그래서 `buildPatch`를 타지 않는 전용 경로 `markSeen(id)`를 만든다.

**② `markSeen`은 목록을 다시 읽게 하지 않는다.** 그룹 안의 정렬이 `seenAt` 오래된 순(§5)이므로, 열자마자 목록을 갱신하면 **방금 연 이슈가 그 자리에서 맨 아래로 점프한다.** 클릭한 항목이 눈앞에서 도망가는 화면이 된다. 반영은 다음 마운트로 미룬다.

**③ 훑기는 `seenAt`을 찍지 않는다.** 분류와 열람은 다른 행위다. 훑어서 `언젠가`로 분류한 이슈는 *분류는 됐지만 손대지는 않은* 상태이고, 방치 시계는 계속 가야 한다. 축을 찍었다는 이유로 시계가 리셋되면 훑기가 방치를 감추는 도구가 된다.

### 마이그레이션 (`0003`)

컬럼 다섯을 더하고 **기존 행을 `triaged_at = created_at`으로 백필한다.**

안 하면 앱을 켜자마자 **"정리 안 됨 50건"**이 뜬다. 이미 쓰고 있던 이슈가 전부 대기열로 쏟아지면 첫 화면이 이 기능을 쓰지 말라고 설득하는 꼴이 된다.

축 셋은 null로 남는다. 즉 백필한 이슈는 **`triagedAt`이 있으면서 축이 비어 있다** — 위의 파생 규칙과 어긋나는 유일한 상태이고, 의도된 것이다. 그룹핑에서는 각 축의 **"미지정"** 그룹에 들어가고, 훑기 대기열에는 뜨지 않는다.

**백필은 파생 규칙 밖이다. 하지만 영구 예외는 아니다.** 그 이슈의 축을 처음 건드리는 순간부터 규칙이 적용되므로, 축 하나만 찍고 나가면 `triagedAt`이 지워져 대기열로 들어간다. 이것이 옳은 동작이다 — *분류를 시작했으면 마저 하라*는 뜻이고, 건드리지 않는 한 그 이슈는 영원히 조용하다. 예외가 시간이 지나며 저절로 사라진다.

> `root_run_id`를 NOT NULL로 만들려다 겪은 것과 같은 함정을 피한다 — SQLite에서 컬럼 제약을 바꾸려면 테이블을 다시 만들어야 하고, 그 `DROP TABLE issue`가 `issue_repo`의 cascade를 태워 모든 repo 태그를 지운다. **전부 nullable로 더하기만 한다.**

## 4. 훑기

### 새 화면을 만들지 않는다

`IssuePanel`의 상세 자리(`panel-split-detail`)를 쓴다. 이슈 상세를 여는 **바로 그 자리**다.

```
┌─ Issues ───────────────────┬─ 훑어보기 (6건 중 1번째) ──┐
│ ⚠ 정리 안 됨 (6)   [훑기]  │                            │
│ 묶기: [급함 ▾]             │  회원 탈퇴 플로우 문의      │
│ ▾ 미지정 (6)               │                            │
│    회원 탈퇴 플로우 문의    │  출처 [고객][기획][회의][개발]│
│ ▾ 긴급 (3)                 │  성격 [버그][기능][리팩][문서]│
│    로그인 후 리다이렉트…   │  급함 [긴급][이번주][언젠가] │
│ ▸ 이번 주 (8)              │  repo [api][web]           │
│ ▸ 언젠가 (21)              │                            │
│ ▸ 완료 (37)                │  [건너뛰기]       [다음 →] │
└────────────────────────────┴────────────────────────────┘
```

이미 있는 동적 3컬럼(선택한 패널이 커지는 것, 본문 편집 설계 §4)을 그대로 쓴다. **새 라우팅도, 새 모달도, `App.tsx`의 `openItem` 계약 변경도 없다.**

### 상태는 `IssuePanel`이 갖는다

```ts
const [triaging, setTriaging] = useState(false)
```

`App.tsx`에 올리지 않는다. 다른 컴포넌트가 이 상태를 쓰지 않기 때문이다 — 본문 편집 설계 §3이 `openItem`을 `App.tsx`에 둔 이유(두 패널이 자리를 다툼)가 여기엔 없다.

부수 효과로 **변이에 강해진다.** CLAUDE.md가 두 단계 연속으로 경고한 새는 자리는 예외 없이 *`App.tsx`가 자식에게 내려보내는 prop 한 줄*이었다. 이 기능은 그 자리를 늘리지 않는다.

### 흐름

| 동작 | 결과 |
|---|---|
| `[훑기]` | `onOpen(첫 "정리 안 됨" id)` + `setTriaging(true)` — 패널이 확장되고 상세 자리에 훑기 카드가 뜬다 |
| `[다음 →]` | 고른 축을 저장 → 다음 "정리 안 됨"으로 `onOpen`. 없으면 `setTriaging(false)`, 상세 자리를 비운다 |
| `[건너뛰기]` | 저장하지 않고 다음으로. **대기열에 남는다** |
| 목록에서 다른 이슈 클릭 | `setTriaging(false)` — 훑기가 끝나고 평소의 `IssueDetail`이 돌아온다 |

`[다음 →]`은 **세 축이 다 찍혀야 활성화된다.** §3의 파생 규칙과 짝을 이룬다 — 부분만 찍고 넘어갈 수 있으면 `triagedAt`이 안 찍혀 그 이슈가 대기열에 그대로 남고, 사용자는 방금 처리한 것이 왜 다시 나오는지 알 수 없다.

repo 태그는 **선택이다.** 이미 `issue_repo`로 존재하고 `list`의 repo 필터(`:95-100`)가 "태그 없음"을 공통 항목으로 취급하므로, 안 찍어도 아무것도 깨지지 않는다.

### 대기열이 비면

배너와 훑기 카드가 함께 사라진다. **"정리 안 됨 0건"을 그리지 않는다** — 0을 보여주는 배너는 화면에 상주하는 잔소리가 된다.

## 5. 목록

### 그룹핑

묶는 축을 고를 수 있다: `묶기: [급함 ▾]` — 급함 · 출처 · 성격 · repo. 사용자가 네 축을 다 쓴다고 했으므로 드롭다운 하나의 값어치가 크다. 기본값은 **급함**이다.

그룹 순서는 각 축의 enum 순서를 따르고, **그 축의 값이 null인 것이 맨 위 "미지정" 그룹**이다. 위로 올리는 이유는 하나다 — 아래에 두면 그것이 정확히 이 스펙이 없애려는 "묻힘"이 된다.

접힌 그룹도 **개수는 항상 보인다.** `▸ 언젠가 (21)`. 안 보여도 있다는 것은 알아야 한다. 이것이 A안을 고른 이유 자체이므로 개수를 숨기는 변형은 이 설계가 아니다.

### 정렬 — 뒤집는다. 그리고 **저장소가** 한다

```sql
ORDER BY (seen_at IS NULL) DESC, seen_at ASC, created_at ASC
```

**안 본 것이 위로 온다.** `seenAt`이 null인 것(한 번도 안 연 것)이 가장 위다 — 방금 던져 넣은 이슈가 맨 위에 온다. 지금의 `updatedAt DESC`(`:103`)를 뒤집는 자리다.

**정렬은 저장소가 하고 `issueGroups`는 그 순서를 보존하며 나누기만 한다.** 양쪽에서 정렬하면 규칙이 두 벌이 되고, 어긋났을 때 어느 쪽이 옳은지 판정할 곳이 없어진다. 그룹핑은 **안정 분할**이므로 저장소 순서가 각 그룹 안에 그대로 남는다.

### `done`

그룹핑에서 **빼고** 맨 아래 접힌 `▸ 완료 (37)` 한 줄로 둔다. 필터 토글을 따로 만들지 않고 **같은 접기 메커니즘을 재사용**한다 — 화면에 새 컨트롤이 늘지 않고, "숨겼지만 개수는 보인다"는 성질도 그대로 얻는다.

### 방치 배지

`now - (seenAt ?? createdAt) > 14일`이면 `⚠` 배지를 붙인다. 상수 하나이고 설정 화면은 없다.

`seenAt`이 null일 때 `createdAt`으로 떨어지는 것이 중요하다. 그러지 않으면 **한 번도 안 연 이슈가 영원히 방치로 잡히지 않는다** — 가장 잊히기 쉬운 것이 배지를 못 받는다.

`done`에는 붙이지 않는다.

### 목록 줄의 상태 칩은 여전히 읽기 전용이다

본문 편집 설계 §9가 정한 경계를 그대로 지킨다. 축 칩(`#버그` `#고객`)도 **표시 전용**이고 목록에서 클릭해 바꿀 수 없다. 여기서 잠기지 않은 쓰기를 하면 그 쓰기가 `updatedAt`을 올려 열려 있는 상세의 기대값을 낡게 만들고, 유령 충돌 배너가 뜬다.

축을 바꾸는 자리는 **상세와 훑기 둘뿐**이다.

---

## 6. MCP

`create_issue`와 `update_issue`가 축 셋을 옵션으로 받는다.

```ts
source:   SOURCE.optional(),
kind:     KIND.optional(),
priority: PRIORITY.optional()
```

안 주면 정리 안 된 채로 쌓여 훑기 대기열에 들어간다. **다 주면 `triagedAt`이 파생돼 훑기를 건너뛴다**(§3).

이것이 캡처의 두 번째 경로를 완성한다 — 회의 메모 덩어리를 대화에 붙여넣고 "이슈로 쪼개서 축까지 찍어 넣어줘"라고 하면, agent가 `create_issue`를 여러 번 부르고 사용자는 훑기를 아예 안 해도 된다. **읽는 쪽(`list_issues`·`get_issue`)은 행 전체를 돌려주므로 자동으로 새 필드를 본다.**

`read_only` 권한에서는 지금처럼 쓰기 도구가 등록되지 않는다(4단계 설계 §8). 축이 붙는다고 이 경계는 움직이지 않는다.

⚠️ **`update_issue`로 축을 지울 수 있어야 하는가**는 이번 범위 밖이다. `.optional()`은 "안 줬다"와 "null로 지워라"를 구분하지 못한다. 지금은 **주면 설정, 안 주면 유지**로만 두고, 지우는 것은 사람이 상세에서 한다. 필요해지면 명시적인 sentinel을 붙인다.

## 7. 오류 처리

축 저장은 **잠기지 않은** `update`를 탄다 — `updateIfUnchanged`가 아니다. 본문 편집 설계 §6의 낙관적 잠금은 여기 걸리지 않는다.

의도적이다. agent는 MCP로 이슈 본문을 끊임없이 고친다. 잠긴 경로를 썼다면 agent가 방금 본문을 채운 이슈일수록 사람이 축을 찍으려 할 때 낡은 `expectedUpdatedAt`에 걸려 충돌하고, 하필 **분류가 가장 필요한 이슈에서** 훑기가 막힌다. 훑기는 축 셋만 쓰고 본문은 건드리지 않으므로 애초에 사람과 agent가 같은 글자를 다툴 자리가 없다 — 잠글 대상이 없다.

그러므로 훑기 중 버전 충돌은 일어나지 않는다. `triageError`와 배너가 잡는 것은 **하드 실패**(IPC 왕복 오류, 저장소/DB 오류)뿐이다. 그런 실패가 나면 **그 한 건에서 멈추고 배너를 띄운다.** 다음으로 자동으로 넘어가지 않는다 — 넘어가면 사용자가 방금 찍은 축이 어디로 갔는지 모른 채 대기열만 줄어든다.

`markSeen` 실패는 **조용히 삼킨다.** 열람 기록은 부수적이고, 이슈를 여는 행위가 이것 때문에 실패하면 안 된다. 다만 `core/`는 `console.error`를 부르지 않으므로 주입된 `onError`로 흘려보낸다(4단계에서 정리한 규칙).

## 9. ⚠️ 대칭 규칙은 여기서 끝난다

CLAUDE.md는 `issue.ts` ↔ `memo.ts`, `useIssues` ↔ `useMemos`의 중복을 **의도된 것**으로 두고 이렇게 못박고 있다.

> **대신 두 쌍을 항상 대칭으로 유지한다.** 한쪽을 고치면 반드시 다른 쪽도 고친다. 어긋나면 그건 진짜 결함이다.

**이 스펙은 이슈에만 붙는다.** 메모에는 `source`도 `triagedAt`도 훑기도 없다.

이것은 규칙 위반이 아니다. 같은 문서가 규칙의 **근거**를 이렇게 적어놨다.

> 이슈에는 앞으로 상태 전이, agent 실행(run) 연결, `needs_answer`가 붙지만 메모에는 붙지 않는다.

**비대칭은 처음부터 예정돼 있었고, 이번이 그 분기점이다.** 메모는 "적어두는 것"이고 이슈는 "처리해야 하는 것"이다. 분류·우선순위·방치 판정은 전부 *처리*에 딸린 개념이라 메모에 붙일 자리가 없다.

**그러므로 CLAUDE.md의 해당 절을 이 작업에서 함께 고친다.** 안 고치면 두 방향으로 조용히 깨진다.

- 누군가(또는 다음 세션의 agent가) "대칭을 맞추려고" `memo.ts`에 `triagedAt`을 붙인다
- 반대로 "대칭이 깨졌으니 결함"이라 판단해 이 기능을 되돌린다

고칠 내용: **`body`·`title`·`repoIds`·삭제 등 두 쌍에 공통인 것은 계속 대칭으로 유지한다. 분류 축·`triagedAt`·`seenAt`·훑기는 이슈 전용이며, 메모에 옮기지 않는다.**

## 10. 테스트와 변이표

각 항목은 **그 줄을 지우거나 뒤집었을 때 빨개지는 테스트**가 있어야 한다.

| # | 변이 | 잡는 테스트 |
|---|---|---|
| 1 | `triagedAt` 파생을 지우고 호출자 값을 그대로 쓴다 | 저장소: 축 셋을 다 주면 `triagedAt`이 찍히고, 하나를 null로 되돌리면 다시 null |
| 2 | 마이그레이션의 백필을 뺀다 | 마이그레이션: 기존 행이 `triagedAt = createdAt`을 갖는다 |
| 3 | `markSeen`이 `buildPatch`를 타게 한다 | 저장소: `markSeen` 후 `updatedAt`이 **그대로**다 |
| 4 | 정렬을 `updatedAt DESC`로 되돌린다 | 저장소: `seenAt`이 오래된 것이 먼저 온다 · `seenAt`이 null인 것이 맨 앞 |
| 5 | 방치 판정의 `?? createdAt` 폴백을 뺀다 | `issueGroups`: 한 번도 안 연 오래된 이슈에 배지가 붙는다 |
| 6 | 접힌 그룹의 개수를 숨긴다 | `IssuePanel`: 접힌 그룹에서도 개수 텍스트가 보인다 |
| 7 | "미지정" 그룹을 맨 아래로 옮긴다 | `issueGroups`: 미지정이 첫 그룹이다 |
| 7b | 백필된 이슈(축 없음 + `triagedAt` 있음)를 대기열에 넣는다 | 저장소: 백필 행은 대기열 개수에 안 잡히고, 축 하나를 찍으면 잡힌다 |
| 8 | `done`을 그룹핑에 다시 섞는다 | `issueGroups`: `done`이 어느 축 그룹에도 없고 별도 그룹에만 있다 |
| 9 | `[다음 →]`을 축이 덜 찍혀도 활성화한다 | `TriageCard`: 두 축만 찍으면 버튼이 disabled |
| 10 | `[건너뛰기]`가 `triagedAt`을 찍게 한다 | `IssuePanel`: 건너뛴 이슈가 대기열 개수에 남는다 |
| 11 | 훑기가 `markSeen`을 부르게 한다 | `TriageCard`: 훑은 뒤에도 `seenAt`이 null |
| 12 | `markSeen`이 목록을 refresh하게 한다 | `IssuePanel`: 이슈를 열어도 목록 순서가 그대로 |
| 13 | MCP `create_issue`에서 축 파라미터를 뺀다 | `tools.test.ts`: 축을 주고 만든 이슈가 `triagedAt`을 갖는다 |
| 14 | 배너를 0건일 때도 그린다 | `IssuePanel`: 정리 안 된 이슈가 없으면 배너가 없다 |

### e2e (`e2e/triage.e2e.ts`)

**화면을 벗어나지 않고** 한 바퀴를 돈다.

1. 한 줄 던지기로 이슈를 만든다 → 배너가 **"정리 안 됨 1건"**
2. `[훑기]` → 상세 자리에 훑기 카드
3. 축 셋을 찍고 `[다음 →]` → 배너가 사라진다
4. 그 이슈가 **해당 그룹 안에** 나타난다

> 다른 화면에 갔다 오면 패널이 다시 마운트돼 구독이 죽어도 통과해 버린다 — `e2e/mcp.e2e.ts`가 같은 이유로 화면을 벗어나지 않는다.

> `getByRole('button', { name: '…' })`은 substring 매칭이 기본이다. `[다음 →]`처럼 짧은 라벨은 도크 토글과 충돌할 수 있으니 `exact: true`를 쓴다.
