# 대화 — 일회용 run에서 이어지는 대화로

**상태:** 설계 확정, 구현 전
**날짜:** 2026-08-18

## 1. 무엇을 고치는가

세션을 이어받는 배관은 이미 있다. `core/execution.ts`의 `resume()`이 원본 run의 `externalSessionId`를 `claude --resume`으로 넘기고, 새 run에 `parentRunId`를 걸어 체인을 만든다. **일회용인 것은 세션이 아니라 UI다.**

그 기능에 닿는 유일한 통로가 인박스다. run이 끝나야 인박스에 뜨고, 거기서 "이어서 실행"을 눌러야 실행 패널이 resume 모드로 바뀐다(`InboxPanel.tsx` → `App.tsx`의 `startResume`). 실행이 시작되면 `resumeFrom`이 즉시 풀리므로 다음 턴에 또 인박스로 가야 한다. 대화록도 없다 — 턴마다 별개의 run 탭이고, 이전 턴을 한 흐름으로 보는 화면이 없다.

이 작업은 **채팅처럼 이어지는 대화**를 만든다. 배관을 새로 놓는 것이 아니라, 이미 있는 체인 위에 "대화"라는 개념과 화면을 얹는다.

**모든 실행이 대화다.** 일회용이라는 개념은 사라진다. 한 번 돌리고 말면 1턴짜리 대화로 남고, 과거 run도 전부 대화로 보인다. 사용자가 "이건 이어갈 수 있나"를 미리 결정할 필요가 없어진다.

## 2. 데이터 모델

`run`에 `rootRunId TEXT`를 더한다. 인덱스는 `(rootRunId, createdAt)`.

**승계 규칙:** `parentRunId`가 없으면 자기 `id`, 있으면 부모의 `rootRunId`.

**컬럼은 nullable이다 — NOT NULL로 만들지 않는다.** SQLite는 기본값 없는 `NOT NULL` 컬럼을 `ALTER TABLE ADD COLUMN`으로 붙일 수 없어 테이블을 통째로 다시 만들어야 하는데, **그 `DROP TABLE run`이 `run_context_item`의 `ON DELETE cascade`를 건드린다.** drizzle이 앞에 붙이는 `PRAGMA foreign_keys=OFF`는 마이그레이션이 트랜잭션 안에서 돌기 때문에 무시된다(SQLite는 트랜잭션 안의 이 PRAGMA를 무시한다). 결과는 **모든 run의 맥락 기록이 조용히 사라지는 것**이다.

그래서 `ALTER TABLE ADD COLUMN`으로 nullable하게 붙이고 백필한다. 백필 후에는 `NULL`이 남지 않지만, 읽는 쪽은 `rootRunId ?? id`로 해석해 낡은 행이 있어도 자기 자신을 뿌리로 본다.

**자기 참조 외래키는 붙이지 않는다.** 스키마가 `parentRunId`에 대해 이미 그렇게 정해뒀다 — drizzle에서 타입 순환을 만들고, 원본 run이 지워져도 이어서 실행한 run의 기록은 남아야 한다. 같은 근거가 그대로 적용된다.

**백필:** 기존 run 대부분은 부모가 없어 자기 자신이다. 부모가 있는 것만 체인을 따라 뿌리를 찾는다 — 마이그레이션 때 재귀 CTE 한 번.

**대화의 메타는 root run 행이 맡는다.** 별도 테이블을 만들지 않는다.

| 대화의 속성 | 어디서 오는가 |
|---|---|
| 제목 | root run의 `userPrompt` 첫 줄 (`Dock.tsx`의 `label()`을 그대로 쓴다) |
| 확인 표시 | root run의 `reviewedAt` / `reviewedKind` |
| 마지막 활동 | 그 대화 run들의 `max(createdAt)` — 목록 정렬에 쓴다 |
| 현재 상태 | **마지막 턴**의 `status` / `needsAnswer` |
| 잠긴 값 | `agentKind` / `cwd` — 세션을 준 run에서 가져온다 (§3-1) |

**왜 `conversation` 테이블이 아닌가.** 대화를 일급 개체로 만들면 제목 편집 같은 확장이 쉬워지지만, 테이블·FK와 함께 "대화는 있는데 run이 하나도 없는 상태"라는 새 경우가 생긴다. 지금 필요한 것에 비해 크다. 제목 편집이 실제로 필요해지면 그때 연다.

**왜 매번 파생하지 않는가.** `parentRunId`만으로도 뿌리를 찾을 수는 있다. 하지만 대화 목록을 그릴 때마다 재귀 CTE가 필요하고, "확인 표시는 체인 전체를 봐야 한다"는 규칙이 코드 곳곳에 흩뿌려진다. 뿌리를 비정규화해 들고 다니면 그 해석이 한 곳에 모인다.

## 3. 실행 경로

두 군데를 고친다.

### 3-1. 이어받을 세션을 core가 고른다

지금 `resume()`은 호출자가 준 `parentRunId`의 세션 id를 그대로 쓰고, 없으면 던진다.

```ts
if (!parent.externalSessionId) {
  throw new Error('이어받을 세션이 없습니다. 새 실행으로 시작하세요.')
}
```

**이 조건이 대화에서 체인을 끊는다.** preflight 실패나 MCP 준비 실패로 끝난 run은 프로세스가 뜬 적이 없어 세션 id가 `null`이다. 3턴째가 그렇게 실패하면 "마지막 run에서 이어받기"가 불가능해진다 — 대화 자체는 2턴까지 멀쩡히 살아 있는데도.

그래서 `resume()`은 **대화 id를 받아 체인에서 세션 id를 가진 가장 최근 run을 고른다.** 세션 id를 가진 run이 하나도 없을 때만 던진다.

**이 규칙은 렌더러가 아니라 core에 둔다.** `agentKind`와 `cwd`를 잠그는 규칙을 core에 둔 것과 같은 근거다 — 나중에 `core/`를 별도 데몬으로 뗄 때 따라가야 한다.

`agentKind`·`cwd`는 계속 잠긴 값이다. 세션을 준 run에서 가져온다(뿌리와 같은 값이지만, 출처를 세션 쪽에 두는 편이 규칙과 일치한다).

### 3-2. 예약된 다음 턴은 진짜 `pending` run이다

한 턴이 도는 중에도 다음 말을 칠 수 있다. Claude Code는 이전 프로세스가 끝나야 `--resume`이 되므로 **실행 자체는 무조건 순차**이고, 사용자가 보내기를 누른 말은 "다음 턴으로 예약됨" 상태로 쌓였다가 앞 턴이 끝나면 자동으로 나간다.

**예약을 렌더러 메모리에 두지 않는다.** 패널이 언마운트되면(다른 화면에 갔다 오는 것만으로) 조용히 죽는다. 4단계에서 `IssuePanel`/`MemoPanel`이 run 완료를 구독하지 않아 겪은 것과 정확히 같은 함정이다.

**DB에 `pending` run으로 만든다.** 화면을 벗어나도 살아남고, 취소는 기존 `cancel()`의 대기 중 취소 분기가 처리한다 — **단, 확인 표시를 찍는 대상은 취소하는 그 턴이 아니라 뿌리다** (아래 §5의 재개 규칙과 맞물린다. 최초 설계는 이 둘을 따로 적어 모순을 남겼었다 — §5는 "확인/보관은 root run에" 기록한다고 했는데 여기는 "기존 `cancel()`이 그대로 처리한다"고만 적어, 턴 id에 찍는 옛 구현이 그대로 남아도 이 문장만으로는 안 걸렸다. 인박스 소속 판정이 뿌리 기준으로 바뀐 이상 확인 표시도 뿌리에 찍어야 한다). 앱을 재시작하면 `reapStale`이 `canceled`로 정리한다 — 이미 있는 동작이고, 사용자가 못 보는 사이에 실행되지 않는다는 점에서 옳다.

두 가지가 따라온다.

**(a) `resumeSessionId`를 `beginRun()` 시점에 해석한다.** 지금은 `launch()`가 미리 계산해 넘긴다. 예약할 때는 앞 턴이 아직 안 끝나 세션 id가 없으므로, 실제로 띄우는 순간에 체인을 다시 봐야 한다.

**(b) `RunQueue`에 `groupKey`(= `rootRunId`)를 더하고 "한 그룹에서 동시에 하나만" 규칙을 넣는다.** 없으면 슬롯이 빌 때 같은 대화의 두 턴이 동시에 떠서 깨진다. 대화끼리는 지금처럼 전역 상한 안에서 병렬이다.

**예약은 대화당 하나다.** 이미 예약이 있으면 전송 버튼이 잠기고, 취소하면 풀린다.

## 4. UI — 도크가 대화창이 된다

전체 설계 §9가 실행 패널을 모달이 아니라 도크 확장으로 정한 이유는 "모달이 뜨면 뒤의 issue/memo를 클릭해 맥락을 담을 수 없다"였다. 대화 화면도 이 제약을 물려받는다 — **도크 안에 산다.**

### 4-1. 컴포넌트 재편

지금 도크는 `view: 'log' | 'new'`로 갈라져 `RunLog`(읽기)와 `RunPanel`(쓰기)를 번갈아 보여준다. 대화에서는 이 둘이 한 화면에 위아래로 붙는다.

| 컴포넌트 | 역할 |
|---|---|
| `ConversationPanel` (신규) | 위는 대화록, 아래는 입력. 새 대화는 대화록이 비어 있을 뿐 같은 컴포넌트다 |
| `Transcript` (신규) | 대화의 run들을 턴 버블로 그린다 |
| `RunLog` (재사용) | 각 턴의 '자세히'가 열릴 때만 `useRunEvents(run.id)`를 걸어 그 턴의 로그를 되살린다 |
| `RunPanel` (축소) | 입력부(composer)가 된다 |

**턴 버블.** `[내 지시]`는 `run.userPrompt` — 맥락이 합쳐진 `assembledPrompt`가 아니라 사용자가 친 것이다. `[답변]`은 `run.resultText`. 여기에 상태 배지와 `답변 필요` 배지가 붙는다.

**진행 중인 턴은 '자세히'가 기본으로 펼쳐진 채** 실시간으로 흐른다. 지난 턴은 접혀 있다.

**예약된 턴은 "대기 중" 버블 + 취소 버튼이다.** `pending` run이므로 취소는 기존 `client.runs.cancel(runId)`가 그대로 처리한다.

**입력부.** 대화록이 비었을 때만 작업 디렉토리·agent 선택이 보이고, 턴이 하나라도 있으면 지금의 `resume-locked` 표시처럼 잠긴 값으로 바뀐다. **권한과 모델은 매 턴 바꿀 수 있다** — 설계 §7의 "차단된 도구를 호출하면 사용자는 권한을 올려 이어서 실행한다"가 대화 안에서 자연스러워진다. 맥락 칩은 §6의 규칙 그대로다: 2턴부터는 기본으로 비어 있고 필요하면 추가한다.

### 4-2. 도크 탭 — 묶는 일은 렌더러에서 한다

`+ 새 실행` → `+ 새 대화`. run마다 하나이던 탭이 대화마다 하나로 줄고, 탭의 상태 배지는 **마지막 턴**에서 온다.

`useRuns(workspaceId)`는 그대로 둔다 — 평평한 run 목록을 주고 `onRunUpdate`를 구독하는 지금의 동작이 대화에도 그대로 맞다. **묶는 것은 그 목록 위의 순수 함수다**: `renderer/conversation.ts`가 `rootRunId`로 그룹을 만들고 마지막 턴을 고른다. `inbox.ts`가 `status`/`needsAnswer`에서 카테고리를 파생하는 것과 같은 패턴이고, 같은 이유로 테스트하기 쉽다.

**인박스는 다르다 — core에서 바꾼다.** 인박스 목록과 배지는 렌더러가 파생하는 것이 아니라 `client.runs.inbox()` / `client.runs.inboxCounts()`가 돌려주는 core 쿼리다(`useInbox.ts`). 그래서 §5의 변경은 저장소 쿼리에서 일어난다.

### 4-3. `App.tsx`

**`resumeFrom` 상태가 사라진다.** 대화창이 대화록과 입력을 함께 갖고 있어서 "resume 모드로 진입"이라는 개념이 필요 없다. `focusRun`은 `focusConversationId`가 된다.

**`draftPrompt`/`draftCwd`는 남는다.** "다시 실행"은 여전히 **새 대화**를 프리필하는 동작이다. `draftCwd`가 빠지면 첫 repo로 실행돼 엉뚱한 저장소가 편집된다(권한 기본값이 `edit`이다).

## 5. 인박스

**항목 단위가 대화(root run)다.** `client.runs.inbox()`가 미확인 run을 그대로 주던 것을 **대화별로 묶어 마지막 턴을 돌려주도록** 저장소 쿼리를 바꾼다. 카테고리는 그 마지막 턴에서 파생하므로 `inbox.ts`의 `inboxCategory()`와 카테고리 다섯 개는 그대로 두고 넘기는 run만 바뀐다.

`inboxCounts()`도 같은 기준으로 센다 — 배지가 대화 수를 말해야 목록과 어긋나지 않는다. 설계 §8이 적어둔 "`reviewed_at`에 인덱스가 없다"는 한계는 그대로지만, 새로 만드는 `(rootRunId, createdAt)` 인덱스가 묶는 쪽은 받쳐준다.

**확인/보관은 root run에 기록한다.** 사이드바 배지는 미확인 대화 수가 된다. **취소도 예외가 아니다** — `cancel()`이 확인 표시를 찍는 자리도 취소하는 그 턴의 id가 아니라 뿌리다. 턴 id에 찍으면 두 방향으로 깨진다: 예약된 뒤 턴을 취소하면 뿌리는 미확인인 채로 남아 그 대화가 "대기 중 취소됨"으로 인박스에 다시 뜨고, 반대로 뿌리(=첫 턴)를 실행 중에 취소하면 뿌리에 확인 표시가 찍혀 대화가 인박스에서 영원히 빠지는데 세션은 살아 있어 계속 이어갈 수 있다 — 그 뒤로 어떤 턴도(`needs_answer`로 멈춘 턴을 포함해) 조용히 인박스에 뜨지 않는다.

**재개 규칙: 새 턴이 생기면 뿌리의 확인 표시가 풀린다.** `markReviewed`는 한 번 찍히면 스스로 지워지지 않는다(멱등 — "처음 확인한 때"를 보존하려는 의도). 그런데 대화가 이어지는 모델에서는 그 성질이 다른 문제를 만든다: 대화를 한 번이라도 "확인함"으로 내리면 뿌리의 `reviewedAt`이 영원히 남아, 그 뒤에 이어지는 모든 턴이 — 다시 `needs_answer`로 멈추더라도 — 인박스에 다시는 뜨지 않는다. 그래서 **`create()`가 `parentRunId`를 받으면(=기존 대화에 새 턴을 잇는 것이면) 뿌리의 `reviewedAt`/`reviewedKind`를 지운다.** 이러면 "확인한 대화를 이어가면 다시 미확인 상태로 돌아온다"가 되어, `needs_answer`가 확인된 대화 뒤에 숨는 일이 없다. "처음 확인한 때"라는 기록은 그 대화가 재개되는 순간 더 이상 유효한 상태에 대한 것이 아니므로, 지워지는 것이 맞다.

**버튼 둘이 하나로 합쳐진다.** 지금은 "로그 보기"와 "이어서 실행"이 따로다. 대화창이 둘을 동시에 주므로 **"대화 열기"** 하나면 된다. `App.tsx`의 `openLog`와 `startResume`도 한 함수로 합쳐진다. "다시 실행"은 새 대화를 여는 별개 동작이라 남는다.

## 6. 검증

CLAUDE.md의 규칙을 그대로 따른다 — **회귀 테스트를 추가할 때는 대상 코드를 잠시 망가뜨려 그 테스트가 실제로 실패하는지 확인한다.**

| 무엇을 | 어떻게 |
|---|---|
| `rootRunId` 승계 | 부모가 없으면 자기 자신, 3단 체인이 전부 같은 뿌리 |
| 백필 | 기존 데이터에 마이그레이션을 걸고 체인이 하나로 묶이는지 |
| 큐 그룹 직렬화 | 같은 대화의 두 턴을 넣고 슬롯이 남아도 하나만 도는지. **`groupKey` 검사를 지웠을 때 실패하는지 확인한다** |
| resume 대상 선택 | 마지막 턴이 세션 id 없이 실패했을 때 그 앞 턴에서 이어받는지. 하나도 없으면 던지는지 |
| `beginRun` 시점 해석 | 예약할 땐 세션 id가 없던 run이 실행 시점에 앞 턴의 id를 집는지 |
| 인박스 파생 | 대화의 마지막 턴에서 카테고리가 나오는지, 확인 표시가 root에 기록되는지 |
| `Transcript` | 턴 순서, 진행 중 턴만 기본 펼침, pending 버블의 취소 버튼 |
| **배선 변이** | `App.tsx`가 내려보내는 `focusConversationId`·`onOpenConversation` 한 줄을 지우거나 다른 값으로 바꿨을 때 잡히는지 |

**e2e** (`pnpm test:e2e`) — 가짜 CLI로 3턴 대화: 1턴 실행 중에 2턴 입력(예약 확인) → 자동 전송 → 3턴. 인박스에 **한 줄만** 뜨는지. **화면을 벗어나지 않고 확인한다** — 다른 화면에 갔다 오면 재마운트로 통과해 버린다(`mcp.e2e.ts`가 같은 이유로 그렇게 쓰였다).

## 7. 빠지는 것

- **대화 제목 편집** — root run의 프롬프트 첫 줄로 갈음한다
- **대화 삭제** — 인박스 보관으로 갈음한다
- **예약 2개 이상, 예약 편집** — 대화당 하나
- **실행 중 끼어들기** — `claude -p`가 못 한다. 취소하고 이어가는 것이 유일한 길이다
- **대화 검색·필터** — 본문 작업이 쪼갠 나머지 셋 중 하나로 남아 있다
- **마크다운 렌더링** — 대화록은 텍스트로 나온다. 별도 후보 작업이다
- **OpenCode 어댑터** — 5단계
- **세션 분기(fork)** — 한 턴에서 갈라져 두 대화가 되는 것

## 8. 확인 필요

**`--resume`이 같은 `session_id`를 돌려주는지 새로 발급하는지가 실측되지 않았다.** 구현 노트 Q31·Q32에 그 관측이 없다.

**이 설계는 어느 쪽이든 동작한다** — 매 턴 체인에서 세션 id를 새로 읽기 때문이다. 같은 id가 유지되면 매번 같은 값을 읽을 뿐이고, 새로 발급되면 가장 최근 것을 읽는다. 그래도 실측해서 구현 노트에 남긴다. 특히 **새로 발급되는 쪽이라면** 3-1의 "가장 최근 것을 고른다"가 필수 조건이지 편의가 아니게 된다.
